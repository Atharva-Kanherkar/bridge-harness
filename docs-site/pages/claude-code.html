agents & runtimes

Claude Code

Claude Code runs inside Bridge through the Claude Agent SDK in a long-lived Node sidecar, never as a claude -p subprocess spawned per turn — that one substitution is what makes a session interruptible, steerable mid-reply, and able to gate individual tool calls in code instead of at a CLI prompt.

A sidecar, not claude -p

Every Claude Code turn in Bridge runs through sidecar/claude-agent/index.mjs, a small Node process that imports @anthropic-ai/claude-agent-sdk and drives one long-lived, streaming-input query() call for the entire life of the session. claude_adapter.rs used to shell out to claude -p once per turn; the sidecar replaces that path entirely, because a one-shot CLI invocation exits after a single reply — keeping a session going meant re-spawning and re-parsing output for every turn.

A longer-lived CLI process would only fix that exit-per-turn problem. What the Agent SDK adds on top is control a subprocess boundary can't offer: a canUseTool callback that decides on every tool call, synchronously, in the same process, before anything reaches the model's tool-execution path — the exact mechanism the briefing boundary below depends on; an interrupt() method on the live query object, so stopping a turn doesn't mean killing the process; and messages that already arrive as typed objects (system, assistant, stream_event, user, result) instead of text scraped off a terminal.

The sidecar's own contract is two frame shapes on stdin and whatever the SDK produces on stdout, one JSON object per line. The stdout shapes are unmodified SDK output — the same shapes Bridge's Claude message normalizer already understood from the claude -p era, so switching transports never required rewriting how Bridge reads a Claude message:

stdio 
// stdin — Rust writes these to the sidecar's stdin
{"type":"user","message":{"role":"user","content":[{"type":"text","text":"…"}]}}
{"type":"control_request","request_id":"irq-3","request":{"subtype":"interrupt"}}

// stdout — raw SDK messages relayed one per line, unmodified
{"type":"system","subtype":"session_ready","session_id":"b8b1e4b2-…","cwd":"/Users/…/worktree","model":"sonnet","resumed":false}

Three verbs cross this boundary. start_turn writes a user frame, and is what send_turn resolves to on the shared AdapterRuntime trait. interrupt writes the control_request frame above; the sidecar's line handler responds by calling the SDK's own run.interrupt(), not by killing the process. respond answers a permission decision the SDK is still waiting on, translating Bridge's own accept / acceptForSession / anything-else vocabulary into the SDK's allow / deny, over a control_response frame.

One more override shows up directly in the product. supports_active_turn_steering defaults to false on the shared trait — most adapters queue a message sent mid-turn and deliver it once the turn ends. Claude's runtime is the one adapter that overrides it to true, because the sidecar feeds one continuous streaming input: a message written while a turn is running is simply picked up by that same turn, the SDK's own steering path, rather than starting a competing one. That flag is also literally what tells Bridge's UI to offer Steer instead of Queue before you submit.

Locating the sidecar

Before any of that can run, Bridge has to find index.mjs on disk. sidecar_entry() tries three locations in order:

BRIDGE_CLAUDE_SIDECAR next to the executable in-repo path
  1. The BRIDGE_CLAUDE_SIDECAR env var. It only wins if the path it names actually exists on disk — an env var pointing nowhere is skipped rather than treated as a fatal misconfiguration.
  2. Next to the running executable. Two candidates relative to current_exe()'s directory: sidecar/claude-agent/index.mjs, and ../Resources/sidecar/claude-agent/index.mjs for a packaged macOS app's Contents/Resources layout.
  3. The in-repo path. sidecar/claude-agent/index.mjs resolved from CARGO_MANIFEST_DIR up to the repo root — what a cargo or tauri dev checkout finds with no packaging step at all.

If none of the three exist, starting or resuming a Claude session fails with exactly this message: Claude Agent SDK sidecar not found (set BRIDGE_CLAUDE_SIDECAR or ship sidecar/claude-agent/index.mjs next to the app).

Node itself is optional at the Bridge level, not just the sidecar. With no node on PATH, Claude reports itself unavailable with "Node.js 18+ is required to run Claude models" instead of blocking the rest of Bridge from starting — the same optional-provider treatment CLAUDE.md describes for every provider CLI.

A second, easily-confused variable sits next to this one. BRIDGE_CLAUDE_SIDECAR picks which script runs; BRIDGE_CLAUDE_SDK_ENTRY picks which installed copy of @anthropic-ai/claude-agent-sdk that script imports. Rust sets it only when a managed runtime payload for Claude is installed, and explicitly clears it otherwise, so a value left over in the environment can never point the sidecar at an SDK Bridge doesn't own. The version Bridge reports for Claude follows the same distinction: it reads the installed SDK's own package.json version — the managed payload's if there is one, else the bundled sidecar's own node_modules — never the Node runtime's version, because the SDK's version, not Node's, is the actual subject a briefing certification check compares against.

Turning a session into SDK options

Model, effort, write mode, instructions, enabled plugins and MCP servers, and whether this is a briefing run all cross the process boundary as one JSON value, passed as the sidecar's argv[2]:

json 
{
  "sessionId": "b8b1e4b2-…",
  "model": "sonnet",
  "cwd": "/Users/…/worktree",
  "resume": false,
  "instructions": "Follow the worker contract…",
  "writeMode": "Isolated",
  "networkAllowed": true,
  "plugins": ["/…/claude-plugins/notion"],
  "mcpServers": {},
  "briefing": null
}

options.mjs's buildOptions turns this into the SDK's own options object. model defaults to "sonnet" whenever the field is missing or blank. Supported effort values (low through max) reach the SDK through its native Options.effort field; an unknown value is omitted rather than guessed. Normal sessions load user, project, and local setting sources so installed skills, commands, agents, and native connector sign-in remain visible. Plugin skills still load, but plugin-bundled MCP auto-discovery is disabled unless the launch explicitly opts it back in; this prevents an authentication-required plugin server from stalling every turn.

writeMode selects a permissionMode, and for ReadOnly, an explicit built-in tool allow and deny list:

Write modepermissionModeBuilt-in tool access
ReadOnlydefault, with prompts disabledVisible local reads: Read, Grep, Glob, Skill, TodoWrite. Bash and WebFetch/WebSearch appear only with task network authority. A Bridge-owned PreToolUse hook allows only exact reviewed MCP identities and denies mutation or unknown tools.
Shared / IsolatedacceptEditsFile edits proceed without a prompt; no explicit allow or deny list.
Full (or unset)bypassPermissionsallowDangerouslySkipPermissions: true — every tool call proceeds unprompted.

ReadOnly still allows Bash. The SDK policy removes direct mutation tools and names every hook denial, but Bridge's actual filesystem-level containment is the separate read-only sandbox covered next. That sandbox makes the checkout and projected host capability sources immutable while leaving one per-worker output directory writable.

instructions — Bridge's delegation protocol and worker brief — never becomes the whole system prompt. It's appended to Claude Code's own built-in preset: systemPrompt: { type: "preset", preset: "claude_code", append: instructions }. Bridge's own prompt-capability ledger records why precisely: Claude's appendable verdict is Supported, because that's what ships; its replaceable verdict is Unsupported, because nobody has yet proven what a bare-string systemPrompt — which the SDK also accepts, and which would replace the preset outright instead of appending to it — actually does to Claude Code's own tool-use instincts, and Bridge won't claim the capability until a live-credentialed integration test confirms it one way or the other. Its readable verdict is Unsupported for an unrelated reason: the SDK compiles the claude_code preset internally and never exposes the resulting text, so Bridge cannot read back what it actually sent even if it wanted to.

Narrower authority: sandboxed and briefing runs

Two mechanisms give a Claude run less authority than an ordinary interactive session gets, at two different layers and for two different reasons.

Read-only sandbox

OS-level. The whole process runs under a macOS seatbelt profile. Used for delegated worker runs.

Briefing run

SDK-level. A canUseTool callback gates every tool call by name. Used for the work board's read-only sweeps.

Read-only sandbox

launch() takes an optional read_only_sandbox: Option<&ReadOnlySandbox>. When it's set, the whole node invocation is wrapped by the shared worker_sandbox::command() helper — on macOS, that means running under /usr/bin/sandbox-exec -f <profile> --, an actual OS-level sandbox, not a permission list the model is trusted to respect. That wrapping isn't Claude-specific — it's shared across adapters (see Worktree isolation for the general mechanism). What follows is specific to this adapter's use of it.

If sandbox-exec is unavailable — off macOS, or a stripped-down macOS install — launch() fails outright: "Read-only workers require macOS sandbox-exec, but it is unavailable; refusing to start without isolation." A sandboxed Claude run never silently falls back to running unsandboxed.

One easy mix-up: under a read-only sandbox, the process's actual OS working directory becomes sandbox.output_dir(), not the cwd carried in the config JSON above — that field still names the real worktree the SDK itself operates on. The two only diverge in sandboxed runs; everywhere else they're the same path.

The rest of what happens here is Claude-specific. launch() points CLAUDE_CONFIG_DIR at a fresh .claude directory inside the sandbox's own output directory rather than the user's real ~/.claude — prepare_isolated_claude_config symlinks in only .credentials.json from the real one, so a sandboxed run can authenticate without inheriting the rest of the user's global settings, hooks, or permissions. CLAUDE_CODE_TMPDIR, TMPDIR, and BRIDGE_WORKER_OUTPUT_DIR all point at that same sandbox output directory. And if CLAUDE_CODE_OAUTH_TOKEN isn't already set in the environment, Bridge reads it straight out of the macOS Keychain (security find-generic-password -s "Claude Code-credentials" -w) rather than requiring it to be exported — a macOS-only path with no fallback, consistent with Bridge being a macOS app.

Briefing runs

A briefing run is how the work board reads your connected tools — search, list, fetch — without a human approving each call. Bridge's own request type documents the design choice directly: briefing authority is a separate axis from write mode, not a rung of it, and the sidecar's briefingOptions() agrees in practice — it replaces the whole permission half of the SDK options wholesale rather than layering on top of whatever writeMode would otherwise have produced. Entering one at all requires write_mode to be exactly ReadOnly; the adapter's own test asserts Shared, Isolated, and Full are all refused.

The gate itself is canUseTool, built by makeBriefingGate. It denies by default and allows exactly two things: an exact match against the reviewed mcp__server__tool wire names Rust compiled into the policy, or a read-verb call (search, read, list, get, query, fetch, find) against a server whose reads were pre-cleared wholesale. Every call that passes is still measured on its serialized argument size against a byte ceiling before it's let through. Nothing is pre-approved through allowedTools — the file's own comment is explicit that doing so would let a call skip the gate, and with it the size check. Around that per-call gate: named built-in tools (Bash, Read, Write, WebFetch, Task, Skill, per the adapter's own pinned test) are stripped before they would even reach it, through disallowedTools; strictMcpConfig restricts the reachable MCP servers to only the reviewed ones; and settingSources: [] plus plugins: [] mean a briefing run inherits nothing from the project it happens to run in. No dialog kind is declared either, which is what stops a permission prompt or an MCP elicitation from parking a run that has no human attached to answer it.
