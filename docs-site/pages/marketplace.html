extensibility

Marketplace & automations

Bridge surfaces two separate catalogs: installable plugins and skills from verified marketplaces, and native scheduled jobs that Claude Code and Codex already keep on disk.

Marketplace & skills

Bridge asks Codex and Claude for their current plugin and skill catalogs, merging both into one browsable list. This is not a proxy marketplace — Bridge invokes the provider's own CLI to query what's available, handle installation, and manage authentication. The providers themselves own the catalog content and the distribution logic.

Plugins and connectors

A plugin is a provider-specific package that brings tools and context into an agent's scope. Codex plugins live in its local app-server; Claude plugins use Model Context Protocol (MCP) connectors for standardized tool definition and lifecycle.

Bridge reads the catalog by running plugin list --available --json on each provider's CLI. For each plugin, the catalog tracks installed state, enabled state, authentication requirement, and available actions. Codex distinguishes between update-only and install/uninstall (those are managed through the app-server handshake); Claude supports the full set including enable and disable.

Actions and authentication

The marketplace catalog for each provider reports which actions are currently available: install, update, enable, disable, uninstall, authenticate. For Codex, the actual install and uninstall actions are blocked through Bridge — the user must authorize them through the Codex app-server UI. Claude allows Bridge to invoke these directly through its CLI.

Authentication varies by provider and connector type. Codex MCP connectors use codex mcp login. Claude MCP connectors use claude mcp login. Codex app connectors (provider-specific) open an authorization URL in the system browser. All sensitive details (tokens, URLs with query parameters) are sanitized before any error message surfaces.

Skills

Skills are packaged automation routines — small, purpose-built prompts that agents invoke when they match the task at hand. Bridge maintains a pinned catalog of 60 community skills, each locked to a specific Git commit hash and published through GitHub repositories. Personal skills are files that live in each agent's skill directory and are never managed by Bridge.

When you install a community skill, Bridge writes a receipt into its own store (~/.bridge/receipts/). This receipt tracks which version is installed, enabling rollback to a previous version or uninstall with confidence that only Bridge-managed copies are removed. If a skill with the same slug already exists as a personal skill (unmanaged by Bridge), installation is refused to prevent accidental overwrites.

Skill installation is executed through npx skills@1.5.19 add, which places the skill files in the appropriate agent-specific directory. Each provider looks for skills in its standard location: Claude Code in ~/.claude/skills/, Codex in ~/.agents/skills/ or the legacy ~/.codex/skills/, OpenCode in ~/.config/opencode/skills/ plus the Agent Skills standard roots.

Bridge's skill catalog is immutable and pinned by commit hash. Every skill entry is verified to have legitimate permissions and risk metadata. Personal skills are discovered but never modified, giving you full control over what gets executed in that namespace.

Automations

Bridge reads the scheduled jobs that Claude Code and Codex natively maintain, showing them in a unified view with minimal mutation capabilities. This is not a scheduling system — Bridge is a read-mostly catalog. Each provider owns its own storage, execution, and scheduling logic. Bridge only aggregates the view and applies the few safe edits each provider's format supports.

Provider support

Claude Code stores tasks in ~/.claude/scheduled_tasks.json, a JSON file that Claude Code's own reader maintains. Each task carries a 5-field cron expression (local-time cron), a prompt, creation timestamp, and last-fired timestamp. The format has no paused state: tasks are either present and active, or deleted. Bridge can delete individual tasks but cannot pause or resume them.

Codex stores automations in SQLite databases under ~/.codex/sqlite/. The app has shipped multiple database names across release channels; Bridge discovers the live automation schema by checking for required columns rather than guessing filenames. Each automation carries an rrule expression (recurrence rule subset), status field (ACTIVE or PAUSED), and historical run records. Bridge can pause, resume, or delete automations, and renders the last 20 run records per automation.

OpenCode has no automations feature; Bridge reports it as unavailable so the UI can say so explicitly rather than guessing.

What Bridge does and does not do

Bridge does not execute automations. It does not modify schedule times or recurrence expressions. It does not alter the prompts or model selection. It reads the native catalog, parses it with fault tolerance (unparseable Claude entries are skipped, not fatal), and exposes a unified read view. The only mutations are delete (both providers) and pause/resume (Codex only).

Automation runs are advisory. For Codex, Bridge renders the thread ID, status, title, summary, and creation timestamp from the run history table. These are read-only: Bridge does not re-trigger, replay, or modify runs. They are shown for context and audit purposes.

Schedule phrasing

Bridge attempts best-effort human phrasing for schedule expressions: "Daily at 09:00", "Weekdays at 14:30", "Every 6 hours". For Claude, it parses the 5-field cron format. For Codex, it parses the rrule subset (FREQ, INTERVAL, BYHOUR, BYMINUTE, BYDAY). Anything irregular falls back to the raw expression.

Availability and errors

The automations catalog always returns successfully, even when stores are absent or corrupted. Each provider in the response carries an available flag and a detail field. If Claude Code has never created a schedule file, it reports as available with "No scheduled tasks yet". If Codex has no database, it reports as unavailable with the reason. Corrupted JSON or schema mismatches surface in the detail field, letting the UI decide how to present the problem without Bridge crashing the session.

Bridge treats automations as read-mostly. The native providers own the full lifecycle, storage, and execution. Bridge's role is unified discovery, best-effort human phrasing, and minimal safe edits.
