getting started

Your first agent

Bridge has exactly two entry points — a direct chat you fall into by typing, and a workspace orchestrator you opt into by connecting a folder — and the two are briefed on entirely different facts about themselves before either reads your first message.

Two entry points

Direct chat

Type into the Welcome composer and send. No folder, no worktree, no delegation — kind: "direct".

Workspace orchestrator

Connect a folder, optionally take an isolated worktree, and land in a session that can ask for workers — kind: "orchestrator".

Open Bridge for the first time and there is one screen: a greeting headline over a single composer pill, nothing else. Type a message and press Enter, or click the arrow, and — unless what you typed is a $harness shortcut, covered below — Bridge calls openNewChat. That creates a session with kind: "direct", workspaceId: null, and cwd: null: a conversation with no folder, no worktree, nothing behind it but a provider process. You are not asked to pick a harness first. openNewChat resolves one on its own: if you already had a direct chat open, it carries that harness and model forward, so switching providers sticks across "new chat"; otherwise it falls back to the adapter behind the configured "standard orchestrator" model profile, then to the first available adapter. A small tier badge (Fast / Balanced / High) sits in the composer's trailing slot, showing which model that first message would actually run on. If no provider is installed or signed in yet, the composer disables itself and its placeholder says so directly — "Install or sign in to a model adapter…" — rather than accepting text it has nowhere to send.

The composer's own + button does not mean "attach a file" here — there is nothing yet to attach to, so Welcome relabels it "New workspace" and routes it to the second entry point instead. Clicking it opens a small dialog titled "New workspace," subtitled "Group related chats. Connect a folder later." — naming a workspace is deliberately separate from giving it a folder. The next step does that: a workspace gets a connect action that opens the OS folder picker, titled "Connect a folder or git repository" in the full desktop app (a fixed path when you run the Vite dev server on its own, since there is no native picker to call). Click + on the resulting workspace card and Bridge asks "Create an isolated worktree?", explaining the choice in its own words: "Bridge can create a new Git branch and worktree automatically. This orchestrator gets its own files and cannot overwrite another chat's uncommitted work." Two buttons follow — "Create worktree," disabled with an inline note if the folder isn't backed by a registered Git repository, and "Use current folder" — plus a caption underneath: "The worktree starts from the repository's current HEAD. Uncommitted changes are not copied." Closing the dialog any other way, including Escape, takes the same no-worktree path as "Use current folder"; its close control is accessibility-labeled "Continue without a worktree," not a bare cancel. Either way you land straight inside the new session's chat, not back on the card or dialog you started from. That session comes back with kind: "orchestrator", the workspaceId you connected, and a cwd pointing at either the fresh worktree or the folder itself.

A third route reaches the same fork more directly once a workspace already exists: a dedicated new-chat action opens a dialog that asks "Where should it run?" up front — no project, or an existing project-backed workspace with its own worktree checkbox — instead of arriving at the choice by clicking through cards.

What kind actually changes

kind is not a label. It decides what a session is told about itself, and even what Bridge bothers to look for in its replies. Every session's system prompt is assembled from a small, fixed set of Bridge-authored sections keyed off a PromptTarget — Orchestrator, Worker(role), or DirectSession — before the provider process ever starts:

prompt sections 
DirectSession  → [rendering_note]
Orchestrator   → [bridge_role, delegation_protocol]

A direct session's one section, rendering_note, says only that Bridge renders diagrams (a fenced ```diagram JSON block — not Mermaid), inline and display math ($...$, $$...$$), and sandboxed HTML specially, and to reach for those only when they communicate better than plain markdown. Nothing about delegation, nothing about capability tiers or effort — just enough for the model to know Bridge's chat is not a plain terminal.

A direct session has no delegation role to brief, but it is still a chat Bridge renders rich content into — it needs the rendering note just as much as the orchestrator does, which is why it carries its own copy of the same text rather than none at all.

That section is recent. Until a fix landed in this repository, DirectSession's list was empty — a plain chat had no idea Bridge renders anything specially, so asking one for a diagram fell back to the model's own habit: hand-drawn ASCII art in a plain code block, not the format the renderer actually understands. The fix gave direct chats their own copy of the note the orchestrator already carried baked into its role briefing, closing a gap that had sat unnoticed until someone actually asked a plain chat to draw something.

The orchestrator's two sections are heavier. bridge_role is orchestrator::briefing() — opening "You are Bridge's starter orchestrator… You are a planner and router" — and lays out when to handle something directly instead of delegating, the fast / standard / strong capability tiers, the low / medium / high / xhigh effort levels, and browser-routing rules, folding its own copy of the rendering note in rather than carrying a separate section for it. delegation_protocol adds the exact shape a delegation request has to take: one fenced ```bridge-delegate JSON object naming a role (research, implementation, verification, planning, documentation), a capability tier, an effort, a write mode, and acceptance criteria — validated field by field before any worker starts, with the exact rejection reason handed back for the model to correct if it gets one wrong.

The gap runs deeper than prompting. Bridge only scans a completed assistant message for bridge-delegate fences when the session's kind is not direct — a flag computed once per turn as is_direct = session_kind == "direct". A direct chat is not merely unbriefed about delegation; its output is never even inspected for the syntax. And being inspected is not the same as being granted: as Bridge's own delegation policy puts it, "Agents may request delegation, but Rust decides whether it runs." The policy engine still checks capability availability, write scope, worktree isolation, concurrency, depth, retries, and budget on every request an orchestrator makes, exactly as it would for any other write. kind: "orchestrator" buys the vocabulary to ask. It does not buy the answer.

The $harness shortcut

One composer shortcut cuts across both entry points. Typing a bare $, a harness id, whitespace, and then a message — anywhere in Bridge's composer — skips whatever session you're looking at and opens a fresh direct chat pinned to that harness, handing it the rest of the text as its first message:

composer 
$codex do you think we're right?

Both composers check for this before doing anything else with what you typed: Welcome's own submit handler, and every open direct or orchestrator session's send path. A $ with nothing after it yet does not fire the shortcut — it drives an autocomplete dropdown instead, matched against the id of every currently available adapter (an unavailable one is filtered out of the list entirely, not just greyed out), prefix matches sorted first. Tab, Enter, or a click completes it to $id  and leaves the caret ready for the real message — picking a harness this way sends nothing by itself.

The shortcut always calls the same path a brand-new chat does, so its result is always a fresh kind: "direct" session — even typed from inside an orchestrator, or a direct chat already pinned to a different harness. It does not retarget the conversation you're in; it replaces your view with a different one. It has no effect inside a worker's own steering box either, which is a separate component that amends the worker's objective rather than sending a chat message.

This is deliberately not the same feature as a /name slash command, which rewrites the current direct chat's harness for its next message and stays put. $harness abandons the session outright. Typing the full $id message form by hand, past whatever the dropdown offered, still works — but only if that harness is actually available; naming one that isn't returns an inline error saying so instead of silently sending the literal text or falling through to your current session.

None of this parsing lives inside ComposerPill itself. The component is deliberately dumb: a value, an onChange, an onSubmit, and a handful of presentation props — layout: "hero" | "dock", a ghost-text suggestion for inline typeahead, activeAction: "steer" | "queue" for what submitting does mid-turn. The $harness state — the query, the match list, the dropdown's own keyboard handling — is computed one level up, in the same place that owns the equivalent state for / slash commands and @ file mentions, and rendered as a popover layered above the same pill. Three independent autocomplete systems wired in from outside is more to assemble than a composer that understands Bridge's own vocabulary directly — but it keeps the pill itself reusable: it renders a text box, and nothing it does depends on knowing what a harness is.
