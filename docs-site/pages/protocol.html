Protocol / RPC

Bridge runs as a versioned JSON-RPC service over a Unix socket, designed so every client — the desktop shell, CLI tools, remote interfaces, and AI agents — speaks the same typed contract.

Why JSON-RPC, not REST

Bridge's surface spans commands, approvals, cancellation, and bidirectional events — RPC is the natural shape for that. REST+SSE was considered and rejected: the protocol needs clients to talk back during an event stream (cancellation, approval responses), and separate polling loops would fragment ownership of the connection state. One RPC channel handles all the traffic.

The protocol lives in the bridge-protocol crate. Everything under docs/protocol/schemas/ and src/protocol/generated/ is generated from a single source of truth and kept in sync by test.

bash 
cargo run --manifest-path src-tauri/Cargo.toml -p bridge-protocol --bin generate-protocol-artifacts
cargo test --manifest-path src-tauri/Cargo.toml -p bridge-protocol

Transports

Bridge supports multiple transports so different clients can connect from wherever they live:

  • Unix-domain socket (local only): <data_dir>/bridged.sock, served by the bridged daemon. This is the primary transport, used by the Tauri shell, CLI tools, and TUI clients.
  • WebSocket (future, remote-capable): Authentication tokens and origin rules are already designed into the handshake so this can ship without redesign.
  • Tauri invoke/event adapter (desktop webview): The React frontend proxies through Tauri, which forwards to bridged by default or runs the runtime in-process in fallback mode.
  • Plain HTTP (health checks only): /healthz and /readyz on 127.0.0.1:4318 for system monitoring.

The daemon and ownership

Only one owner can hold a data directory at a time. bridged acquires an exclusive OS file lease on <data_dir>/owner.lock and keeps it for the entire lifetime of the daemon. If another process — the desktop app, a CLI tool, another daemon — tries to start, it fails fast and reports who holds the lease. The lock dies with the process; kill -9 needs no recovery, and boot-time recovery handles anything the dead process left behind.

A daemon is started with:

bash 
bridged --data-dir ~/Library/Application\ Support/dev.bridge.deck

The desktop app finds or starts the bundled daemon on startup, and bridge exec either attaches to a running daemon (if one owns the directory) or hosts the runtime itself for exactly the duration of the command.

Connection and handshake

Every new connection opens on the Unix socket with mode 0600 (owner-only). The first request must be protocol/handshake, or the server answers invalid_request.

The client sends an auth token from <data_dir>/daemon.token (64-character hex, created 0600 on first daemon start). The server verifies it; a wrong or missing token is rejected with error code 2001 unauthorized before revealing any version or capability information. The handshake has a 10-second deadline; if it doesn't complete in time, the server reclaims the connection slot.

On success, the server responds with:

  • protocolVersion — the protocol level (today 1.0)
  • server.name and server.version — the application identity
  • capabilities — which method domains it serves

A version mismatch is caught here: if the client's major version differs from the server's, the server rejects with error code 2000 incompatible_protocol, including both versions in the error data. A major bump is breaking; a minor bump is additive (new methods, optional fields). A server accepts a client if majors match and the client's minor is not newer than the server's.

json 
// Client request
{
  "jsonrpc": "2.0",
  "id": "hs-1",
  "method": "protocol/handshake",
  "params": {
    "authToken": "a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6"
  }
}

// Server response
{
  "jsonrpc": "2.0",
  "id": "hs-1",
  "result": {
    "protocolVersion": "1.0",
    "server": {
      "name": "Bridge",
      "version": "0.1.0"
    },
    "capabilities": ["sessions", "approvals", "state"]
  }
}

Frame format

After handshake succeeds, the connection speaks newline-delimited JSON-RPC 2.0. One frame per line in both directions; notifications can interleave between responses.

  • Request ids are client-chosen strings or numbers, echoed back in the response. Numeric ids must fit in JavaScript's safe integer range (±2^53 − 1); anything larger is rejected on the wire.
  • Params, when present, must be an object or array. Sending "params": null is rejected; omit the key instead.
  • Responses are a union: exactly one of result or error, never both. "result": null is a valid success (for commands returning nothing).
  • Frames over 1 MiB → error invalid_request, connection closed.
  • Requests per connection are sequential; backpressure is the socket. Only one request is in flight at a time.

A connection that can't keep up with events is told so explicitly: it receives a stream-lagged notification with the count of missed events, then refetch hints, then replay durable history from its saved cursor. Lag is never silent.

Health endpoints

/healthz and /readyz are plain HTTP, served on 127.0.0.1:4318 by default (disable with --health-addr none). A GET /healthz returns 200 when the daemon is alive; GET /readyz returns 200 when it's ready to serve connections. These exist for system monitoring and container orchestration — they are not RPC methods and do not require authentication. Bind and startup failures are fatal and printed to stderr; they never silently fail.

Methods and contract

All methods are in the registry (docs/protocol/schemas/methods.json). Wire names are domain/command, matching the Tauri command names exactly — the compatibility adapter maps by name alone, and a test keeps the registry 1:1 with the shell's command handlers.

Domains include: approvals, browser, sessions, state, health, terminal, config, models, learning, and others.

Every method has a paramsSchema (a schema file) or explicitly null meaning no parameters — there is no uncontracted state. Params use camelCase, matching Tauri's invoke arguments, and a test ensures the registry matches the shell's actual signatures.

Every method's result is contracted too — either a resultSchema (a schema file) or documented as a deferred core DTO, or UnitResult for commands returning nothing. Nothing is silently absent.

Agent harness identifiers

HarnessId is an open string that names which agent runs a session. It follows the pattern [a-z0-9][a-z0-9._-]{0,63}. Examples: claude, codex, opencode, gemini, cline.

The id is the agent, never how Bridge runs it. Claude reached through the Agent SDK and Claude reached through an ACP adapter are the same agent with one id and one session history; the transport is Bridge's concern. This also means a custom adapter can replace a generic one without renaming anything or migrating sessions.

Whether an id is runnable (does Bridge have an adapter for it?) is separate from whether it's valid (does it match the grammar?). A well-formed but unknown id parses fine and fails at session start with an error naming the missing harness.

Params carry strict HarnessId (the pattern above); results carry StoredHarnessId (unconstrained). This way, a session persisted by a newer Bridge with an agent the current version doesn't know stays readable — history doesn't vanish because an agent was uninstalled.

Error codes

Error codes are the contract; message text is not. Codes are never reused or renumbered.

  • -32700 to -32600: JSON-RPC envelope errors (spec-reserved)
  • 1000–1999: Runtime errors, variant-for-variant with bridge_core::BridgeError
  • 2000–2999: Protocol lifecycle errors

Notable codes:

  • 2000 incompatible_protocol — version mismatch at handshake, with both versions in error.data
  • 2001 unauthorized — token missing or wrong
  • 2002 cancelled — request was cancelled
  • 2003 shutting_down — daemon is shutting down and new requests are refused
  • 2004 overloaded — too many concurrent connections

Cancellation

Send a notification named $/cancel with the in-flight request id you want to cancel. Cancellation is best-effort, LSP-style: the cancelled request still gets a response — either its result if it won the race, or error 2002 cancelled if it didn't.

On the daemon's sequential socket transport, a $/cancel notification arrives only after the request it names has already completed, so it's consumed as a valid no-op. For long-running turns, the domain-level interrupt is sessions/interrupt_turn, which stops a running agent session.

Notifications and events

The server pushes notifications to clients. Each notification is marked durable or transient in the registry (docs/protocol/schemas/notifications.json):

Notification Delivery Meaning
agent-event mixed Session entry; durable ones carry a per-session sequence number; sequence-zero frames are transient
state-changed transient Refetch hint: re-read the state snapshot
adapters-changed transient Refetch hint: re-read which agents are available
session-output transient Terminal bytes (worthless once stale)
stream-lagged transient This connection's live event channel dropped events; refetch hints follow, replay durable history from your cursor

The session forest (SQLite) is the source of truth for durable history. The live channel is bounded and notify-only — it drops the oldest events when a receiver falls behind. Durable events are published only after their database transaction commits and carry the cursor needed to reconcile after a disconnect or lag.

Gap-free event replay

When a client connects or falls behind on the live channel, it needs to recover events it missed. Bridge provides two mechanisms working together:

  1. Replay on lag: When a connection can't keep up, it receives a stream-lagged notification naming how many events were missed, then refetch hints. The client re-reads the durable snapshots (via state/get_state, etc.) to catch up on high-level state.
  2. Durable event replay: For a session's raw event history, call sessions/replay_session_events with the last durable cursor you saw (afterSequence). The server returns the next page of missed events in order, no gaps, no duplicates. The default limit is 500 events per page (maximum 1000); keep calling with the last returned sequence until fewer than the requested number of events come back. Transient and sequence-zero frames are never replayed.

This design ensures that across disconnects, daemon restarts, and live-channel lag, a client can reconstruct the exact sequence of events. To close the subscribe-before-replay race: discard any live durable events at or below the highest sequence you received from replay, then process newer live events normally.

The bridge-client Rust crate (src-tauri/bridge-client/) encodes these recovery rules once, so the Tauri shell and TUI build on top of it without reimplementing the state machine.

Clients

Desktop shell

The Tauri app runs as a daemon client by default. On startup it attaches to bridged, or starts the bundled binary and waits for it. Every Tauri invoke is proxied generically: the command's registry method is called with the invoke payload as params, and every daemon notification is re-emitted to the React webview unchanged — the frontend cannot tell which host it is running on.

A supervisor thread owns the connection. After a daemon restart it reattaches on its own, and after any reconnect or stream-lagged marker it emits refetch hints so the UI recovers durable history (open approvals included) exactly as the in-process fallback always worked. The environment variable BRIDGE_DESKTOP_HOST selects the host strategy: auto (default: attach → start → fall back to embedded), daemon (daemon only, no fallback), or embedded (in-process, for migration). An exclusive file lease prevents concurrent daemon and embedded owners of the same data directory.

CLI tools and CI

bridge exec --json is the one-shot CI client. It attaches to a running daemon if one owns the directory, otherwise hosts the runtime itself for exactly that command — CI never keeps a daemon alive. It supports prompt mode via --harness naming an available agent, and --timeout budgeting the whole flow (connect, setup, event stream). Failed turns are recognized by a trailing error event after the completion event. Exit codes: 0 success, 1 failure, 2 usage, 3 timeout.

bash 
# One-shot state read
bridge exec --json --data-dir "$DIR" --method state/get_state

# Interactive turn with an agent
bridge exec --json --data-dir "$DIR" --harness codex "run the tests"

Shared Rust client

bridge-client wraps the handshake, sequential request dispatch, interleaved notifications, and the gap-free recovery rules. It exports SessionEventStream, which yields a session's durable events without gaps across disconnects, lag, and sequence gaps. The Tauri proxy and TUI build on this client rather than reimplementing recovery.

Generated types

src/protocol/generated/protocol.ts is generated from the JSON schemas (one source of truth) and type-checked by tsc. It exports envelope and handshake interfaces, the BridgeMethod string union, the BRIDGE_METHODSERROR_CODES, and PROTOCOL_VERSION. The frontend will migrate onto these types as the compatibility adapter lands.

The protocol is the contract. Generated code is never hand-edited — drift is test-enforced so the schema, the Rust types, and the TypeScript types stay in sync.
