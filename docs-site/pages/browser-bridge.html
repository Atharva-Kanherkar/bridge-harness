extensibility

Authenticated browser bridge

Bridge can supervise one user-approved tab from your normal logged-in browser, letting agents handle workflows that require your existing credentials, personal state, or real-time collaboration — without Bridge ever copying, storing, or persisting browser data.

Why use the authenticated tab

A fresh headless browser starts clean: no cookies, no logged-in sessions, no passkeys, no file upload context. That's the right tool for most work—isolated, fast, repeatable. But some workflows cannot be automated headlessly because they require human-only affordances or state Bridge has no way to recreate:

  • Passkeys and hardware security keys. The browser's WebAuthn API talks to the OS credential store and hardware authenticators; Bridge cannot forge or proxy those interactions. If a site requires passkey auth, you hand over your approved tab.
  • CAPTCHA and challenge flows. Computer use can screenshot and attempt to solve, but many CAPTCHAs are designed to reject non-human patterns. Handed to your browser, they integrate with your device's trust history and human context.
  • Personal logged-in state. Your browser holds sessions to dozens of internal tools, personal SaaS accounts, and authenticated APIs. Rather than orchestrate credential entry (and never store them), Bridge can use what's already there.
  • Real-time visible collaboration. If you're watching the agent work and want to click or navigate parallel to it, both share the same tab state. The agent sees what you just changed; you see what it just typed. No synchronization lag.

When the task fits, this beats asking the agent to solve authentication cold or requiring you to pre-stage credentials.

Browser routing and when Bridge chooses each

Bridge evaluates workflows in a strict priority order. It does not try every option—it stops at the first one that fits:

  1. Structured MCP or API. If the system exposes a programmatic interface (Slack API, GitHub, Notion), use it. Fast, reliable, no UI.
  2. Your attached authenticated tab. If you've registered a tab in Bridge and the task fits (same domain, no credential barriers), use it. Your credentials, your state.
  3. Local headless browser. Fire up Playwright or similar, run locally, isolated. Faster than remote and appropriate for untrusted sites, automated tests, and parallel work.
  4. Optional remote browser provider. If you've configured remote infrastructure (for geo-locking, proxy requirements, or unattended concurrency), route there.
  5. Screenshot-first computer use. Fall back to computer use, the slowest but most general approach. Works anywhere the tab can navigate.

Automated tests, untrusted sites, and isolated QA route to headless first. Geo-requirements or unattended work route to remote. This order ensures Bridge picks the fastest, most direct path without burdening you with credential management.

Setting up your browser

Chrome

The Bridge desktop app includes the native host and extension binaries. To activate:

  1. Build or run Bridge. The Tauri build bundles bridge-browser-host automatically.
  2. Open a task and choose Browser → Register native host. Bridge writes the Chrome native-messaging manifest to the system.
  3. Go to chrome://extensions, enable Developer mode, and choose Load unpacked. Use the extension path shown by Bridge.
  4. Click Find tabs, select one HTTP(S) tab, and grant Interact only when clicking or typing is needed.

The extension ID is pinned in browser-extension/manifest.json; native messaging accepts only that origin. The tab displays a badge while a lease is active. A lease expires after 30 minutes, at task completion, when you manually detach, when the tab closes, or when you navigate outside the granted domain.

Safari

Safari Web Extension support shares the same semantic actions, leases, approvals, and safety rules as Chrome. The implementation lives in safari-extension/. Build it with bun run prepare:safari-extension, which invokes Apple's converter and creates an Xcode wrapper under .generated/. Safari does not expose Chrome DevTools or tab-capture capabilities; otherwise the feature parity is complete.

Safety boundaries and recovery

Read-only is the default. You grant Interact capability only when the agent truly needs to click, type, scroll, or navigate.

Dangerous side effects—submitting a form, sending a message, deleting data, purchasing, publishing, or entering credentials—require explicit approval. When the agent attempts one, Bridge pauses the surface and shows you a plain-language summary. You must click to proceed.

Three field types are permanently blocked from auto-fill: password inputs, payment/card fields, and one-time-code inputs (like 2FA codes). If the agent encounters one, it must hand over control with Take over or Open tab, letting you type it yourself. This prevents credential leakage even if the extension is compromised.

Browser Surface also watches for suspicious instruction-like page text in DOM content and pauses if it detects an attempt to inject commands disguised as content. Sensitive page regions (payment forms, credential entry zones) are redacted before screenshots are delivered to Bridge. Command IDs are retained in chrome.storage.session, so if you reconnect after a detach, the surface resends a stored result instead of repeating a side effect.

Network and console inspection is opt-in and attaches only to your leased tab, never shared or cached.

Bridge does not copy profiles, export cookies, or persist a continuous recording of your tab. The browser itself remains the credential boundary. Extension permissions are read-only by default; you approve interaction and dangerous changes case by case.

Metrics and benchmarks

Bridge records per-site aggregate counts: success, failure, latency, DOM-token usage, screenshot frequency, interventions, approvals, and duplicate side-effect detections. It does not store page text in these metrics. This data helps you understand where agents struggle and which domains benefit from which strategy (authenticated tab vs headless vs computer use).

For researchers and comparative work, testing/fixtures/browser-bridge-benchmark-v1.json defines the evidence schema for authenticated tab, Playwright MCP, Browser Use, and computer use implementations. src/browserBenchmark.ts validates that all scenarios have comparable evidence and rejects incomplete runs.
