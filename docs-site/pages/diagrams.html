Diagrams

Bridge renders its own node/edge diagrams instead of Mermaid — a deliberately narrow format that can't produce illegible output because it has no concept of a generic box.

Why Bridge has its own diagram format

Bridge replaced Mermaid entirely because the problem Mermaid solves — "draw a box-and-arrow diagram without hand-authoring SVG" — enables a different problem: you can author a diagram spec that is syntactically correct but renders unreadably. A Mermaid flowchart with poorly laid-out nodes, overlapping edges, and labels struck through by lines can be produced without error, leaving the author to debug by trial and error.

Bridge's diagram format has no concept of a generic box. It only knows nodes (circles placed on a grid) and edges (lines between them). That narrowness is intentional: a diagram either shows a real mechanism or it doesn't, and if a sentence says it faster, you don't draw it. The renderer is responsible for legibility, not the author. Every diagram is small, because a diagram that's small enough to understand doesn't need 50 nodes.

The visual language

Bridge diagrams follow a single visual grammar across chat, docs, and PRs. Every mark starts achromatic — currentColor, which repaints for free when the theme flips from light to dark. Exactly one hue exists, Bridge's --ring slate blue, reserved for the single thing the reader should follow (the active branch, the approved path, the path the story hinges on). Never use it decoratively, and never add a second hue.

Grid-based placement

Nodes sit on row and col integers. Row 0 is arbitrary; row grows downward. Column 0 is arbitrary; column grows rightward. You place every node deliberately — there is no force-directed layout fighting you.

Fork points draw themselves heavier

A node's visual weight is computed from its out-degree (how many edges leave it). Any node with more than one outgoing edge renders at radius 6px instead of 5px, so forks look like forks without a manual flag.

Muted branches stay visible

An abandoned branch or a denied path never disappears from the diagram. It renders at 45% opacity with emphasis: "muted", embodying Bridge's append-only philosophy: nothing is deleted, nothing is rewritten. The forest only grows.

Markers carry state, not additional colors

Three marker shapes exist:

  • marker: "checkpoint" — a solid halo ring, 11px radius, marking a verified boundary or confirmed state
  • marker: "tip" — a dashed halo ring (stroke-dasharray 2.5 3), marking a live or provisional endpoint
  • marker: "continues" — three fading dots below the node, suggesting growth past this point without drawing every stage

Edges tell a story with shape

curve: true draws a smooth S-curve to a node in a different column — a branch or a fan-out. Straight lines mean the history is continuing down the same logical path. Combined with emphasis: "active" on the edge, a curved active edge reads as the chosen fork.

The DiagramSpec JSON structure

When you author a diagram for Bridge chat or the React component, you write a JSON spec that describes nodes and edges on a grid:

json 
{
  "nodes": [
    { "id": "start", "row": 0, "col": 0, "label": "init" },
    { "id": "fork", "row": 2, "col": 0, "label": "decision" },
    { "id": "active", "row": 4, "col": 0, "label": "chosen path", "emphasis": "active", "marker": "tip" },
    { "id": "abandoned", "row": 3, "col": -2, "label": "rejected", "emphasis": "muted" }
  ],
  "edges": [
    { "from": "start", "to": "fork" },
    { "from": "fork", "to": "active", "emphasis": "active" },
    { "from": "fork", "to": "abandoned", "curve": true, "emphasis": "muted" }
  ],
  "caption": "The active branch continues while the rejected path fades from view.",
  "ariaLabel": "A diagram showing a fork with an active path and an abandoned path at reduced opacity."
}

Node fields

  • id (string, required) — unique within this spec
  • row, col (integers, required) — grid placement
  • label? (string) — short label, kept to 1–3 words
  • emphasis? (enum: "default" | "muted" | "active") — visual prominence
  • marker? (enum: "none" | "checkpoint" | "tip" | "continues") — state indicator
  • labelSide? (enum: "right" | "below") — placement preference (the renderer will override to keep it legible)

Edge fields

  • from, to (strings, required) — node ids (both must exist)
  • curve? (boolean) — true draws an S-curve to signal a branch; default is a straight line
  • emphasis? (enum) — same values as node emphasis

Top-level fields

  • caption (string, required) — the single claim this figure supports (rendered as figcaption)
  • ariaLabel (string, required) — plain-language equivalent for screen readers

Authoring diagrams

In Bridge chat

Wrap the JSON spec in a ```diagram fenced code block. The Bridge chat UI parses it and renders it using the DiagramFigure React component. If the JSON is malformed, it falls back to a plain code block; a bad spec never crashes the chat.

On the docs site or in a README

Hand-author inline SVG following the exact same visual grammar. See the example below for the mechanics. The key constants are:

  • 56px row spacing (vertical distance between rows)
  • Minimum 66px column spacing, widened per-diagram if a label needs more room
  • Node circles: r="5" for normal nodes, r="6" for heavy (fork) nodes
  • Halo rings: r="11", solid for checkpoint, stroke-dasharray="2.5 3" for tip
  • Labels: 11px font, monospace, either right-side (with a short tick) or centered below
  • Colors: currentColor for neutral marks, var(--ring) for the accent

What the renderer guarantees

Three structural guarantees exist so an authored spec never needs hand-tuning around collision detection:

No same-row collision

Column pitch is not a fixed width. It expands for the entire diagram to whatever its widest label needs. Three labeled nodes at col: 0, 1, 2 will never crowd each other, no matter the label lengths. You never need to manually space siblings apart; a short label costs nothing, and one long label among short ones widens the whole grid rather than just the pair that needs it.

No label under a crossing edge

A right-side label sits at its node's y-coordinate — exactly where a horizontal edge to a same-row neighbor runs, so the edge would strike through the text. No amount of column spacing rescues that problem on the wrong axis. The renderer automatically drops any label a same-row edge would cross to below the node. In a horizontal chain (nodes connected left-to-right), every label except the last one typically renders below the line — that's correct, not a fallback.

Display scale compensates for coordinate-space font size

Labels are drawn at 11px in the SVG's native coordinate space, which reads noticeably smaller than Bridge's prose at 15px. The renderer displays the whole figure at 1.35x so labels land at prose size. You don't need to inflate anything yourself.

Keep labels to 2–3 words regardless. A label wider than roughly 12 characters signals the node needs a shorter name, not that the system should find more space for it. The renderer caps truncation at 18 characters with an ellipsis as a hard backstop.
