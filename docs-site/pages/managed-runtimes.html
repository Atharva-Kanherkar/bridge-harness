Managed runtimes & the catalog

Bridge maintains two independent catalogs: one that mirrors the upstream Agent Client Protocol index for discovery, and one that lists exactly which agents Bridge has tested and supports.

Why two catalogs instead of one

Bridge separates discovery from verification because they serve opposite purposes. The upstream ACP registry is descriptive—it says what agents exist and how to fetch them. Bridge's verified catalog is prescriptive—it says which agents Bridge has tested, vetted for safety, and is willing to run.

A single catalog conflates two decisions that must remain distinct: "this agent exists" (upstream says so) and "this agent is safe to run here" (Bridge has tested it). Publishing to ACP is an input to Bridge's verification process, never a substitute for it. An agent can appear in the ACP registry without ever appearing in Bridge's catalog, and Bridge's tested support list does not automatically track upstream releases.

Discovery and verification are separate questions because upstream publication happens at vendor pace and according to vendor judgment; Bridge's testing happens at Bridge pace and according to Bridge's own standards. Treating them as one would mean trusting vendor releases as implicitly verified, which they are not.

The Agent Client Protocol registry

The ACP registry is a read-only mirror of the upstream index published by the Agent Client Protocol project, fetched from a public CDN without authentication. It answers the question: what coding agents are available, how do I fetch them, and which platforms support them?

Bridge reads this registry to show users what agents exist and which ones are installable on their machine. If an agent offers an npm package, a PyPI package, and macOS and Linux binaries, the registry entry names all four methods. A user can see that an agent is available even if no build exists for their platform—the catalog is transparent about what is and is not supported.

The registry parser is tolerant, not prescriptive

The published ACP schema documents certain fields as required, but the actual registry has entries missing those fields. For example, repository is documented as required yet absent on 6 of 38 upstream entries; website is absent on 7. Rather than reject these entries as invalid, Bridge parses them pragmatically—it follows the data, not the schema. If an entry cannot be installed by any method Bridge understands, it is skipped and counted; one uninstallable entry does not drop the entire catalog.

Caching and freshness

The registry is cached locally with its ETag. A second fetch sends the cached tag back; if upstream confirms the copy is current with a 304 response, the cached copy is reused. If the network is unreachable or upstream unavailable, the cached copy is served marked as stale—the caller can say the catalog is old rather than silently showing unchanged data. A fetch failure with no cache is an error.

The registry cache stores the verbatim upstream document, not a parsed version of it. When Bridge's parser improves later, previous skipped entries automatically reparse on the next read without waiting for a network refresh.

Bridge's verified catalog

The verified catalog lists agents at exact versions that Bridge has tested and supports. Each entry is authenticated, validated, and installed whole or not at all. Nothing in this catalog could carry an executable, a command, a script, an interpreter, or a credential—everything executable lives in a named integration module compiled into Bridge itself.

Verification is structural, not inferred

An entry reaches the verified catalog only through explicit testing. The Verification struct in each entry records which revision of the conformance suite produced the verdict, when it ran, and an opaque reference to the evidence. There is no field where a verdict could be inferred from upstream activity or cached from a previous check—the only way a Verified status exists is if evidence was produced for it. A Pending verdict (queued but not yet run) or a Failed verdict (tried but failed) never loads; an entry carrying either is refused before it reaches the user.

Each entry is signed and cannot be rolled back

A snapshot document is authenticated with an Ed25519 detached signature before parsing. The signature is verified over the exact bytes on disk before anything reads them—a document Bridge cannot authenticate is a document it will not parse. Each snapshot carries a monotonic generation number; a snapshot that does not advance the generation is refused, which prevents a replayed older document from reinstating a withdrawn entry.

When a snapshot is installed, the exact bytes that verified and the detached signature over them are cached separately. On restart, the cached bytes go through the full authentication and validation path again—a cache that is missing, tampered with, or valid-but-now-refused (a key withdrawn, a Bridge downgrade, an entry this build no longer accepts) loses to the bundled bootstrap, so Bridge always has a catalog.

The bootstrap catalog

Bridge ships a compiled-in last-known-good catalog. It is empty of agents by design—the catalog framework exists to make verification structure testable, not to ship real agents in this epic. The bootstrap passes exactly the validation a remote snapshot must pass, so it is a fallback that can actually serve, not a placeholder.

How they work together

A user sees the ACP registry in Bridge's UI as "agents available to install from"—it is the scope of what can be discovered. Within that scope, Bridge filters to the verified catalog when deciding which agents are safe to run. The two catalogs answer sequential questions:

  1. Does this agent exist and have a way to fetch it? (ACP registry answers)
  2. Has Bridge tested this exact version and does it approve? (Verified catalog answers)

If both answers are yes, the agent can be installed. If the ACP registry lists an agent but the verified catalog has not tested it, that agent remains discoverable but unrunnable—the user sees why and what stands in the way rather than the agent disappearing silently.

Runtime lifecycle and ownership

Bridge manages agent runtimes through ten states: not_installed, installing, installed, ready, running, stopping, uninstalling, external, broken, and repairable. Payload ownership, integration readiness, and process liveness are three independent facts tracked separately.

When an agent is installed, Bridge does not trust that the bytes are what it thinks they are. Instead, every installation carries an embedded receipt plus an atomically written active receipt. The receipt records the exact integrity digest of the installed tree—not hashed permission bits (those do not survive every transport), but the logical file tree folded into a SHA-256 hash. If a payload is later modified, the digest no longer matches and the installation reports as drift rather than being handed out to run.

An installation id is derived from the agent, version, platform, and integrity without source. This means a relabelled but byte-identical artifact maps onto the same directory and passes its own check, rather than being forced into a new location every time the source URL changes.

Resolution order

Every agent resolves its runtime in one order: the executable the user configured explicitly, then a Bridge-managed receipt-bound payload, then a copy bundled with the app, then the system PATH. The first hit wins. A managed payload that has drifted—its receipt no longer matches what is on disk—is not handed out at all; resolution falls back to the user's own copy instead of launching bytes that no longer match their receipt.

Removal requires ownership proof

Removal reads and validates the receipt chain, requires every owned path to be a safe relative descendant of the managed root, and removes only that receipt-owned installation plus the active receipt. A corrupt receipt, an unproven directory, a symlinked managed ancestor, or an owned path outside the exact installation all fail closed without deleting anything. Removal additionally refuses while a provider process is alive for that agent—a payload cannot be removed underneath a live process. Stale rows must not make an agent permanently un-removable, so identity is verified against tracked adapter pids and their recorded OS identity rather than assumed.

The agents RPC domain

Operations run to completion and their result says what happened—installed, repaired, removed, already current, already absent—plus the post-operation status. There is deliberately no operation id and no progress stream because backgrounding these operations is a future change with a new result shape, not a reinterpretation of this one.

Eight conditions get stable error codes in a 3000 range: unsupported platform, integrity failure, external-not-managed, busy, corrupt receipt, vendor prerequisite missing, uninstall not permitted, and unknown agent. They live in a typed domain error so a client can act on them differently and a UI can say which one happened without parsing prose.

Settings UI

The managed runtimes surface in Settings → Harnesses → Agent runtimes. One card per integration appears above harness configuration—whether an agent is installed comes before how it behaves once it runs.

Removal is offered only when removable is true, the API's own answer to "is this Bridge's to remove". The UI never derives removability from a state string, so a future state it has never heard of cannot open the destructive path.

A working user install reads as settled: it says it works, names itself as the user's own, and offers letting Bridge manage its own copy as a quiet opt-in. Removal asks first, and the confirmation names the exact payload—label, version, path—and states what survives: conversation history, vendor configuration, sign-in, and any copy the user installed themselves. Focus lands on the keep action.

No credentials here

Nothing in this subsystem owns a credential. There is no API-key form, OAuth client, credential vault, login dashboard, or logout action. A vendor that needs a login surfaces its own message verbatim under the vendor-prerequisite code, and the agent stays installed rather than being recast as broken—nothing is broken, the user simply has not authenticated with the vendor yet.
