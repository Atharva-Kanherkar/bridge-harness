git & worktrees

Worktree isolation

Every agent runs in its own git worktree, stored alongside its siblings on disk, isolated by owned-path leases and a durable adoption lifecycle that survives restarts.

What is a Bridge worktree

Bridge uses git worktree to give each agent its own directory alongside the user's checkout. The workspace tree has three levels:

Repository root

The original clone or working tree the user is using.

Task worktree

One per Bridge session, the checkout the user is currently working against — usually a branch.

Worker worktrees

Isolated checkouts where agents run. Each gets a child worktree under a namespace directory.

On disk, the structure looks like this:

text 
my-repo/
  .git/
  src/
  bridge/
    task-worktrees/
      prague/           # one task worktree per Bridge session
        .git
        src/
    worker-worktrees/
      prague/           # namespace per task
        claude-123/     # one child per agent, named by session ID
          .git
          src/
        claude-456/
          .git
          src/

Each agent gets a dedicated directory where it writes, commits, and potentially makes changes. For isolated agents, this child worktree is completely separate from the user's checkout — the agent's work stays in its directory until the user decides to adopt it.

Isolation by owned-path leases

When an agent is launched with write access, it declares which paths it owns. Bridge enforces these leases so concurrent agents cannot edit the same files. A lease like ["src/**", "tests/integration/**"] means the agent can write anywhere under those patterns, while other agents touching those paths are refused creation entirely.

This is checked when the worktree is created, not during execution — create_child_worktree queries the database for active writer sessions and calls authorize_disjoint_writer. If overlap is detected, the new worktree never gets created. Once a worktree exists, the paths it can touch are fixed, so the user can start multiple agents without them colliding later.

In-place writers share the task checkout with the user and with each other. The lease still prevents overlapping writes, but they operate on the same files, so they need coordination outside the worktree system.

The adoption lifecycle

Agents that write into isolated worktrees produce changes that exist only in their directory. Bridge records where every write-mode agent runs in a worker_worktree_adoptions row, and tracks whether the user has approved merging that work into the task checkout.

The lifecycle has five states:

states 
in_place          # agent wrote directly in task worktree; nothing to adopt
pending_adoption   # isolated agent produced changes; awaiting user decision
adopted            # changes merged into task worktree
discarded          # isolated changes thrown away on purpose
empty              # isolated agent finished without touching files
settling           # adoption or discard in flight; claim prevents race conditions

Recording the binding

When an agent starts, Bridge records a binding: the path where it will write, the base commit it started from, what the task checkout's branch is, and which paths were already dirty (for in-place writers). The state depends on whether the agent writes in isolation or in place.

For an isolated worker, the initial state is pending_adoption. For in-place writers, it's in_place immediately, because there's nothing separate to adopt — they're editing the shared task checkout.

Deriving evidence and settling the state

When the agent finishes, Bridge reads the Git state of its checkout: what commits it made, what paths it changed, whether the tree is dirty. This derived evidence is the ground truth. An isolated agent with no commits and no uncommitted changes is marked empty. One with changes is marked pending_adoption and waits for the user.

If the agent worked in place, the binding is immediately marked in_place — there's no separate worktree to adopt, so the state is terminal and the worktree directory is left alone (it's the task checkout, after all).

A parent session cannot finish until all its children are in a terminal state (adopted, discarded, empty, or in_place). The user must make an adoption decision for every child with pending changes before they can close the session.

Integration without verification loss

When changes are adopted, Bridge runs git merge --no-ff to integrate the worker's branch into the task worktree. But it doesn't just blindly merge: it checks that the tree being merged is the exact same tree that passed a completion gate during verification. If the worker's checkout changed after being verified, or if the task branch advanced so the merge produces a combined tree nobody verified, adoption records that the proof is stale and re-opens the completion gate.

This prevents a simple race: agent finishes, gets verified, then something else edits its worktree before adoption completes. The merged result wouldn't be the verified one, so it needs re-verification.

For dirty worktrees (common with coding harnesses that don't commit), Bridge calls commit_worker_worktree to capture the uncommitted edits onto the worker's own branch before integrating. That way the normal case — edit, don't commit, adopt — still works.

Cleanup and removal

Worker worktrees are never removed until their adoption state is terminal and the worker session can no longer be resumed. This is conservative by design: removing a directory while a session is warm or active would break resumption.

The flow is:

  1. Adoption or discard settles the state in the database.
  2. Bridge calls git worktree remove only if the binding is terminal and the worker is not reusable.
  3. A maintenance pass (release_terminal_worktrees) runs periodically, collecting any worktrees that have since become collectable.

If removal fails — the tree is dirty, another session is using it, or Git refuses for any reason — Bridge silently leaves it in place and logs the event. No work is ever lost to a background cleanup failure.

Worker adoption after restart

Bridge's data directory can be shared across sessions. If Bridge crashes with a worker adoption in flight, the database record survives. On startup, worker_adoption::recover reconciles the database state with what actually exists on disk.

Stuck claims

An adoption or discard sets the state to settling before Git runs (with the database lock released, so Git doesn't block other operations). If Bridge crashes mid-Git, restart finds a settling row. Recovery unsticks it by returning to pending_adoption, so the decision can be retried.

Missing worktrees

If a worker worktree no longer exists but its binding is still pending_adoption or settling, the work was already lost (perhaps deleted manually, or cleaned up by another process). Recovery marks the binding discarded explicitly, with a detail message explaining the worktree was gone. This unblocks the parent session instead of leaving it wedged forever waiting for work that will never reappear.

Warm workers and worktree retention

A worker that was warm at adoption time (paused, not finished) is never removed immediately, because the user might resume it. The binding stays in its terminal state but the directory remains. Only when the worker genuinely becomes terminal — finished and un-resumable — does the maintenance pass collect it.

Similarly, if multiple workers share a worktree path (a verifier running in the same checkout as the implementation worker), removal is blocked until all of them are done. Bridge queries live_borrowers to find every session currently using that path and refuses removal if any are still running.

Why this design

The three-level workspace tree could be flattened — every agent could write into a fresh clone. But that's expensive: cloning a large repository for every agent, fetching updates, managing disk space. Git worktrees solve this by sharing the object database and letting multiple working trees point to the same repository, so the overhead is just the `.git/` metadata and the working files.

The durable adoption lifecycle exists because agents are not trusted to be correct about what they changed. A coding harness might claim it modified five files when Git shows ten. Or it might have crashed and left the worktree dirty. By deriving evidence from Git rather than from the agent's report, Bridge always knows the truth. And by gating adoption on a decision the user actually made, Bridge never silently merges unreviewed work.

Recovery reconciliation handles the restart case: a data directory that survives a crash should still be usable. An agent's worktree might have been deleted by the user or by the OS, but the database row lived on. Rather than assuming the row's state was correct, recovery checks disk and corrects the record — turning stuck claims back to pending, and marking work permanently discarded when its worktree is gone.
