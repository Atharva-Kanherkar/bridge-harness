Environment variables

Bridge responds to a set of environment variables that control where it stores data, which host backend it uses, and how to locate its bundled components.

Data storage

BRIDGE_DATA_DIR

BRIDGE_DATA_DIR sets the directory where Bridge stores its SQLite database, session history, and other persistent state. If you run bridged (the daemon) as a command-line tool, you must either pass --data-dir or set this variable; one of the two is required. The desktop app falls back to a platform-specific default (~/Library/Application Support/dev.bridge.deck on macOS, $XDG_DATA_HOME/dev.bridge.deck on Linux) if neither is set.

Exactly one owner can hold the data directory at a time — enforced by a file-system lease. If you need two concurrent instances (for example, testing multiple versions in parallel), use separate data directories.

Host mode

BRIDGE_DESKTOP_HOST

BRIDGE_DESKTOP_HOST tells the desktop app which host backend to use. Valid values are auto (default), daemon, or embedded.

auto: The app attempts to use a daemon-backed session; if bridged is not reachable, it falls back to the embedded in-process host. Simplest for most users.

daemon: The app requires a running bridged instance and proxies every invoke through the socket. If the daemon is not available, the app exits at startup. This mode is intended for setups that want the performance and isolation characteristics of a separate daemon process.

embedded: The entire runtime runs in-process within the app. No separate daemon is needed. Useful for single-user scenarios or when network proxying overhead is a concern, but the app cannot be backgrounded as cleanly.

Component location

Bridge ships with several bundled binaries and external programs. These variables override the automatic location logic.

BRIDGE_CLAUDE_SIDECAR

Path to the Claude Agent SDK sidecar entry point, typically sidecar/claude-agent/index.mjs. If set, the path must exist. If not set, Bridge searches (in order): next to the main executable (production app bundle), then the in-repo path (development). The sidecar is how Bridge runs Claude Code agents through the Claude Agent SDK in a Node.js process.

BRIDGE_BROWSER_EXTENSION

Path to the browser extension folder. If set, this directory is used directly. If not set, Bridge searches (in order): next to the executable in the macOS app-bundle structure, flat layouts at the same level as the binary, then a compile-time fallback for development builds. The browser extension enables native host communication for the Bridge browser integration.

BRIDGE_OPENCODE_SIDECAR

Path to the OpenCode sidecar executable. If set, this exact path is used first. If not found or not set, Bridge searches next to the main executable. This is one entry point for managed OpenCode sessions.

BRIDGE_BROWSER_HOST

Path to the bridge-browser-host native executable. If set, this path is used. If not found or not set, Bridge searches next to the main executable. This binary is installed as a browser native host manifest for handling browser bridge communication.

BRIDGE_DAEMON_BIN

Path to the bridged daemon binary. If set, this path is used to start the daemon. If not set, Bridge searches next to the main executable. Rarely needed because the daemon is usually discovered automatically or the app runs with BRIDGE_DESKTOP_HOST=embedded.

Worker isolation

BRIDGE_WORKER_OUTPUT_DIR

When a worker runs in read-only OS isolation (via Seatbelt on macOS), the workspace and parent directories are immutable. BRIDGE_WORKER_OUTPUT_DIR is the only writable location available — Bridge sets this per-worker to an isolated output directory. Workers should write artifacts, logs, and temporary files here rather than trying to mutate the workspace. The policy engine enforces this through the sandbox; users and agent runtimes learn this directory from the environment and can produce outputs that Bridge will later retrieve.

BRIDGE_READ_ONLY_NETWORK

Set to deny or denied to deny network access in worker sandboxes during read-only OS isolation. If not set or set to any other value, network access is allowed at the runtime's discretion. This is a blunt knob: it applies to all workers globally, not per-delegation. Most installations leave this unset and control network policy through policy & delegation instead.

Process supervision

BRIDGE_DISABLE_PARENT_WATCHDOG

The parent watchdog is a background monitor that kills a wrapped child process if the supervisor that spawned it dies (crash, SIGKILL, or unclean exit). This prevents orphaned agent runtimes. Setting BRIDGE_DISABLE_PARENT_WATCHDOG to any value disables this monitor. The watchdog is enabled by default and should not be disabled in production.

BRIDGE_SKIP_LEGACY_ORPHAN_SWEEP

On startup, Bridge scans the system for orphaned opencode serve processes that predate the process ledger — accumulated before process-supervision history was tracked in the database. Setting BRIDGE_SKIP_LEGACY_ORPHAN_SWEEP skips this scan. This scan is rare (runs once per system after an upgrade) and can be skipped if your Bridge installation started after process ledger was available. Never set this unless you know you need to.

Provider discovery

Bridge locates the Codex, Claude Code, and OpenCode command-line tools by checking your PATH environment variable. If a provider CLI is missing, its adapter is marked unavailable instead of blocking startup. To use a provider, ensure the codex, claude, or opencode command is on your PATH, or build Bridge with the vendor runtimes under runtimes/.

Component location variables are rarely needed — they exist primarily for testing and for deployments where the app bundle layout differs from the standard macOS structure. In normal use, Bridge finds everything automatically.

Internal use only

BRIDGE_LOCK_HELPER, BRIDGE_LOCK_HELPER_DIR, and BRIDGE_BROWSER_SOCKET are set internally by Bridge or used during testing. Do not set these yourself.
