core concepts

Policy & delegation

The policy engine decides whether an agent's request runs, queues, or requires approval before anything starts.

What the policy engine decides

When an agent requests delegation—work that is large enough or risky enough to run in isolation—Rust's policy layer decides what happens next. The request arrives as a typed envelope containing the task family, objective, capability tier, requested write paths, owned-path boundaries, and what the agent already knows about the target. The policy engine returns one auditable decision:

  • Execute in parent — run the work in the same session without spawning.
  • Resume a compatible worker — a previous worker can pick up this objective.
  • Spawn — create a new isolated session and start the work.
  • Queue — hold the request until conditions change (resources free, parent completes a turn, human approves).
  • Reject — the request violates a hard constraint; it cannot run.
  • Require approval — the request is valid but needs a human to authorize before spawning.

This is not a ranking system. Each request goes through the same sequential gates. Policy is deterministic about structure: topology, concurrency limits, capability tier thresholds, budget tracking, and trusted path provenance. It does not reason about whether an objective is semantically wise or appropriately decomposed—that judgment stays at the boundary where durable user evidence decides.

Sequential policy gates

A request passes through five independent gates in sequence. Each gate checks a single constraint; passing all five leads to spawn, queue, resume, or approval.

The five gates check:

  1. Capability tier. Does the agent have authorization to run at the requested level? Bridge tracks three tiers: fast, standard, and strong. Tier escalation is terminal after strong.
  2. Write scope. If the request writes, do we have durable evidence the user authorized those exact paths? This is the strictest gate—requests without write authorization pause and require an approval card before spawning.
  3. Concurrency budget. How many workers can run in parallel? Are there spare slots? Bridge enforces per-turn worker counts and capability-unit budgets (24 units per turn by default, with strong workers consuming more).
  4. Worktree isolation. If the request needs a worktree, are there conflicts—overlapping write ownership, active siblings, or resource exhaustion? Overlapping writers queue FIFO; conflicting paths are detected at the path-component level.
  5. Approval. Does the request require human approval that is not yet granted? If so, pause and emit an approval card before spawning.

Cross-harness projection

Agents may request delegation to a different harness—asking Codex to spawn a Claude worker, or Claude to use OpenCode. Provider reasoning state cannot move between Codex, Claude, and OpenCode because each has its own model and internal reasoning history. Bridge handles this by not moving the state directly. Instead, cross-harness requests are projected: the child receives the evidence from the parent's work so far, but not the raw provider transcript.

Policy keeps a cross-harness request queued while its parent has an active turn, releasing it after turn completion, a durable checkpoint, a compaction boundary, or worker-result verification. The session records one of three states:

  • native — same-harness continuation.
  • projected_at_boundary — cross-harness, released at a safe point.
  • projected_mid_turn — cross-harness request arrived during an active parent turn and had to wait. This is still possible under races and is surfaced as degraded rather than hidden.

This design ensures reasoning state stays tied to the harness that produced it, while allowing agents to delegate work across providers.

Worker approval workflow

When a worker needs approval—either for write scope or another gate—it enters a durable blocked_on_human state. This is not a failure; it is a legitimate pause where the worker waits for a decision.

Mirroring to the parent

A worker's approval card normally appears on the worker's own conversation, which may not be visible if you are focused on the parent. Bridge mirrors the card onto the parent conversation with the worker's label, objective, command, and owned-path scope, so you see the blocker immediately. Resolving the approval from any surface—the parent's mirrored card, the worker's own card, or the mission control detail view—updates both the parent and the worker lifecycle together.

Timeouts and cleanup

A worker waiting for approval has its own deadline separate from the general stall watchdog: WORKER_APPROVAL_TIMEOUT_SECONDS (30 minutes). If no decision arrives by then, the worker is resolved to a terminal blocked result naming the unanswered approval, which releases the parent. The timestamp waiting_since is updated every time a worker enters or leaves the waiting state, so an expired approval cannot leave stale timestamp data behind.

A blocked-on-human worker is legitimate pending work. It is never treated as failed or timed out by the general stall watchdog because approval delays are legitimately long—users may be thinking, away, or handling other priorities.

Write scope authorization

Write-capable workers must prove the user authorized the paths they will modify. There are exactly two ways authorization can happen, and no third:

  1. User declares the scope in their message. A line like Write scope: src/**, docs/** in the user's message authorizes those paths for that turn. The syntax is exact: the line must start with write scope: (case-insensitive), appear outside code fences and block quotes, and list paths comma- or semicolon-separated and repository-relative.
  2. User accepts an approval card. When no declaration covers the requested paths, policy raises an approval card with the exact paths shown. Accepting it authorizes only those paths.

Anything else does not authorize: assistant-proposed ownedPaths, repository exploration, or path mentions in prose. Read-only workers skip authorization entirely because they cannot write.

The practical flow

A cold-start request like "implement X" from a user who has not used the Write scope: syntax will raise an approval card. That is designed behavior, not a failure. The parent receives a structured notice with the remediation reason so neither you nor the orchestrator has to guess. On acceptance, the launch proceeds. On decline or cancel, the worker is never spawned.

Bridge normalizes repository-relative declarations and checks them against the real workspace tree. Existing files and directories are eligible. A new file is eligible only when its immediate parent exists. Canonical-path checks reject scopes that escape through symlinks.

Shared writers and worktree isolation

Read-only workers run concurrently without conflict. Write-capable workers follow stricter rules:

  • A shared writer (multiple workers writing in the main worktree) requires non-overlapping ownership. Workers claiming different path sets can run in parallel.
  • Overlapping writers queue FIFO. Two workers both writing to the same file or directory are serialized; they wait for earlier claims to complete.
  • write mode: isolated always creates a child worktree, even for a lone writer. Isolation is a promise about where writes land, not an optimization applied only when contention exists.
  • Every write-capable worker gets a durable repository binding at launch, recording the exact checkout and base revision it runs in. worktree_path is never null after launch.
  • Read-only workers are checked after execution; tracked file changes fail the guard and the worker is downgraded to blocked.

Adopting isolated worker output

When a worker runs in an isolated worktree, its output is not automatically merged back. Verifying that the worktree is consistent proves nothing about the user's task checkout. Isolated output has an explicit lifecycle:

Isolated worker lifecycle 
in_place              shared/full writer — nothing to adopt

pending_adoption ─┬─ adopted            fast-forward merge into task worktree
                  └─ discarded          thrown away

empty                 isolated writer changed nothing

A parent cannot become ready while any child sits in pending_adoption, so every verified change must be explicitly adopted or discarded. Adoption refuses to run against a dirty or active task worktree and rejects non-fast-forward merges, leaving work pending rather than losing it. Child worktrees are removed only once their row is terminal.

Repository evidence and verification

Before a write-capable worker's result becomes canonical, Bridge checks the work against Git. The result is checked against the actual repository state in the worker's worktree:

  • Bridge derives HEAD, branch, committed and dirty paths, and a diffstat from the worker's bound checkout.
  • The result's filesChanged is replaced with the derived path list, so a worker cannot suppress required tests by omitting a path, nor invent irrelevant ones.
  • A completed claim is downgraded to blocked if the repository shows no change at all, or if the worker wrote outside its owned-path lease. The reason is explicit evidence-mismatch.
  • Changed-but-unreported paths are recorded as risks and surfaced to you.
  • The derived revision, branch, dirty state, and diffstat are carried into the parent-facing result.

This verification is deterministic and structural. It does not prove an objective is semantically complete or wise—only that the claimed work matches Git reality. Human approval remains the boundary when that proof is absent.

Completion proof and verification gates

Implementation workers open a durable completion contract from the user's acceptance criteria. The contract, deterministic eval plan, check runs, findings, and proof live in SQLite. Bridge runs implementation and verification sequentially, not in parallel.

Deterministic build, test, lint, and repository commands become required gates. Bridge executes them: the core check runner takes one pending shell check at a time, runs the command in the worker's exact repository path with no shell expansion, captures bounded output and exit status, and records the verdict. Commands are allowlisted by program name; any other program or shell metacharacters are refused and recorded as blocked.

Verification has a deadline: COMPLETION_VERIFY_TIMEOUT_SECONDS (45 minutes). Past it, every required check that never reached a terminal state is recorded blocked with an explicit reason—for semantic checks, that no eligible verifier claimed it. The attempt fails and the parent is released so it can decide next steps. Timed-out gates are marked on the attempt and distinguished from gates Bridge could not build at all; the latter still fails closed and requires an explicit waiver.

A skill or plugin can register a verifier manifest describing triggers, required tools, and cross-family requirements. Matching manifests are added to the plan, but they cannot grant themselves capabilities or mint passing evidence.

Permission bypass

You can configure Bridge to skip approval requests automatically. This is a global setting that applies to every session and workspace. The bypass toggle appears in Settings > Permissions as Bypass all approvals.

What bypass does and does not do

With bypass on (bypassAll: true), every regular approval from any provider is resolved accept immediately, through the same function a human click calls. The session, worker lifecycle, mirrored card, and parent notice all behave exactly as they would for a human decision. Auto-approved requests are recorded in a durable audit ledger as approval.auto_allowed entries.

Two gates survive bypass and will still raise approvals:

  • Worker write scope. Write-path authorization is a structural gate raised by policy.rs, never over a provider control channel, so it cannot be auto-answered. It will still pause the worker and require an explicit approval or a Write scope: declaration.
  • Browser outward effects. Sensitive browser operations (send message, purchase, publish, enter credentials) are gated separately in browser_bridge.rs with their own audit channel. Bypass does not touch them.

Auto-approval is deferred until after a request is persisted to the database, ensuring every auto-approved action is durable.

Visibility while bypass is on

A persistent badge in the app chrome reads "Approvals bypassed" whenever the policy is on, so the mode is never invisible. Each auto-approved request is shown in the conversation as an approval.resolved entry, identical to a human resolution, and listed in Settings > Permissions under recent auto-approvals. The audit trail is complete and durable.

Bypass is a global convenience setting, not a security override. Write-scope authorization and sensitive browser gates remain enforced. Use bypass when you trust your agents completely within these boundaries.

Cost and quality routing

Bridge can learn from worker outcomes to predict which provider and model will work best for each task. The learning router records the complete inventory of candidate harnesses and models, reasons for excluding each, conservative pass-probability estimates, latency predictions, normalized cost, and retry risk.

The router starts in shadow mode per workspace. Shadow recommendations are measured while the baseline route continues. Autonomous mode cannot be enabled until the workspace has at least 20 completed shadow outcomes with fewer than 5% no-route selections. Users can pin or exclude harnesses and models, but preferences cannot revive a candidate excluded by availability, platform, permissions, quota, or deterministic policy gates.

Learning selects a candidate before the policy gates run, not instead of them. Owned-path provenance, approval, depth, concurrency, worktree, and budget rules in Rust still decide whether the selected route may spawn, resume, queue, or run at all. Failed worker results become outcome labels, not permission to alter safety policy.

Replay past decisions without starting a provider by running cargo run --manifest-path src-tauri/Cargo.toml --bin policy-replay -- /path/to/bridge.db --workspace WORKSPACE_ID. Test proposed policy changes against historical requests.
