agents & runtimes

Codex

Codex is Bridge's one adapter that never leaves native code: it spawns the codex binary itself in its own long-lived app-server protocol mode, with no Node runtime, SDK package, or sidecar script standing between Bridge and the model the way there is for Claude.

One subprocess, not a chain of them

Bridge launches Codex by spawning the codex binary directly, in its own protocol mode: codex app-server --listen stdio://. Stdin, stdout, and stderr are all piped — stdin carries every request Bridge writes, stdout carries everything Codex writes back (handshake responses, turn events, and Codex's own incoming requests, all interleaved on the same stream), and stderr is captured into a bounded rolling tail kept only for failure reporting. The process is spawned once, at start or resume, and stays open for the life of the session: every later turn is a new message on the same pipe, not a new invocation of the binary.

That persistence is exactly the point of contrast with Claude. Claude's adapter never invokes the claude binary for a turn — it spawns node running a script Bridge itself wrote (sidecar/claude-agent/index.mjs), which imports and drives the @anthropic-ai/claude-agent-sdk package. The adapter's own comment explains why: Claude runs through the Agent SDK, driven by a Node sidecar, so that one long-lived streaming query serves every turn on a single session — fixing what the comment itself calls the claude -p ‘exit after one turn’ behaviour. Codex doesn't need an equivalent layer, because its own app-server mode already is that long-lived, stateful protocol; Bridge's job is to speak it, not to build persistence on top of something that lacks it.

Day to day this is mostly invisible — a Codex-backed session looks like any other Bridge session — but it does mean Codex has exactly one external dependency: the codex binary itself, Bridge-managed or already on your PATH. Claude needs Node 18+ as well; claude_adapter::start fails immediately with an explicit message if node doesn't resolve, a check Codex's launch path has no equivalent of.

Starting and resuming a thread

A session opens with a synchronous handshake: initialize (request id 1), wait for the matching response, then a bare initialized notification with no id — Codex isn't expected to answer it. Only then does Bridge send thread/start for a new session, or thread/resume for an existing one, as request id 2, and wait again. wait_for_response reads the stream line by line until it finds a frame whose id matches the one it's blocking on; Codex is free to start emitting other frames before it gets there, and none of those are dropped — they're collected and handed back to the caller as startup_messages.

stdio 
→ { "method": "initialize", "id": 1, "params": { "clientInfo": { "name": "bridge", "title": "Bridge", "version": "0.9.4" }, "capabilities": { "experimentalApi": false, "requestAttestation": false } } }
← id 1 result: handshake acknowledged
→ { "method": "initialized" }
→ { "method": "thread/start", "id": 2, "params": { "cwd": "/repo", "approvalPolicy": "on-request", "sandbox": "workspace-write", "ephemeral": false, "serviceName": "Bridge" } }
← { "id": 2, "result": { "thread": { "id": "thread_7f2a91" } } }

The thread's identity is not Bridge's to choose. It comes back from Codex in that response, read out with a JSON pointer at /result/thread/id; if that path isn't there, starting the session fails outright rather than continuing with something Bridge can never resume later. That's the inverse of Claude, whose session_id is a UUID Bridge generates before the process is even spawned and simply hands to the sidecar as configuration. Codex's provider issues the identity; Claude's adapter does.

Resuming isn't just "start again with an id." thread_resume_params sends threadId, cwd, approvalPolicy, and sandbox unconditionally, plus model and developerInstructions when given — and nothing else. It never sends ephemeral or serviceName, which describe how to create a thread rather than how to reattach to one, and — more consequentially — it never sends an effort value at all: ResumeRequest carries one, but the function that builds resume params was never written to accept it as a parameter. A reasoning-effort override only takes effect on a fresh thread/start; resuming a Codex thread leaves whatever effort it already had running. Claude doesn't have this gap — the extended-thinking budget derived from effort is set in the same launch() path that both start and resume share.

Turns, interruption, and approval

A turn is {"threadId", "input":[{"type":"text","text":…,"text_elements":[]}]}. When a caller uses send_turn_with_context instead of the plain send_turn, an additionalContext.bridge.credentials object rides alongside it — trusted, application-owned context, such as a broker-scoped credential, that stays out of the human-visible turn text entirely. That's a real capability, not a cosmetic one: the trait's default implementation of send_turn_with_context just calls send_turn, folding everything into one visible message, and Claude's runtime never overrides it. Codex's does.

stdio 
→ { "method": "turn/start", "id": 10, "params": { "threadId": "thread_7f2a91", "input": [ { "type": "text", "text": "run the test suite", "text_elements": [] } ], "additionalContext": { "bridge.credentials": { "kind": "application", "value": "broker-scoped-token" } } } }
← turn/started, item/agentMessage/delta or item/completed, turn/completed — streamed back asynchronously, not paired to this id
→ { "method": "turn/interrupt", "id": 11, "params": { "threadId": "thread_7f2a91", "turnId": "turn_c11e" } }

turn/interrupt needs a turn id, read out of current_turn, and if that's still None — no turn ever recorded — interrupt() returns a typed error, "No active turn to stop", instead of doing nothing quietly.

codex_adapter.rs never writes to current_turn itself — the field starts at None and interrupt() only ever reads it. Something on the event-normalization path fills it in once Codex's own turn/started notification confirms a turn has actually begun, which means interrupting immediately after sending a turn — before that confirmation lands — fails with the same "No active turn to stop" error as interrupting an idle session.

Approval runs the same exchange in reverse: Codex sends a request of its own — a frame carrying both method and id — and Bridge answers by echoing that id back with a result. respond() writes exactly {"id", "result":{"decision"}}. Nothing about the transport marks an approval ask as different from a turn event except that shape; the registry's own normalize checks for both fields being present before routing a frame to normalize_codex_request instead of normalize_codex_message. read_usage() follows the same fire-and-forget pattern as a turn: it sends account/rateLimits/read with null params — the protocol requires that field to be null — and lets the answer arrive later on the shared read loop rather than blocking for it. Only the two startup calls are ever awaited synchronously; everything after id 2 is numbered upward from 10 and never paired to a response inline.

Codex never overrides supports_active_turn_steering, so it keeps the trait's default of false: a second message sent while a turn is running queues behind it rather than joining it. Claude overrides it to true, for exactly the reason above — one streaming query can absorb a message the way a queue can't. The asymmetry doesn't run only one way, though: Codex's descriptor declares plans, file_changes, and history as capabilities that Claude's descriptor doesn't, while steering is the one tag unique to Claude's.

Two sandboxes, enforced separately

Codex's own approval and sandbox behavior is set once, at thread start, from Bridge's write mode — and the mapping collapses more cases than it distinguishes.

Write modeapprovalPolicysandbox
none (the orchestrator's own session)neverdanger-full-access
ReadOnlyon-requestworkspace-write
Sharedon-requestworkspace-write
Isolatedon-requestworkspace-write
Fullneverdanger-full-access

No write mode at all and WriteMode::Full land on the same pair: Codex is told not to gate itself. ReadOnly, Shared, and Isolated all land on the other pair, and Codex can't tell those three apart from this setting alone — the difference between a worker sharing the task worktree and one with its own isolated copy isn't something Codex is ever told about. It's enforced by which worktree Bridge actually points cwd at, and by how Bridge answers the approval requests that on-request generates.

That's one sandbox. A second, independent one exists only when a session runs inside Bridge's own OS-level read-only worker sandbox (read_only_sandbox: Some(...)), a mechanism worker_sandbox::command sets up around the process regardless of which provider is inside it. When that sandbox is active, every turn/start additionally carries a per-turn sandboxPolicy:

json 
{
  "type": "workspaceWrite",
  "writableRoots": ["/private/tmp/bridge-worker-9c2f"],
  "networkAccess": false
}

This pins Codex's idea of a writable root to exactly the one output directory Bridge carved out for the run, on top of — not instead of — the isolated HOME/TMPDIR the OS-level sandbox already set. A sandboxed Codex worker is constrained twice, by two mechanisms that don't know about each other.

Bridge's own sandbox

Wraps the process itself: isolated HOME and TMPDIR, one designated output directory, network allowed or not. Set up by worker_sandbox::command the same way for every provider.

Codex's own sandbox

The approvalPolicy/sandbox pair from the write mode, narrowed further — only inside a read-only sandbox — by a per-turn sandboxPolicy naming that same one output directory.

Reaching that sandboxed worker still has to authenticate. prepare_isolated_codex_home builds an isolated .codex directory under the sandbox's output directory and symlinks in auth.json and config.toml from the real ~/.codex, when they exist and aren't already linked, then points HOME/TMPDIR there. It's Unix-only — on any other platform the function fails outright rather than launching an unauthenticated worker. Claude's equivalent, prepare_isolated_claude_config, does the same symlink trick for one file, .credentials.json, and goes one step further on macOS: reading an OAuth token straight out of the Keychain when the environment doesn't already carry one. Codex's adapter has no analogous Keychain lookup.

Both adapters are eligible for this sandbox at all: Codex and Claude each advertise Bridge's full SandboxMode::ALL range, ReadOnly included. OpenCode is the sole exception, and the registry has a test pinning exactly why — OpenCode drives a local HTTP server, and that sandbox is offline, so a read-only OpenCode worker can never start. Day to day, a Codex-backed verification worker can still write files; just only inside its own scratch directory, invisible from the outside twice over.

Briefing runs are refused, not ignored

A "briefing" run is Bridge's deny-by-construction mode for letting a model read from connected tools without a human watching each step: nothing is reachable except one exact, already-reviewed tool identity, and the built-in tool families a coding agent would normally reach for are refused by name as well.

Codex's launch() checks for a briefing policy before it does anything else — before even resolving the binary.

Codex refuses a briefing run outright. The reasoning is in the code itself: Codex "cannot express one connector tool's exact identity," so treating a briefing policy as real here would only be decoration. The refusal carries the reason; it is never accepted and silently ignored.

Claude, by contrast, actively supports it. After confirming the adapter is allowed to brief at all and that the write mode is ReadOnly — a briefing run may never also hold a writable tree — it compiles the policy into allowedTools, allowedServers, readScopeServers, deniedBuiltins, and maxArgumentBytes, and hands all of it to the sidecar as configuration. Codex isn't a degraded option for this kind of run; it isn't an option at all.

Which binary actually runs

resolve_runtime() prefers a Bridge-managed payload and falls back to whatever codex is already on PATH. The doc comment states the intent plainly: a user-managed codex "keeps working exactly as before when no managed payload is installed, and is never claimed or removed by Bridge." binary_version() doesn't cache or assume a version string — it runs whichever copy would actually launch and asks that copy for its own version, so a managed payload is never described by whatever else happens to sit on PATH. The descriptor's available flag is literally version.is_some(): there's no separate existence probe, only this one.

Whether a Codex session can be resumed at all isn't assumed from the binary being present — it's discovered from the binary's own protocol schema, once, and cached. discover_native_resume shells out to codex app-server generate-json-schema --experimental --out <dir> and checks the emitted ClientRequest.json for both "thread/resume" and "ThreadResumeParams". Compare that to Claude's and OpenCode's own resume checks: Claude's is just whether node resolves and the sidecar file exists; OpenCode's is just whether its server-discovery catalog has finished loading. Codex is the only one of the three that actually interrogates the installed binary's protocol surface before trusting it — and the registry checks that result before ever calling into the adapter, refusing a resume with an explicit "does not support native resume" otherwise.

The schema probe runs once per process lifetime — its result is cached in a OnceLock, not re-checked on every session start. Upgrading the installed Codex binary to a version that adds thread/resume support needs a Bridge restart before that capability is picked up.

The descriptor also advertises four models across three tiers: gpt-5.6-luna (fast, and the overall default), gpt-5.6-terra (standard), gpt-5.6-sol (strong), and gpt-5.3-codex (a non-default standard-tier option).

When the process dies

Codex's stderr is captured on a dedicated thread into a rolling tail — the last 30 non-empty lines, each truncated to 500 bytes — the same StderrTail machinery Claude's adapter uses. failure_context() pairs that tail with the exit status, when there is one, into a single string; if the process is still running and has said nothing on stderr, it returns nothing rather than reporting a failure that hasn't happened. When a worker's typed result never arrives, this is what gets attached to the synthetic failure a supervisor reports — Codex's own last words, not a bare "process exited."

Shutdown goes through the same path whether it's asked for or not: stop() and Drop both call terminate(), which signals the whole process group with TERM, polls for exit, escalates to KILL if it doesn't, then falls back to a direct child.kill()/wait(). Because it also runs from Drop, a CodexRuntime that's simply dropped without an explicit stop() still tears its subprocess down instead of leaking it.

Codex against Claude, mechanism by mechanism

None of this makes one integration more correct than the other — it follows from what each provider ships. Codex's app-server mode is a stateful protocol server Bridge only has to translate; Claude Code's own CLI doesn't expose that same surface, so Bridge builds the equivalent statefulness itself, in a sidecar it owns, on top of the Agent SDK the vendor does ship for exactly this purpose.
