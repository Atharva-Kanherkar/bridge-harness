work, memory & learning

Memory & adaptive learning

Bridge separates three distinct systems: durable account memory that can be saved or safely extracted from chats, a learning router that ranks eligible coding agents from workspace history, and full-text search within individual chat sessions.

Account memory ledger

Your durable account memory lives in a memory_records table under the named scope account:local. Unlike routing decisions or session history, these records persist across chats and stay visible in the Memory screen, where you can review, edit, or forget them.

What gets stored

Each record has a kind (preference, fact, decision, or constraint), a body, provenance, lifecycle status, validity interval, timestamps, and optional source-session, confidence, rationale, expiry, conflict, and revision metadata. Explicit saves use user_explicit provenance; extracted candidates use model_proposal. Deleted, rejected, expired, and superseded rows remain as history, while only active records can be recalled.

How memory gets in and out

Save a pin via the Bridge command /pin <text> or the protocol method memory/save_memory_record. List active memory with /pins, and forget a record with /unpin <id>. Forgetting creates a tombstone rather than erasing the row, so the same extracted body cannot silently return.

The Memory screen also controls post-turn extraction. Manual only stops future extraction; existing active memory remains active, and new memory is saved only when you ask. Review first, the default, places each validated extraction that fits the scope budget in the review queue. Automatic promotes only candidates with at least 90% confidence that cite and match an explicit, durable cue in the same unquoted clause of a visible user message, contain no temporary, retracted, or credential-shaped data, do not match forgotten memory, and do not appear to conflict with active, pending, or same-batch memory. Bridge requires Automatic both when the run is queued and when it is applied, so changing the setting cannot escalate existing review work. Other validated candidates that fit the budget stay in the queue for review; invalid, unsafe, duplicate, and over-budget output is refused.

Every automatic candidate is written as a proposal first and uses the same lifecycle transition as manual approval. A mode change during a run can downgrade automatic promotion to review, but cannot escalate a review-only run. Scope budgets refuse overflow rather than evicting older memory.

When Use active memory in new chats is enabled, active account memory can be selected for future sessions through a bounded, cited packet. Proposed, rejected, deleted, superseded, and expired records are never injected. Turn the setting off to disable that future-chat context without deleting the ledger.

/pin, /pins, and /unpin are Bridge-handled commands and never auto-switch harness. They are not your provider's /memory — account memory is entirely Bridge-local.

Why three systems exist

Account memory solves a different problem than the routing learning system: it retains durable preferences, facts, decisions, and constraints across sessions. Its extractor evaluates the user's statements in one visible chat; it does not learn from routing outcomes or silently merge router evidence into memory. The deterministic gate, ledger lifecycle, and user-selected mode remain authoritative.

Adaptive learning router

Bridge can rank which coding agents (from the set of available providers, models, and effort levels) tend to perform better on tasks in your workspace, based on real outcomes from previous runs. The learning router is workspace-scoped: each of your workspaces learns independently, and direct chats with Claude are opted out of learning. The deterministic policy engine still owns all safety gates — learning can only rank candidates that are already authorized.

What learning sees and doesn't see

The router stores versioned role profiles, eligible/excluded agent snapshots, task fingerprints, repository revision, and outcome records (success/unknown, acceptance, retry/intervention, latency, provider cost, token count, confidence). It does not see or learn from memory jobs, direct chats, or your account memory pins. Existing rows from before the routing split are tagged `legacy:global` and are never selected; live routing always scopes to `workspace:{id}`.

Missing quota or context information is treated as unknown (eligible), not as exhausted. Only a live session in the same workspace can mark an agent QuotaExhausted or ContextExhausted; an old row at 100% usage does not block a fresh routing decision.

Modes: Manual, Ask, Automatic

After a learning run evaluates candidates against your workspace's last 5,000 held-out outcomes, it produces a recommendation. How that recommendation gets used is up to you:

  • Manual — A recommendation is recorded and you can review it, but it never automatically takes effect.
  • Ask — Bridge shows you the recommendation and asks for approval before promoting it to the live policy.
  • Automatic — Bridge promotes the recommendation to a canary policy automatically. If it causes worse outcomes (regression), a rollback is created and activated.

Running learning

Use the Learning router UI in your workspace settings for an immediate local run. Bridge can also be scheduled (in-app or via external trigger) to run learning periodically. If an external scheduler wakes the runner, it receives no evidence database and cannot write the active policy — it's strictly about periodicity. When multiple runs are queued, they iterate one workspace at a time and never mix evidence.

Each run acquires a durable lease, freezes an evidence high-water mark, runs deterministic evaluations, and aggregates by task fingerprint, profile, provider, model, and effort level. Bounded model evaluations are currently deferred work (no executor yet), so learning reports show zero spend and zero tokens from evaluation.

The policy engine decides who is allowed to run and where. The learning router ranks only those already-allowed candidates. One system handles safety and scope; the other handles quality and speed.

Session recall via full-text search

Within a single chat session, you can search your session's entire forest history using full-text search over an FTS5 index. This is per-chat, zero-LLM, and completely separate from account memory or routing learning — it's purely a search tool to find what was said in this specific conversation.

How it works

The session forest stores every entry (messages, decisions, tool invocations, forks) in an append-only structure keyed by session ID. An FTS5 index sits over that forest. When you search, the index runs a deterministic text query against that one session's history — no embedding lookup, no external call, no LLM inference. A zero-LLM search means it's instant and consistent: the same query always finds the same matches.

Why separate from learning and account memory

Session recall solves search within one conversation. Account memory is about saving personal facts for later. Learning is about ranking agents across workspace history. Blending them would make each worse: a session search might pull in stale account memory; learning would get cluttered with session-specific details; account memory would grow enormous if it had to store every session's searchable content.

Session recall is not the helper picker, not Bridge's memory engine, and not a workspace-wide index. It's a search tool for one chat at a time.

How these three systems interact

Each system has its own scope and purpose, and they remain independent:

  • Active account memory can reach future chats through a bounded, cited packet when Use active memory in new chats is enabled. It is never fed into the learning router.
  • Learning router decisions are never retroactively changed by your account memory. A new pin doesn't rewrite past routing decisions.
  • Session recall searches only the current chat's forest. It doesn't pull from other sessions' histories or your account memory.
  • The policy engine sits above all three. It decides whether learning can run at all, which providers are available, what scopes you can access, and which candidates qualify to be ranked.

If you want a fact to influence future learning runs, use Bridge's workspace guidance or include it in project documentation. Account memory can guide future chats, but it does not steer the router.
