agents & runtimes

OpenCode

Codex and Claude are subprocesses Bridge drives over their own stdin and stdout — OpenCode is the one adapter that spawns a local HTTP server instead and dials into it, and that single choice explains most of what makes this integration different.

All three coding-agent adapters implement the same AdapterRuntime trait — send_turn, interrupt, respond, an event stream Bridge normalizes into its own message shape. What differs underneath that trait is the physical channel, and for OpenCode it's the odd one out among the three.

Loopback HTTP, not a pipe

Bridge dials into opencode serve over 127.0.0.1 instead of driving the child's own stdin and stdout.

No read-only sandbox

The only one of Bridge's three adapter descriptors that excludes the offline, read-only worker sandbox.

Coarse permission families

Rules cover edit, bash, and external-directory access as whole families — never one named tool.

A live catalog, not a roster

Models are discovered from whatever providers are connected, then sorted into tiers on the fly.

A local server, not a pipe

launch() resolves an opencode executable, checks its version, reserves a free TCP port, and spawns opencode serve --hostname 127.0.0.1 --port <port> with OPENCODE_SERVER_USERNAME and OPENCODE_SERVER_PASSWORD set to bridge and a UUID generated fresh for that one process. Every request afterward carries an HTTP Basic-auth header built from those two values. Codex's adapter runs codex app-server --listen stdio:// and keeps the child's own piped stdin and stdout; Claude's adapter launches a Node sidecar over piped stdio, driving the Claude Agent SDK. Both of those channels are file descriptors only Bridge and that one child hold. OpenCode's is a TCP socket on loopback — reachable, in principle, by anything else on the machine that finds the port.

Which opencode binary actually runs follows one fixed order — an explicit path from Settings always wins, a Bridge-managed copy outranks anything already on PATH:

configured path Bridge-managed system PATH

That loopback socket costs two checks neither other adapter needs. reserve_port() binds port 0 to get a free number from the OS, then releases it before opencode serve binds that same port — a real gap, named directly in the source: another local process can win the race and answer in the child's place before it's even spawned. So once the health endpoint responds, a second check fires an unauthenticated request at it from a separate probe client and requires a 401 back — proof that whatever just answered is this launch's own server, which demands the password just generated for it, and not an unrelated process that happened to grab the port first. A pipe never needs this: the two ends of a pipe are guaranteed to be the two processes holding the descriptors.

OpenCode below version 1.18.3 is refused before any process starts. Version parsing is lenient about missing components (a bare "1.19" reads as 1.19.0), but the floor itself isn't negotiable — a test names the reason one exists at all as an incompatible context schema below that version. discover enforces the identical floor before it will list a single provider.

The same command also runs a second, throwaway way. discover, saving a provider's API key, and removing one each spin up their own opencode serve purely to answer one or two HTTP calls, then never become a session. A dedicated wrapper kills that child in its own Drop implementation the moment the call returns, so — in the source's own words — the child dies and its launch record clears on every exit from the scope, unwinding included, instead of only on the straight-line return path.

One effect of all this is visible from the outside: before Bridge treats an OpenCode session as ready, it polls that health endpoint roughly ten times a second for up to eight seconds. Codex and Claude have no equivalent wait — their process is usable the moment the OS hands back a live child.

Streaming turns over SSE

Sending a turn posts to /session/{id}/prompt_async with the message text, the resolved model if one was set, and an optional variant — Bridge's effort hint. The system prompt is Bridge's own instructions and any trusted per-turn application context, joined with a blank line and attached only if at least one side is non-empty. What comes back streams over a completely separate connection: a dedicated thread holds a long-lived GET to /event, reads it line by line, and parses each data:-prefixed payload as JSON. Nothing on that connection guarantees the events belong to this one session, so every frame is checked against properties.sessionID and dropped if it doesn't match.

Most surviving frames go through a durable send that back-pressures the socket when Bridge's own consumer stalls, instead of buffering without bound. One event kind is the exception: message.part.delta, an incremental streaming chunk, is sent as transient and may be dropped under load — safely, because its own eventual message.part.updated carries the complete text regardless. event_queue_metrics() exposes that bounded queue's pressure for diagnostics.

If the event stream ends while Bridge isn't the one shutting things down, the turn doesn't just quietly look finished. The adapter synthesizes its own session.error frame — "OpenCode event stream disconnected unexpectedly" — and pushes it durably, so a network hiccup surfaces as a visible error in the transcript rather than a turn that silently stops updating.

Every blocking HTTP call this adapter makes, and every drop of its reqwest client, runs on its own dedicated OS thread rather than inline on the calling Tauri command. reqwest's blocking client owns an internal Tokio runtime that panics if its last handle is dropped from an async context — a real constraint this file works around explicitly, not an accident of style.

Write modes become permission families

Bridge's WriteMode — the same ReadOnly / Shared / Isolated / Full vocabulary used across every adapter — gets translated into OpenCode's own shape once, at session creation: a JSON array of {permission, pattern, action} rules. Every session starts from one wildcard rule that allows everything, then the write mode layers overrides on exactly three named families.

The literal rule list an Isolated session sends:

json 
[
  { "permission": "*", "pattern": "*", "action": "allow" },
  { "permission": "edit", "pattern": "*", "action": "ask" },
  { "permission": "bash", "pattern": "*", "action": "ask" },
  { "permission": "external_directory", "pattern": "*", "action": "ask" }
]

Answering an approval maps Bridge's four abstract decisions onto OpenCode's own three-word reply vocabulary — accept becomes once, acceptForSession becomes always, decline and cancel both become reject — posted to /permission/{id}/reply. Separately, OpenCode is the only one of Bridge's three adapters that overrides answer_question and reject_question; Codex and Claude both fall through to the trait's default, which errs immediately rather than silently doing nothing, because neither raises question-shaped requests at all. OpenCode's questions are a distinct channel from permission prompts — answers post as an array of chosen values per question to /question/{id}/reply, a rejection to /question/{id}/reject — for whatever OpenCode's own protocol asks mid-turn that isn't a yes-or-no over one tool call.

Every id interpolated into one of these URLs — session, permission, question — is checked first against a strict allowlist (alphanumeric plus -, _, ., 128 characters max) so nothing shaped like a path segment or a query string can ride along into the request.

Where OpenCode refuses to run

OpenCode's AdapterDescriptor declares only two of Bridge's three sandbox modes — WorkspaceWrite and DangerFullAccess — leaving out ReadOnly entirely. Codex and Claude both declare all three. The reason is named directly in the registration comment: OpenCode drives a loopback HTTP server, and Bridge's read-only worker sandbox is offline, with no network at all, so a read-only OpenCode worker could never reach its own server in the first place. Declaring the gap at the descriptor level lets the router exclude that combination before a worker session is ever attempted, rather than after a launch that was doomed from the start. launch() checks again anyway: asked to start under the read-only sandbox, it refuses up front, refusing to start without isolation rather than attempting it and leaving the failure to whatever happens when an HTTP client can't reach a server it just spawned.

The same root cause shows up again for a different feature. A start request carrying a briefing — Bridge's read-only, connector-scoped session kind — is refused outright, citing Bridge's briefing policy table for OpenCode. That table gives the reason in one line: OpenCode's permission rules are coarse families — edit, bash, external_directory — not individual named tools, so one reviewed connector tool cannot be admitted without admitting its neighbours. A briefing session needs a real allowlist: read this one connector, nothing else. OpenCode's permission surface has no rule finer than an entire family, so rather than approximate that with whichever coarse rule is closest — locking out every connector, or opening all of them — the adapter refuses at the boundary, with the reason attached, before anything runs.

A live catalog, not a fixed roster

Codex and Claude's descriptors each carry a short, hand-maintained tuple list — id, label, tier, whether it's the tier's default — written directly into the adapter registry. OpenCode carries none: its model list comes from whatever discover() just fetched from the running server's /provider and /provider/auth endpoints. The adapter is a router over however many providers a person has actually connected, so Bridge can't hand-maintain that list — it doesn't know what's in it until it asks.

parse_catalog normalizes OpenCode's raw provider JSON into a sorted, connected-first catalog. One entry, abbreviated:

json 
{
  "id": "anthropic",
  "connected": true,
  "defaultModel": "anthropic/claude-sonnet-4",
  "models": [
    { "id": "anthropic/claude-sonnet-4", "reasoning": true, "contextWindow": 200000 }
  ]
}

None of that raw data carries a "how strong is this model" signal, and Bridge's picker only knows Fast, Standard, and Strong. A keyword-and-cost heuristic scores each model — names containing nano, mini, or flash score down, pro, max, opus, or reasoning score up, and a model's own output cost adds a little more — then splits the sorted result into thirds, preferring whichever model each connected provider already reports as its own default for that tier's pick. It's a heuristic standing in for a lookup table that an open-ended catalog can't have, but a deterministic one: a test asserts that re-running it against the same catalog always assigns the same tiers, so a model doesn't visibly jump tiers between one app launch and the next.

What a person actually sees in Settings follows directly from this: with no configuration, every model from every connected provider shows up, sorted into tiers automatically. Naming a subset in visibleModels narrows that list to just those — the setting that matters once "however many providers you've connected" stops being a short list.
