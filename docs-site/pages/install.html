getting started

Install & first run

Bridge starts with one command, but staying up reliably depends on understanding what actually owns your data directory afterward, and the two macOS quirks that otherwise make a working install look broken.

Prerequisites

Bridge is packaged for macOS only today. The machine that runs it needs:

RequirementVersionWhy
macOS12 or laterBridge ships only as a macOS .app bundle today
Bun—Installs dependencies for the root app and the sidecar workspace, and runs every bun run script
Node.js18 or newerRuns the Claude Code sidecar process — the Agent SDK runs in a Node process, not claude -p
Rust toolchainstable, with CargoBuilds bridge-core, bridged, bridge-client, bridge-protocol, and the Tauri shell
Gitwith worktree supportBridge isolates every task in its own worktree
Provider CLIsoptional: codex, claude, opencodeMissing binaries just show that adapter as unavailable

Provider CLIs are optional at the binary level: Bridge resolves them from PATH and common local install locations, and the app still starts when one is missing. The Claude Code sidecar is stricter about one thing — it needs Node.js resolvable on PATH to run at all — while the sidecar script itself is located via BRIDGE_CLAUDE_SIDECAR first, then a copy next to the Bridge executable, then the in-repo path.

Two ways to run it

Clone the repository and install once. This pulls dependencies for both the root app and the sidecar/claude-agent workspace:

bash 
git clone https://github.com/Atharva-Kanherkar/bridge-harness.git
cd bridge-harness
bun install

From there, bun run starts one of two genuinely different things:

bun run dev

Vite only, served at http://127.0.0.1:1420. Outside Tauri, src/api.ts serves local mock data instead of a real backend — this is what most component tests and pure frontend iteration exercise.

bun run tauri dev

The full desktop app: Rust shell, SQLite stores, real provider adapters, Git worktrees, and the PTY terminal. The only mode that actually supervises a Codex, Claude Code, or OpenCode session.

Only the second one exercises anything the rest of this page covers — the daemon, the ownership lease, and the macOS checks all live on the Rust side that bun run dev never starts.

If a provider shows unavailable

Bridge starts even when a provider binary is missing; that adapter just reports unavailable until its binary and credentials exist. Confirm the same environment that launches the app can actually see them:

bash 
command -v codex
command -v claude
command -v opencode
node --version
rustc --version

Before you open a PR

bun run build and bun run test must both be green. For faster iteration, narrow either suite instead of re-running everything:

bash 
bun run check              # tsc -b + cargo check --workspace
bun run test               # sidecar node:test + vitest run + cargo test --workspace
bun run build              # tsc -b && vite build

bunx vitest run src/components/WorkView.test.tsx
cargo test --manifest-path src-tauri/Cargo.toml -p bridge-core policy::

The daemon-client model

By default the desktop app hosts no runtime of its own — it is a client of bridged, the daemon that owns a data directory's sessions, SQLite stores, PTYs, and provider processes. On startup the app attaches to a bridged already serving its data directory, or starts the bundled binary and waits for it to come up (stdout and stderr land in <data_dir>/bridged.log). From then on, every Tauri invoke is proxied to the daemon as the JSON-RPC method it maps to, and every daemon notification is re-emitted to the webview under an unchanged name and payload — the frontend cannot tell which host it is talking to, and src/api.ts's call()/subscribe() look identical either way.

Tauri shell bridge-client bridged bridge-core

BRIDGE_DESKTOP_HOST picks which of three hosts wins that attach-or-start attempt:

auto (default)

Attach to a running bridged; if none answers, start the bundled binary and wait up to 30 seconds; if that also fails, fall back to running the runtime in-process.

daemon

The same attach-or-start attempt, but a failure is fatal instead of falling back — the protocol documentation calls this the “acceptance configuration”: proof the daemon path actually works, not a quiet slide into the old runtime.

embedded

Skips bridged entirely and runs bridge-core in-process, exactly as the app did before the daemon existed. Kept only for the migration; the lease means it is never concurrent with a daemon on the same data directory.

Auto's fallback exists for what its own source calls “the migration promise”: a machine where the daemon cannot run should still get a working app, just on the older path.

Exactly one owner per data directory

Whichever host wins, it first acquires an exclusive OS file lease on <data_dir>/owner.lock (bridge_core::ownership) before the runtime boots. The lease is advisory and tied to the process holding it — nothing releases it explicitly, so a kill -9 drops it with the process, and the next owner's boot-time recovery handles whatever the dead owner left rather than running any stale-lock cleanup. The lock file also carries the winning owner's identity as JSON — kind (daemon or embedded), pid, version, start time — so a process that loses the race is told exactly who holds the directory instead of a bare “resource busy”:

text 
a bridged daemon (pid 4821, version 0.9.0, started 2026-08-24T09:12:03Z) already owns
the Bridge data directory /Users/you/Library/Application Support/dev.bridge.deck —
stop it first, or point this process at a different --data-dir

This is a hard constraint on purpose, not a missing feature: a second simultaneous owner would race turn commits against the same SQLite stores and orphan the first owner's supervised provider processes. Ruling that out at the lease means the session forest, worktree coordination, and PTY lifecycle can all assume single-writer access instead of defending against a second writer everywhere they touch disk.

In practice, this is the error you hit if you point two bun run tauri dev instances, or a manually started bridged and a running desktop app, at the same data directory. The desktop app resolves its own data directory automatically — the OS-standard per-app location, ~/Library/Application Support/<bundle id> on macOS. BRIDGE_DATA_DIR and --data-dir matter when you are driving bridged or the bridge exec CLI client directly instead of through the app, and BRIDGE_DAEMON_BIN overrides which daemon binary the app starts when auto or daemon mode needs to start one at all.

A running bridged also exposes /healthz and /readyz over plain HTTP — 127.0.0.1:4318 by default, disabled with --health-addr none — the one plain-HTTP surface on an otherwise Unix-socket protocol, meant for external process monitors rather than the app itself.

Troubleshooting repeated macOS permission prompts

macOS gates ~/Desktop, ~/Documents, and ~/Downloads behind per-app consent (TCC). The first time Bridge, or an agent process it supervises, touches a file inside one of those folders, macOS shows a “Bridge would like to access…” prompt — and a prompt that is denied, or simply never answered, turns into silent file-access failures later with no further prompt to explain them. Two macOS-specific conditions produce exactly that symptom while nothing in Bridge itself is wrong, so health/health detects both and explains them instead of leaving you to guess.

The health response already reports adapter availability and the exact database, telemetry, and snapshot paths on disk; it now also carries a warnings array — always present, empty when nothing is wrong, so a protocol 0.6+ client is unaffected and an older daemon's response without the field still deserializes. Each entry looks like this:

json 
{
  "id": "macos-tcc-protected-path",
  "title": "Project folders sit inside macOS-protected locations",
  "detail": "These registered folders are inside ~/Desktop, ~/Documents, or ~/Downloads, which macOS gates behind per-app file-access consent…",
  "paths": ["/Users/you/Documents/bridge-harness"]
}

The full detail text — elided above — always names the repeated-prompt symptom and points at this exact section by name; that is a tested invariant of both warnings, not incidental wording. In the app, each warning renders as its own alert in the health banner: title, detail, and a monospace list of the offending paths. The banner renders nothing at all when the array is empty.

Warning idTriggers whenThe fix
macos-tcc-protected-pathA registered project or workspace path sits inside ~/Desktop, ~/Documents, or ~/DownloadsMove the repo somewhere unprotected such as ~/Code, or grant Bridge Full Disk Access in System Settings → Privacy & Security
macos-adhoc-signaturecodesign on the running binary reports an ad-hoc or missing signatureSign development builds with a stable identity, or expect to re-approve access after every rebuild

The protected-folder boundary is exact

The check is component-wise, not a string prefix. It matches the protected folder itself and any path beneath it — ~/Documents and ~/Documents/repos/bridge both count — and rejects a sibling, a folder merely prefixed with the same name (~/DesktopBackup), a folder with that name deeper in the tree (~/Code/Documents — a protected name only counts directly under home), and any relative path, since a relative path can never match an absolute home directory. Offending paths from every registered project and workspace are aggregated into a single warning, sorted and deduplicated, rather than one warning per path.

Ad-hoc signing resets on every rebuild

bun run tauri dev and bun run tauri build --debug both produce ad-hoc signed binaries by default, and an ad-hoc identity is regenerated on every build. macOS keys the access grants it hands out for Desktop, Documents, and Downloads to that identity, so a rebuild silently invalidates all of them and the prompts return — indistinguishable, from inside the app, from a fresh install. Bridge runs codesign --display --verbose against its own running executable and classifies the result: a real Authority= chain or a non-empty TeamIdentifier reads as stable; Signature=adhoc — including linker-signed builds, whose CodeDirectory flags still contain (adhoc — or no signature at all does not.

Classification is deliberately conservative: codesign output the parser cannot interpret is classified unknown and never produces a warning. A wrong “your build is broken” banner costs more trust than an occasional missed one.

Sign development builds with a stable identity — set signingIdentity in the Tauri bundle configuration, or re-sign the built app with an Apple Development certificate — to keep access grants across rebuilds. If prompts keep reappearing after that, stale per-app decisions can be cleared before relaunching:

bash 
tccutil reset SystemPolicyDocumentsFolder <bundle-id>
tccutil reset SystemPolicyDesktopFolder <bundle-id>
tccutil reset SystemPolicyDownloadsFolder <bundle-id>

Both checks are inert on any non-macOS host — warnings just stays an empty array there, never absent.
