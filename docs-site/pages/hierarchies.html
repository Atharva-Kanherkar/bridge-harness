core concepts

Three hierarchies

Bridge keeps three separate data structures—workspace, agent, and conversation—independent by design, because conflating them is the recurring bug in agent tooling.

Why this matters

In agent tooling, it is tempting to assume that these three structures are in lockstep. When you fork a conversation, you might expect a new filesystem snapshot. When you end a session, you might expect a worktree to be cleaned up. When you switch between agents, you might expect the conversation to move with you. None of these assumptions hold. Bridge deliberately keeps them separate because conflating them is the recurring design bug.

The separation buys concrete properties: a conversation can be examined or resumed later without touching the filesystem. A worker can be spawned in an isolated worktree without disrupting an ongoing conversation. A conversation can be forked and explored in a branch while the worker process continues unaffected. These independence guarantees are impossible if the three trees are entwined.

The workspace tree

The workspace tree is the Git repository on disk, from the root repository down through task and worker worktrees. Each level holds real filesystem state:

  • Repository: the original clone, usually the user's working copy.
  • Task worktree: a Git worktree for a single user task. Created when the user starts a task session, it isolates the user's work from other parallel sessions.
  • Worker worktree: an optional additional layer created by a policy-authorized worker. If a worker requests isolated execution, it gets its own worktree, with changes verified and adopted back into the task worktree only after completion, via fast-forward merge.

Worktree lifetimes are governed by the policy engine and the completion lifecycle: a worker worktree is retained until its adoption attempt (successful or deliberate discard) is terminal. A task worktree persists across multiple agent sessions and conversation branches—ending a conversation does not remove it.

The agent tree

The agent tree is the process hierarchy and delegation structure. It starts with an orchestrator (e.g., Claude Code running in the parent session) and spawns workers to handle delegated sub-tasks.

  • Orchestrator: the parent agent running the user's conversation. It makes decisions about what to delegate.
  • Workers: child agents spawned on demand. Each worker runs in its own process and session. Workers may themselves spawn further workers.

Policy gates every delegation: capability tier, write scope, owned paths, concurrency, retries, and approvals are all decided in the policy engine before a worker spawns. A worker result is a typed, validated data structure that the orchestrator receives—not a transcript, not raw prose, but a structured summary with evidence binding. Workers cannot be resumed across harness families (Codex, Claude, OpenCode are separate runtime ecosystems); cross-harness delegations are projected at boundaries rather than native.

The conversation tree

The conversation tree is the session forest: the append-only, immutable record of every message, tool call, and event in a conversation. It is stored locally in SQLite.

  • Root entries: the starting point of a conversation.
  • Entries: immutable records with a parent, an event kind, and visibility rules. Each entry belongs to one session and is never modified.
  • Active branch: the currently-selected branch. Forking the conversation switches which branch is active, but the old entries remain in the forest.

A conversation can be forked at any point. The fork does not create a new session, a new worktree, or a new worker; it simply marks a new branch in the forest as active. Later appends to that branch create a new history thread. All previous entries on both branches remain accessible. When a conversation is compacted (summarized to reduce context), the summary is added as a checkpoint, not substituted into the history—the raw entries stay intact.

How they interact (and don't)

The trees interact in a few specific, carefully gated ways:

Workspace to Agent

A worker is spawned with a binding to a specific worktree checkout. The worker's typed result records which worktree path it ran in and the exact Git HEAD at that time. If it is a write-capable worker in isolated mode, it gets a child worktree and its changes must be verified against Git before adoption. This binding is durable evidence: you can always look up a worker result and know exactly which checkout it ran in.

Agent to Conversation

When a worker completes, its result is recorded as a durable `worker.result` entry in the conversation forest. The entry ID is the evidence reference. Later workers can request that evidence by ID, and Bridge resolves the exact typed payload from SQLite, checking that the evidence belongs to the same session and active branch. Conversely, a worker receives excerpted evidence from recent ancestors—not the raw transcript, but a digest of messages and tool calls—so it knows what has been tried already.

Conversation to Workspace

At resume time or after a compaction checkpoint, the forest snapshot is compared with the current worktree state. Every entry records a deterministic hash of the porcelain dirty state at the time it was created. A mismatch surfaces as conversation/file divergence and is shown to the user—"your conversation remembers the files at state X, but the worktree is now at state Y." This is not automatic reconciliation; it is visibility. The conversation never rewrites filesystem history, and the filesystem never rewrites the conversation.

Why separation is essential

Keeping these trees separate enables several safety and usability properties:

Isolation: a worker can run in an isolated worktree without affecting the user's task worktree until the user explicitly accepts the result. A conversation fork does not change the filesystem at all.

Durability without coupling: a conversation can be paused, resumed, forked, or searched months later. The worktree may have moved, the workers may be gone, but the forest entries are immutable and self-contained.

Concurrency: multiple workers can be active at once. Each one gets its own workspace layer (via worktree or write-scope isolation) and its own process tree. The conversation can record events from all of them on the same branch.

If you conflate these trees—assume a conversation fork creates a filesystem snapshot, or that ending a worker cleans up its worktree, or that switching harnesses moves the conversation with it—you will create edge cases where users lose work, where state gets corrupted, or where cleanup is incomplete. Bridge pays the cost of keeping them separate upfront so those bugs never materialize.

For AI agents working on Bridge

When modifying the codebase, remember that these trees are deliberately independent. A change that assumes they are coupled will almost certainly introduce a subtle bug. Some specific red flags:

  • A worker spawn that assumes the task worktree is already at a specific state without binding it.
  • A conversation fork or branch switch that tries to revert or reset the filesystem.
  • A session end that deletes a worktree without checking policy rules and adoption status.
  • Reading a worker result without verifying it belongs to the active session and branch.

The policy engine in `bridge_core` and the session forest in `session_forest.rs` are the two places that formalize this separation. Learn those modules first.
