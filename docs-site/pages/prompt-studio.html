Prompt Studio & Context Lens

Edit Bridge's prompt sections per target, inspect exact compiled bytes, and measure what each section costs via leave-one-out accounting.

What is Prompt Studio

Prompt Studio is the settings interface for tuning Bridge's internal prompts. It lives in the Desktop app's Settings pane and lets you edit, save, reset, and audit the revision history of every prompt section Bridge uses when speaking to agents — Orchestrator directives, delegation protocols, and worker contracts.

Each section has a default built-in text. When you override that text, it replaces the default for the current session and all future sessions until you reset it back. Every edit appends to an append-only revision history, so you can restore any prior version at any time. The compiled preview shows you exactly what bytes Bridge will send to an agent for those overrides, split between Bridge-authored material and provider-owned layers.

Targets and sections

Prompt Studio organizes sections by target — the agent role you are customizing:

  • Orchestrator — the top-level agent that coordinates tasks and routes work to workers. Includes bridge_role (role description) and delegation_protocol (how to invoke workers).
  • Worker roles — Research, Implementation, Verification, Planning, Documentation. Each has a worker_contract describing its responsibilities and constraints.
  • Direct session — shows read-only context (the rendering note explaining how Claude interprets the Bridge context format).

A worker contract adjusts based on worker depth — how many layers of delegation remain available. The contract at depth 0 is different from depth 3; Bridge embeds the remaining depth budget into the language itself so each worker knows its scope.

When you navigate to a target, the sidebar lists its sections. Each row shows the section ID, a live byte-and-token estimate, and a badge when the section has been edited.

Section states and editing

Every section exists in exactly one of three states:

  • Default — using the built-in text. No badge. Revision history is empty or contains only prior edits that were reset.
  • Overridden — you edited the text and saved it. Badge appears. This state is persisted in Bridge's configuration store.
  • Deleted — you deleted the section entirely. It contributes no bytes to the compiled prompt. A distinct visual treatment marks this state.

To edit, select a section and use the code editor (CodeMirror 6 with markdown syntax highlighting). The editor preserves your unsaved draft if you navigate away and return; unsaved changes do not auto-save and do not silently discard.

While editing, lint warnings appear inline if your text would drop a required marker — for example, a delegation_protocol override must include the `bridge-delegate` marker, or agents cannot invoke workers. Warnings warn and explain but do not block save; you can save a deliberately minimal version if needed.

Revision history and restore

Every time you save, delete, or reset a section, Bridge appends a revision entry capturing the operation, new state, timestamp, and exact text (if the state is Overridden). The revision history is append-only and bounded to the most recent 50 revisions in the Studio view; older revisions remain addressable by ID and can be restored.

The history panel shows each revision chronologically with a restore action. Restoring a prior revision creates a new entry (marked with the restore operation) that makes the section adopt that prior text again. History never branches and never rewrites — every edit is a new entry.

Resetting a section to its default does not erase the override from history — it appends a Reset operation. Later restores can bring the override back.

Compiled preview

The preview panel compiles your overrides into the exact bytes Bridge will use in the next turn. The panel splits into two regions:

  • Exact Bridge bytes — the stable prefix wrapped in <bridge-stable-prompt> tags, built only from the resolved sections (overrides applied, deletions omitted). Labeled exact, with byte count and token estimate (bytes ÷ 4, rounded up). Also shows a hash and prefix ID for cache identity tracking.
  • Provider layers — downstream material contributed by the provider adapter (base prompt, tools, runtime context). Each row is labeled by its source: reported (the provider told us the bytes), measured (Bridge observed them), estimated (a labelled approximation), or unavailable (nothing defensible). Until an adapter capture exists, all provider-base rows are unavailable with a reason.

The preview also shows a cache-impact indicator: if the stable prefix hash changed since the last preview load, it signals that provider caches may rebuild on the next turn. Any provider cache effect is labeled estimated unless telemetry proves it measured.

Context Lens: exact prompt accounting

Context Lens measures the exact byte cost of every element in Bridge's compiled prompt, enabling you to see which sections drive the most overhead and make targeted edits. Unlike raw token counts, Context Lens attributes every single byte — punctuation, keys, separators — to the specific element that caused it.

The accounting data is stored alongside each compiled prompt in Bridge's database (the prompt_compilations table) and surfaces both per-section byte counts and per-region summaries. This is observability metadata only; it does not change what Bridge sends to agents.

Leave-one-out delta serialization

Context Lens uses a precise attribution method called leave-one-out delta serialization. For each section or element in the prompt:

  1. Serialize the full envelope with all elements included.
  2. Serialize the envelope again with that one element removed.
  3. The attributed bytes = full size − removed size.

This single-pass method charges JSON escaping, key names, colons, commas, and quotes directly to the element that triggered them, without reimplementing serde_json logic. An element that contains a newline or quote character will have more attributed bytes than its raw text length, because the escaping cost is included.

Empty or deleted sections produce no accounting entries — they are already filtered out before serialization and thus do not appear in the accounting records.

example 
Full: {"sections": [{"id": "role", "text": "Be helpful."}]}
Without role: {"sections": []}
Attributed to role: 48 bytes (includes id name, comma, braces, quotes, escapes)

Attribution regions

The compiled prompt splits into three regions, each with its own accounting entries:

  • Stable region — one entry per surviving element in StableEnvelope:
    • Role (kind: role)
    • Each stable section (kind: stable_section), with section ID and serialized byte count
    • Each tool schema (kind: tool_schema)
    • Each project rule (kind: project_rule)
  • Variable region — one entry per surviving named text in VariableEnvelope (task context, session metadata, runtime memory, etc.)
  • Envelope overhead — explicit entries for bytes that belong to no content:
    • Stable envelope tags (<bridge-stable-prompt>, </bridge-stable-prompt>)
    • Variable envelope tags
    • JSON punctuation (braces, brackets, commas, colons) not charged to any element
    • The two-byte \n\n separator between regions

The sum of all entries in all regions equals the total compiled prompt length exactly: Σ(stable) + Σ(variable) + Σ(overhead) + 2 (separator) = total bytes.

Storage and telemetry

Context Lens data is persisted per compilation (per turn) in the prompt_compilations table:

  • sections_json — the full ordered list of accounting entries (camelCase serde)
  • stable_bytes — length of the stable prefix
  • variable_bytes — length of the variable suffix
  • stable_token_estimate, variable_token_estimate — bytes ÷ 4 (rounded up), with a source label
  • token_estimate_source — labels the method (e.g., bytes_div4_v1 for the current formula)

Legacy database rows created before this feature retain NULL for these columns and remain readable. The cache identity fields (prefix_hash, prefix_id, prefix_bytes) are unchanged by accounting — they remain byte-for-byte identical to before, ensuring provider cache reuse is unaffected.

Why exact accounting matters

Prompt size is a real cost lever: larger prompts mean higher API bills, slower response time, and more context burn in multi-turn conversations. Without exact attribution, you cannot tell whether a section is bloated or whether the overhead itself is the bottleneck. Context Lens reveals the true cost of each element so you can make informed edits — delete unnecessary sections, trim verbose policies, or accept a larger cost if that section genuinely drives value.

The leave-one-out method is precise enough to catch escaping overhead (a section with many quote characters costs more than its text alone suggests) and low-level enough to attribute every JSON character, making it trustworthy for cost tracking and optimization.
