core concepts

Compaction & resume

When Bridge reattaches to a session, it names exactly how much continuity survived — a live process, a native provider resume, or a checkpoint it verified independently before trusting it — and it never lets one pass for another.

Three kinds of context

Bridge tracks three things that all sound like "the conversation" and are not the same. Stored history is every entry the session forest has recorded — immutable, append-only, and independent of whether anyone is currently looking at it. Provider-native context is whatever thread or session state the underlying Codex, Claude, or OpenCode process itself is holding. Projected restoration context is what Bridge actively builds and hands back when it reattaches to a session without a live connection to reuse. Persisting an entry into stored history does not mean it has been injected into a provider thread — the three can drift apart, and a resume mode is really just a name for how far apart they were at the moment Bridge had to reconcile them.

Resume modes

Whenever Bridge needs to reattach to a session it isn't already holding a live connection to, the reattachment resolves to exactly one of four modes:

ModeMeaning
hotThe adapter process is still running.
nativeThe provider can resume its stored thread or session ID.
checkpoint_restoredNative resume is unavailable or failed, so Bridge starts fresh with a validated projection.
freshThe task intentionally starts without prior conversation context.

hot is the trivial case: if the adapter process never stopped, there's nothing to reconcile — provider-native context and Bridge's live connection are the same thing, and no resume logic runs at all. Otherwise Bridge tries native resume, and whether that's even attempted depends on what the installed harness supports: a harness without it is skipped outright, and one that has it but fails gets recorded as a failed attempt before Bridge falls back to a checkpoint. That fallback, checkpoint_restored, isn't raw history replayed verbatim — it's a projected restoration context built from a checkpoint Bridge has already independently verified (see Verifying a checkpoint, below). fresh stands apart from this whole cascade: it isn't what a session gets when the other three fail, it's what a task gets when it's deliberately started with no prior conversation to bring back.

The recording matters because a freshly-started process and a successfully native-resumed one can look identical from the outside — both are just a provider running and answering messages. Bridge never labels a fresh process as natively resumed, and a failed native attempt stays on the record even after the checkpoint fallback that follows it succeeds. The mode names what actually happened underneath, not what the surface looks like.

Who compacts, and when

Deciding when a checkpoint is needed is Rust's job, not the agent's: a compaction controller in the host process decides to trigger compaction, but the session being compacted authors the checkpoint itself. That split is deliberate — the session being compacted is the one that owns its decisions, its risks, and its incomplete work, so it's also the one positioned to describe them. The same boundary reappears one level up the tree: an orchestrator only ever receives typed worker results and checkpoints from the workers it spawns, never their raw transcripts. Whatever an orchestrator acts on has already passed through this same self-authored, then independently verified, summary step.

Compaction triggers on context pressure, at phase boundaries, before suspension or a model downgrade, before a risky native resume, or on manual request. It's suppressed while a tool call or an approval is in flight, for short-lived workers that already have a valid final result, and when nothing meaningful happened since the last boundary — compaction that would just restate the previous checkpoint doesn't run.

A checkpoint, once committed, is an immutable forest entry like any other — the raw events underneath it are never deleted or rewritten, only summarized in front of. A checkpoint that fails validation gets exactly one same-session repair attempt. If the process that would own that repair is already dead, a recovery worker produces the checkpoint instead, and that result is explicitly marked reconstructed, so nothing downstream mistakes a reconstruction for the original session's own account of itself.

Verifying a checkpoint

A checkpoint can be perfectly well-formed JSON and still be wrong — it's the compacted session's own account of itself, and schema validity alone doesn't say whether that account is complete. So before a checkpoint boundary is committed, Rust independently re-derives what it should contain: it scans the active SQLite branch back to the previous completed compaction, deduplicates the durable worker decisions and file evidence from that window, and checks that the session's checkpoint actually contains every one of them. Schema-invalid and incomplete-but-well-formed checkpoints share the same fate — one same-session repair attempt, and if the repair still doesn't hold up, the boundary fails closed instead of being committed anyway.

Structurally, a checkpoint is nothing more than the same forest entry shape as everything else, carrying two extra facts:

forest entry 
{
  "id": "evt_c771",
  "parent": "evt_a13f",
  "kind": "assistant_message",
  "visibility": "context",
  "checkpoint": true,
  "reconstructed": false
}

A checkpoint that passes gets its evidence counts committed in the same atomic write as the checkpoint itself, as a checkpoint.evidence_verified audit event — the verification result and the boundary it verifies can never fall out of sync, because they were never two separate writes to begin with. Reconstructed checkpoints — the ones a recovery worker builds when the original session is dead — carry that provenance forward explicitly rather than being folded in as if self-authored. It's also what makes checkpoint_restored trustworthy enough to resume from: the mode's own definition calls it a "validated projection," and this independent re-derivation is exactly what earns that word.

Where this actually lives

Everything this page has been describing lives, physically, in one file: bridge.db holds the correctness-critical state — session entries and heads, worker leases and queues, approvals, usage, and the outbox. Bridge is explicit about what this is and isn't: durable local history, not a tamper-proof or replicated evidence ledger.

Provider telemetry is kept separate, in its own bridge-telemetry.db. Normalized spans are batched in only after their semantic transactions commit, so a telemetry writer lock or failure can't delay, roll back, or relabel the correctness-critical state next door — observability isn't allowed to become a way to corrupt the record it's observing.

On top of both, Bridge exports a transactionally consistent SQLite snapshot at startup and every 15 minutes, under history-snapshots/. Each export carries a versioned manifest with its filename, creation time, and a SHA-256 checksum; verification recomputes that checksum, so disk corruption or an accidental edit becomes visible instead of silent. These snapshots reduce the risk of losing everything to one bad file — they are not a backup by themselves. Copying the snapshot directory to another device is still the user's own responsibility.

Don't confuse a snapshot with a checkpoint. A snapshot is a periodic, checksum-verified copy of the whole database, guarding against disk corruption. A checkpoint is a single verified forest entry summarizing one session's own history. They run on different clocks, guard against different failures, and neither substitutes for the other.
