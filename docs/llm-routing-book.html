Before you startWhat this book covers

A router is the piece of infrastructure that sits between an agent and a model and decides, per request, which model serves it and in what dialect. This book is about the two ways that piece fails: it costs you time, and it changes what you said.

Inside

The request path from client to model and back. What a hop costs in milliseconds and where those milliseconds go. Load-aware, cache-aware and quality-aware routing policies, and how each one degrades. The translation layer between OpenAI Chat Completions, Anthropic Messages and OpenAI Responses, and the catalogue of fields that silently do not survive it. Streaming through a proxy. Retries, hedging and circuit breakers. Prompt-cache economics. Credentials at a multi-tenant gateway. And the discipline of proving any of it.

Adjacent, and excluded

Front matterScope

Model training and fine-tuning. Retrieval design and prompt engineering. GPU kernel work, quantisation, and the internals of the model itself. Agent orchestration above the router. Where those touch routing — and prefill, decode and the KV cache do touch it hard — the book teaches exactly the part routing leans on, and says so.

Vocabulary collision, first page for a reason

“Router” means two unrelated things in this field. Inside a mixture-of-experts model, the router is a learned gating network that assigns tokens to expert sub-networks; it lives on the GPU and runs per token. In this book, a router is a network service that assigns requests to models; it lives on a CPU and runs per request. Interviewers ask about both, sometimes in the same hour, occasionally without disambiguating. If a question about “the router” is ambiguous, ask which one before you answer — that question is itself a signal.

Say this

“Two things make a router hard: it is on the critical path of every request, so its own latency is pure overhead; and it is a translator, so every field it fails to carry is a silent behaviour change nobody gets an error for.”

Ground truth

Three things routing leans on so heavily that Part II is unreadable without them: an LLM request is two workloads, not one; the number that matters is a tail, not a mean; and “OpenAI-compatible” describes three incompatible data models.

One · Two workloads in one requestPrefill and decode

Chapter oneTwo workloads in one request

Ask “how fast is this model?” and there is no answer, because a single completion is two different computations with two different bottlenecks, and a router can make one faster while making the other worse.

The problem

A router has to choose a backend before it knows how long the work will take. If it optimises the wrong half of the request, it will look good on a dashboard and feel bad to a user — or feel fine to a user and starve an agent. So the first thing to fix is what “fast” means.

Prefill

Prefill is the pass over the whole input prompt that populates the key-value cache and produces the first output token. Every prompt token is processed in parallel, so prefill saturates arithmetic units: it is compute-bound. Its cost scales with prompt length, and it is the phase a long system prompt or a large retrieved context lands in. Doubling the prompt roughly doubles prefill work; it does not touch generation at all.

One · Two workloads in one requestPrefill and decode

Decode

Decode emits one token at a time. Each step reads the entire KV cache and the model weights to produce a single token, so almost no arithmetic happens per byte moved: decode is memory-bandwidth-bound, and it is strictly sequential. Doubling the output length roughly doubles decode time. Nothing about a shorter prompt makes decode faster.

Those two sentences are the whole chapter. The rest is what follows from them.

Say this

“Prefill is compute-bound and parallel; decode is memory-bandwidth-bound and serial. That is why prompt length and output length show up in completely different metrics, and why one routing decision cannot optimise both.”

One · Two workloads in one requestTTFT, TPOT, end-to-end

The three metrics, and the arithmetic that binds them

Redraw this one. Five segments, one dashed line. The argument is in the geometry: the router's own cost (rtr) is the narrowest box on the page, and the segment it most influences by choosing a backend is queue, not prefill.

TTFT, time to first token, is everything left of the dashed line: network, TLS, router overhead, queueing at the chosen backend, and prefill. TPOT, time per output token, is the mean width of one decode step; the same quantity measured between consecutive tokens rather than averaged is ITL, inter-token latency, and its variance is what a user perceives as stutter. End to end is then just:

e2e  =  TTFT  +  TPOT × (output_tokens − 1)
// 400 tokens at 20 ms/token is 8.0 s of decode.
// A router that shaves 200 ms off TTFT has moved 2.4% of that request.

The consequence. For a chat UI, TTFT is the whole perceived latency and the decode tail is hidden behind reading speed. For an agent that must parse a complete tool call before it can act, TTFT is nearly irrelevant and end-to-end is everything. These two goals select different backends.

One · Two workloads in one requestGoodput

Goodput: the only throughput number worth quoting

Raw throughput — requests per second, or tokens per second — is trivially improvable by making everyone wait. Batch harder and the GPU does more total work per second while every individual request gets slower. Goodput closes that loophole: it is throughput counted only over requests that met their latency objective, typically stated as a pair, p99 TTFT < t1 and p99 TPOT < t2. A system with high throughput and low goodput is a system that is fast on average and failing its users.

Goodput is the number to reach for whenever an interviewer offers you a throughput-versus-latency trade-off, because it is the metric that refuses to let you take one side of it.

Continuous batching, in one paragraph

Modern servers do not batch by collecting n requests and running them together to completion. They run continuous (or in-flight) batching: at each decode step the scheduler assembles whatever requests are currently active, so a finished sequence leaves the batch immediately and a newly arrived one joins at the next step instead of waiting for the batch to drain. This is why a backend's queue can move faster than its slowest in-flight request, and it is the mechanism that makes queue depth a usable routing signal at all.

One · Two workloads in one requestGoodput
Trap

“Streaming makes the response faster.” It does not. Streaming changes nothing about the total compute or the end-to-end time; it changes only when the client learns about it. For a human reading prose, that is an enormous perceived win. For an agent that cannot execute a tool call until the arguments are complete and parsed, streaming buys one real thing — earlier detection that the response is going wrong — and costs you a protocol that is far easier to mistranslate, which is chapter nine.

Say this

“I'd want the SLO as a pair, and I'd measure goodput against it. Throughput on its own is a number you can always improve by making the p99 worse.”

Practice sheet oneTwo workloads in one request

  1. A team doubles its system prompt from 2,000 to 4,000 tokens. Output length is unchanged. What moves?

    c. Prompt length lands in prefill, which is the last segment of TTFT. Decode reads a slightly larger KV cache per step, so TPOT drifts up a little, but not by a factor of two — the dominant per-step cost is streaming the model weights, not the cache. b is the tempting one because “attends over more context” is true and sounds like it should dominate; it does not. d confuses “parallel” with “free”: prefill parallelises across tokens but still does the arithmetic.

  2. You add streaming to an agent that calls tools. What does the agent actually gain?

    b. The agent cannot execute a tool call until the arguments are complete and parsed, so the last token still gates the action. What it gains is the ability to abort early — on a stop sequence, a budget breach, or an obviously wrong trajectory. a is the near-universal belief and it is wrong: the same total compute happens either way. d overcorrects; early cancellation is a real saving, and in chapter nine streaming also becomes the main source of translation bugs, which is the opposite of “nothing”.

Model answer

Two · Queues and the tailWhy the mean lies

Chapter twoQueues and the tail

A router chooses a backend before it can know how long the work will take. Every routing policy in this book is, underneath, a guess about a queue — so the shape of queueing delay is the thing you have to hold in your head.

The problem

Requests do not arrive evenly and do not take equal time. A backend at 50% mean utilisation is not half busy in any useful sense: it is idle much of the time and saturated some of the time, and the requests that arrive during saturation are the ones that define your p99. A policy that balances counts therefore does not balance waiting, and the gap between those two is where tail latency comes from.

Utilisation is not linear in latency

Take the simplest queue — one server, random arrivals, random service times — and the mean time in system is W = 1 / (μ − λ), where λ is arrival rate and μ service rate. Written in terms of utilisation ρ = λ/μ, the waiting term carries a factor of 1/(1−ρ). At 50% utilisation that factor is 2. At 90% it is 10. At 99% it is 100.

Two · Queues and the tailWhy the mean lies

Real serving is not an M/M/1 queue and you should say so if you invoke this. But the shape is right and it is what makes the argument: the last 10% of capacity you buy costs far more latency than the first 10%, and a fleet run at 90% to look efficient is a fleet whose tail is already ten times its floor.

Little's Law, for saying out loud

L = λW: the mean number of requests in the system equals arrival rate times mean time in system. It holds for any stable queue regardless of distribution, which is why it is safe to use in a room. Concretely: 200 requests per second at a mean of 4 seconds in system means 800 requests concurrently in flight. That number is what sizes your connection pools, your in-flight limits, and your memory.

Say this

“Two hundred a second at four seconds mean is eight hundred concurrent — that's Little's Law, and it's the number I'd size the pool and the admission limit against before I pick a routing policy.”

Two · Queues and the tailAmplification

Why an agent loop has a worse tail than the model it calls

The amplification argument. Dean and Barroso's point, restated for agents. A service that fans out to 100 leaves, each with a 1-in-100 chance of being slow, sees a slow leaf on about 63% of requests. A ten-step agent loop is the same arithmetic in series. Your loop's tail is not your model's tail.

This is also why per-step timeouts that look generous are not. If each step is allowed the p99 before it is cut off, one loop in ten hits a cut. Budget the loop, not the step, and let early steps borrow from later ones.

Two · Queues and the tailHedging

Hedging: buying the tail back with a little extra load

If most of the variance is queueing rather than service, a request that is already slow is likely to stay slow, and a second attempt on a different backend is likely to be fast. That is the whole idea. The discipline is in the trigger.

Fire the second request immediately and you have doubled your load for nothing. Fire it after the request has been outstanding longer than the 95th percentile expected latency and, by construction, you only duplicate about 5% of requests — while catching essentially all of the tail. Dean and Barroso's measured case: reading 1,000 keys across 100 BigTable servers, a hedge issued after 10 ms cut the 99.9th percentile from 1,800 ms to 74 ms for about 2% extra requests.

The refinement they describe is tied requests: enqueue on two servers at once, but tell each about the other, so whichever dequeues first cancels its twin. That removes the hedge delay entirely at the cost of needing cross-server cancellation, and the paper reports roughly a 37% tail reduction from it.

Two · Queues and the tailHedging
Trap

“Hedging is just a retry.” It is the opposite. A retry fires after a failure, when the first attempt has already been abandoned; a hedge fires during a still-live request and races it. The consequences differ: a hedge doubles cost for the hedged fraction, needs cancellation to avoid paying twice, and — the part candidates miss — is only safe on idempotent work. Hedging a request that has already started billing tokens means paying for both, and hedging a tool call with side effects means executing it twice. On LLM traffic specifically, hedging a streaming request is worse still, because the first token may already be on the wire to the client.

Say this

“I'd hedge at the p95, not immediately — that bounds the extra load at about five percent by definition. And I'd only hedge before the first token is emitted, because after that I've already committed a stream to the client.”

Two · Queues and the tailPercentile hygiene

Three things you may not do to a percentile

You may not average them. The mean of two backends' p99s is not the p99 of the pool. Percentiles are order statistics; they do not compose arithmetically. To get a fleet p99 you need the merged distribution, which is why you store histograms and not summary numbers. An interviewer who hears you average percentiles will stop listening to the rest of the answer.

You may not compare them across different populations. A p99 measured over a mix that is 90% short requests and a p99 measured over a mix that is 50% long ones are different questions with the same name. On LLM traffic this bites constantly, because output length varies by orders of magnitude across a single endpoint. Normalise: report TTFT unconditionally, but report end-to-end per output-token bucket, or report TPOT instead.

You may not treat a p99 improvement as an improvement for anyone. p99 is a threshold on a distribution, not a user. Moving p99 from 3 s to 2 s while moving p99.9 from 8 s to 20 s is a regression for the people who were already worst off, and it is exactly what an over-aggressive admission controller does.

Two · Queues and the tailPercentile hygiene
The metric a router should actually publish

Per route (client dialect × policy × chosen backend), a histogram of TTFT and a histogram of TPOT, plus a counter of decisions by reason. If the router cannot tell you why it chose a backend for a given request id, no latency graph it produces is debuggable — you will be able to see that something is slow and never which decision made it so. NeMo Switchyard, for instance, records the selected model, the decision rationale, token usage and latency per call, and that rationale field is the one people skip and then need.

90 sec“Would you hedge LLM requests? Talk me through it.”

Model answer

Yes, narrowly, and say the conditions in this order. Hedge only before the first token, because after that a stream is committed to the client and you would have to reconcile two divergent token streams. Marked down for: not mentioning cost. Hedging is a latency technique that spends money, and on LLM traffic the money is unusually visible.

Three · Three dialects“OpenAI-compatible”

Chapter threeThree dialects called “compatible”

“OpenAI-compatible” is a claim about a URL and a bearer token. It is not a claim about a data model, and there are at least three data models in play, none of which is a superset of the others.

The problem

An agent speaks one dialect. A backend speaks another. Something in the middle has to translate, and translation between structures that do not have the same expressive power is lossy by construction. The question is never whether a gateway loses information; it is which fields it loses, whether it tells you, and whether the loss changes what the model does.

The three

OpenAI Chat Completions (/v1/chat/completions). Messages are a flat list; content is usually a plain string; the system prompt is just a message with role: "system" and may appear anywhere. A tool call is signalled by finish_reason: "tool_calls" plus message.tool_calls[], each with an id, a function.name, and function.arguments as a JSON string. A tool result comes back as a message with role: "tool" and a matching tool_call_id.

Three · Three dialects“OpenAI-compatible”

Anthropic Messages (/v1/messages). system is a top-level field, not a message, and the messages array must alternate user and assistant. content is an array of typed blocks — text, tool_use, tool_result, thinking, image, document. A tool call is stop_reason: "tool_use" plus a tool_use block whose input is an already-parsed object. A tool result is a tool_result block inside a user message, referencing tool_use_id, and carrying an is_error flag. max_tokens is required.

OpenAI Responses (/v1/responses). A third shape again: input rather than messages, instructions rather than a system message, max_output_tokens rather than max_tokens, an output array of typed items, structured output under text.format, and its own call_id that the client must echo back.

Say this

“These aren't three spellings of one API. Anthropic has typed content blocks and a required max_tokens; Chat Completions has a flat string and stringified tool arguments; Responses has a third vocabulary again. Any gateway between them is doing a real translation, and translation between structures of unequal expressive power loses things.”

Three · Three dialectsThe IR, and why it is the chokepoint

Why every gateway grows an internal representation — and why that is where the losses live

The insight is the geometry. Pairwise translation is O(dialects × backends) and nobody ships it. Everyone converges on an internal request type — NeMo Switchyard calls it the internal request format, LiteLLM has its own — which is O(dialects + backends). The cost is that the IR becomes a lowest common denominator: if it has no field for is_error, then no adapter downstream can carry is_error, and the loss appears simultaneously on every route.

That is why gateway bugs cluster in families rather than appearing one at a time, and it is the single most useful thing to say in an interview about why these systems are hard.

Chapter fourThe cost of the hop

A router sits on the critical path of every request, so its own latency is pure overhead paid by everyone. The published overhead numbers span three orders of magnitude, and most of them were measured in a way that cannot tell you what yours will be.

Adding an indirection to save cost or improve reliability is only worth it if the indirection is cheap relative to what it buys. Four · The cost of the hopOverhead against what

Overhead against what?

Set 40 ms of proxy overhead against a frontier model's ~550 ms first token and it is 7% of TTFT and well under 1% of a 400-token completion. Set the same 40 ms against a custom-silicon host answering in 180 ms and it is 22% of TTFT. Same proxy, same code, two completely different verdicts — which is why “is 40 ms a lot?” has no answer without the backend.

But TTFT is not really the right denominator either. The honest comparison is overhead against what the routing decision saved. A router that costs 40 ms and steers a request away from a backend with three seconds of queue in front of it has bought 2,960 ms. A router that costs 40 ms and picks uniformly at random has bought nothing and should not exist.

The three questions that price a hop

One: what is the overhead at your p99, at your concurrency, with your body sizes? Measure it with the gateway's own instrumentation — LiteLLM returns x‑litellm‑overhead‑duration‑ms on every response for exactly this. Two: what does the decision save, measured as the difference between the chosen backend's queue and the pool median? Three: what does the hop buy that is not latency at all — failover, a single credential boundary, spend attribution, one dialect for every client? Those are usually the real reason the router exists, and a candidate who prices only latency has priced the wrong thing.

Where a hop stops being cheap

Four · The cost of the hopOverhead against what

Three failure modes turn a 2 ms proxy into a 200 ms one, and none of them show up in a benchmark. Cold connections: without upstream keepalive you pay a TCP and TLS handshake per request, which cross-region is tens of milliseconds before any work happens. Five · Load-aware routingBalancing load, not counts

Chapter fiveLoad-aware routing

Requests pile up behind the busiest backend unless routing knows something about the queue. Round robin balances counts, and on LLM traffic counts and load are barely related.

The problem

On ordinary HTTP traffic, requests are roughly interchangeable, so an even split of requests is an even split of work and round robin is nearly optimal. LLM traffic breaks that assumption in both directions at once: a 200-token summarisation and a 20,000-token codebase analysis differ by two orders of magnitude in cost, and the router cannot know the output length at admission time because nobody knows it until the model stops. Even distribution of requests is therefore not even distribution of load, and the difference shows up entirely in the tail.

Five · Load-aware routingThe herd

Why the most intuitive policy is the one that oscillates

Redraw this when asked about latency-based routing. The loop is four boxes and a return edge, and the return edge is where the delay lives. Any policy that routes deterministically to the current best, on a lagging signal, exhibits it.

The three standard fixes, in ascending order of how much they cost you: randomise — sample from a distribution weighted by inverse latency rather than taking the argmin, so the winner absorbs more traffic without absorbing all of it; damp — use an exponentially weighted moving average with a time constant longer than the actuation delay, accepting slower reaction to real failures; use a leading signal instead of a lagging one — in-flight count changes the instant you dispatch, where observed latency changes only when a request completes.

Five · Load-aware routingP2C

Power of two choices

Pick two backends uniformly at random; send the request to whichever has fewer requests in flight. That is the entire algorithm. It never herds, because the candidate set is different for every request. It is O(1) rather than O(n), so it does not need to scan or maintain a view of the whole pool. And its imbalance grows doubly-logarithmically rather than logarithmically in pool size, which in practice means the worst-loaded backend stays close to the mean even at large n. HAProxy and NGINX both ship it.

Trap, and it is a contested one

“Power of two choices beats least-connections.” Not in a single load balancer with a complete and current view of the pool — there, scanning every backend and taking the true minimum is strictly better information, and published head-to-head tests have found least-connections around 4% better on response time, with P2C indistinguishable from round robin. P2C's advantage appears where the assumption of a complete current view fails: many independent routers, each with stale local state, where global least-connections makes all of them stampede the same backend simultaneously. Say which regime you are in before you pick. A candidate who names P2C as a universal upgrade has read the blog post; one who says “it wins when the load balancer is distributed and the state is stale” has understood it.

What makes this harder than it is for HTTP

Three things. Cost is unknown at admission. You cannot weight by work you cannot see; output length is decided by the model. Some systems predict it from the prompt and route on the prediction, which converts a scheduling problem into a machine-learning problem with its own error budget. Occupancy is long. An in-flight LLM request holds a slot for seconds to minutes, so in-flight count is a far stronger signal than it is for millisecond HTTP calls — this is the one way LLM traffic is easier. Six · Cache-aware routingThe biggest lever

Chapter sixCache-aware routing

Most prefill work in an agent workload is recomputation of a prefix the system already processed a second ago. A router that ignores which replica holds that prefix throws away the largest single latency win available to it.

The problem

An agent conversation is append-only. Turn one sends a system prompt and a question. Turn two sends the system prompt, the question, the assistant's reply, the tool result, and a new question. Turn ten sends everything again. Since prefill is the compute-bound phase and its cost scales with prompt length, a ten-turn conversation spends most of its total prefill re-deriving keys and values for tokens that have not changed since turn one.

Prefix caching fixes the arithmetic: the server hashes fixed-size blocks of tokens, keeps their computed KV blocks, and on a request whose leading tokens hash identically it reuses them and prefills only the suffix. But the KV blocks live in one replica's GPU memory. Route turn two to a different replica and there is no cache to hit, and you pay the full prefill again.

Six · Cache-aware routingThe biggest lever
Say this

“Prefix caching is a per-replica win, so it's only a win if routing cooperates. Cache-blind load balancing across N replicas turns a hit rate into roughly a one-in-N hit rate.”

Two ways to know where the prefix is

Approximate routing predicts cache residency from the router's own memory of what it sent where: keep a prefix tree of recent requests keyed by hashed token blocks, and route a new request to whichever replica most recently received the longest matching prefix. Cheap, needs nothing from the backend, and wrong whenever the backend evicted the blocks under memory pressure — which the router cannot see.

Precise routing reads the backend's actual block state. vLLM emits KV-cache events; an indexer maintains a near-real-time global view of which blocks live on which pod; the scheduler scores pods by genuine prefix-match length. This is what llm-d does inside the Kubernetes Gateway API Inference Extension, and it is more accurate at the price of a new stateful component in the path.

Six · Cache-aware routingDrawn

The same three turns, routed two ways

Reported gains, and read the conditions. llm-d's precise prefix-cache-aware routing reports a 99.5% mean TTFT reduction and a 159.5% throughput increase against a cache-blind baseline, and separately 57× faster TTFT and 2× throughput versus round robin on 8 pods and 16 H100s. These are vendor figures on workloads with heavy prefix sharing — the best case for the technique, by construction. Quote them as “order of magnitude on shared-prefix workloads”, never as a general expectation, and expect an interviewer to push on exactly that.

Six · Cache-aware routingThe real trade-off

Cache affinity is the enemy of load balance

This is the whole difficulty, and it is the question a good interviewer asks next. Routing by prefix match is session affinity by another name: it deliberately concentrates a conversation on one replica. Chapter five spent its entire argument on not concentrating traffic. Both are correct, and they pull against each other.

What real schedulers do is score rather than choose: each candidate replica gets a weighted sum of prefix-match length and available capacity, and the weights decide how much queueing you are willing to accept for a cache hit. The right weighting is workload-dependent and there is no universal answer — which is exactly why it makes a good interview question.

Trap

“Then just use sticky sessions on the conversation id.” Tempting, simple, and worse than prefix scoring in three ways. It pins a conversation to a replica even after that replica has evicted the blocks, so you get the load imbalance with none of the cache benefit. It cannot share a prefix between conversations — and the largest shared prefix in most deployments is the system prompt, which every conversation has. And it has no graceful degradation: when the replica dies, every one of its sessions is cold at once, whereas a scored router simply finds the next-best match.

Seven · Quality routing and cascadesChoosing the model

Chapter sevenQuality routing and cascades

Chapter one established that choosing the model is the latency decision. It is also the cost decision, by roughly the same factor. Which raises the obvious question, and then the much harder one: can you decide per request, and can you decide correctly?

The problem

A frontier model answering “summarise this paragraph” is spending a hundred times the money and ten times the first-token latency of a small model that would have answered it identically. But you do not know in advance which requests those are. Quality routing is the attempt to predict, per request, the cheapest model that will still be good enough — and every design in this chapter is a different bet on how to make that prediction.

Four shapes, and what each bets on

Learned pairwise routers. RouteLLM trains a router on human preference data — Chatbot Arena battles — to decide between a strong and a weak model per query. Published results: cost reductions over 85% on MT Bench, 45% on MMLU and 35% on GSM8K against a GPT-4-only baseline, while retaining 95% of GPT-4's measured performance. The bet is that query difficulty is predictable from the query text alone.

Seven · Quality routing and cascadesChoosing the model

Classifier routers. An embedding model or small classifier assigns the query to a category or a difficulty band, and a table maps that to a model. The bet is that your categories are separable in practice, which is where they usually fail: “simple factual lookup” requests routinely contain implicit complexity, and “needs judgement” requests routinely resolve trivially.

Cascades and escalation. Try the cheap model, check the answer, escalate on failure. The bet is that verification is cheaper than generation — which is true when the check is a schema validation or a test suite, and false when the check is another model.

Signal routers. Route on something structural rather than semantic. NeMo Switchyard's stage router examines tool activity to infer which phase of a coding task the agent is in; its prefill router extracts residual-stream signals to predict success likelihood per candidate model. The bet is that context, not content, predicts difficulty — and on agent traffic that bet is often the best one available.

Seven · Quality routing and cascadesCalibration and drift

Why a router that worked stops working

Confidence is miscalibrated. A cascade escalates on a signal — a self-reported confidence, a verifier score, a heuristic. Model-reported confidence is known to be poorly calibrated and highly prompt-sensitive, which means the threshold you tuned is a property of your prompt as much as of the task. Change the system prompt and the escalation rate moves without anything about the workload changing.

The threshold does not transfer. A threshold tuned on one traffic mix fails on another, and traffic mix drifts continuously as users learn what the product can do. This makes a router a component with a decay rate, which is unusual for infrastructure and is the thing that surprises teams: nothing broke, and it got worse.

Cascade quality is bounded by the check, not by the models. If the verifier cannot tell a wrong answer from a right one, escalation fires at random and you have bought latency and cost for nothing. Where the check is a compiler, a schema validator, or a test run, cascades are excellent. Where the check is a model grading another model's prose, be sceptical and demand the measurement.

The instrumentation this needs

Three counters, per route: the escalation rate, the disagreement rate on a shadow sample where you run both models and compare, and the cost-per-successful-task rather than cost per call. “Route each turn independently to the best model for it.” Switching model mid-conversation costs more than the routing table suggests. Eight · What translation losesBug families

Why the same defect appears in six unrelated products

Three reasons, and being able to give all three is the difference between reciting a bug list and understanding the domain.

The internal representation is a lowest common denominator. Chapter three's figure: everyone collapses dialects × backends into dialects + backends by routing everything through one internal request type. A field that type cannot express is unreachable from every adapter at once. is_error has no Chat Completions equivalent, so it tends not to exist in the IR, so it cannot come out the other side even on routes where it could have.

Tests are written per-dialect, not per-round-trip. A gateway's test suite typically asserts that its OpenAI route works and that its Anthropic route works. The cross-format path — Anthropic ingress, OpenAI-shaped backend — is the product's whole reason to exist and is the least-tested code in it. The evidence is in the controls: in nearly every case above, the same process's same-format route handles the field correctly. Bifrost drops stop_sequences on its Anthropic ingress while its OpenAI route forwards stop 5 times out of 5. The mapping exists. It is simply not applied.

Silence has no test. You can write a test for a 400. Writing a test for “the response was fine but one flag is missing three hops upstream” requires capturing what the gateway forwarded, which requires a rig most projects do not have. This is why the losses are all on the encode side and why they survive for years.

One defect, all the way down: the tool-call id sanitiser

native id, direct from the provider  : functions.list_skills:0

The output is charset-legal — that is the point of sanitising, and it is not the bug. Bifrost has the mirror-image defect: it sanitises correctly for the client and then forwards the sanitised form back upstream, where the original was expected.

Chapter nineStreaming through a proxy

Streaming is where a gateway either preserves the entire point of TTFT or destroys it, and simultaneously where translation is hardest, because the unit you are translating is a fragment rather than a document.

The problem

A non-streaming translator can be a pure function: parse the whole response, build an internal representation, emit the target format. That design is easy to test, easy to reason about — and if you apply it to a stream, you have to buffer the whole response before you can emit anything, which converts a 300 ms first token into an eight-second wait. Streaming translation must be incremental and stateful, and that is a fundamentally harder program. Every bug in the back half of this chapter follows from that sentence.

Half one: the milliseconds

Nine · Streaming through a proxyTwo ways to ruin it

The classic failure is not in the gateway at all, it is in whatever reverse proxy sits in front of it. NGINX enables proxy_buffering by default, which for a Server-Sent Events stream means it accumulates the upstream response and forwards nothing — so the client hangs, or receives the whole conversation in bursts. The reported symptom is unmistakable: updates arriving in 15-to-20-second clumps, sometimes with the stream dying outright.

proxy_buffering        off;      // the actual fix
proxy_http_version     1.1;      // 1.0 blocks chunked transfer
proxy_set_header       Connection "";
proxy_read_timeout     3600s;    // the 60s default kills long completions
proxy_send_timeout     3600s;

// or, from the application, per-response:
X-Accel-Buffering: no
Cache-Control: no-cache

Four defaults, four different symptoms. Buffering gives you burst delivery; HTTP/1.0 blocks chunked transfer entirely; the 60-second read timeout truncates exactly the long generations you most wanted; and compression middleware inserted anywhere in the path will buffer to compress. Each is a one-line fix and each has cost somebody a week.

Nine · Streaming through a proxyFragment translation

Half two: the meaning

An incremental translator has to make decisions with incomplete information, and each of these is a real, reproduced consequence.

The terminal signal arrives last and is easy to get wrong. Whether a turn contained a tool call is only fully known at the end of the stream, and the stop reason is emitted there. Both LiteLLM and Bifrost have shipped streaming paths that end a turn containing a valid tool_use block with end_turn — and Bifrost's was a regression of a bug it had already fixed, caught by an unchanged checker written for a different vendor.

Tool calls arrive in fragments that must be reassembled by index. OpenAI streams tool_calls as deltas carrying an index; a translator that ignores or omits the index merges two parallel calls into one, or loses the second entirely.

Chunk boundaries are not semantic boundaries. When reasoning and visible text arrive in a single upstream chunk, their relative order must be preserved into the target stream; Switchyard has been observed emitting text before the thinking that preceded it. Similarly, an empty content chunk emitted before the tool chunks is legal-looking and breaks strict client SDKs.

Sentinels can appear inside payloads. SSE terminates on data: [DONE]. A tool argument whose value contains the literal string [DONE] can therefore false-terminate a naive line-oriented parser. Worth knowing precisely because of how kairo's attempt to reproduce it went — see the box below.

Streaming and non-streaming are two products

They are usually two code paths, and they diverge in both directions. Switchyard's streaming tool-call translation is correct — kairo probed it specifically and recorded a clean result — while the same version's non-streaming Anthropic path invents an empty {"type":"text","text":""} block before every tool_use when the backend is OpenAI-shaped. So a conformance result on one path tells you nothing about the other. If you take one operational rule from this chapter, make it that: every invariant must be asserted twice, once streamed and once not.

Cancellation, which nobody tests

A user closes the tab. The client disconnects. Does your gateway notice, and does it propagate the cancellation upstream? If it does not, the model keeps generating into a socket nobody is reading, and you are billed for every token of it. On an agent workload with long generations and an impatient UI, this is a real and entirely invisible line item.

The same question in reverse is the hedging constraint from chapter two: once the first token has been forwarded to the client, you have committed to that stream. A gateway cannot fail over mid-stream without either replaying tokens the client already has or emitting a discontinuity. Which produces the operational rule worth saying out loud:

Say this

“Failover is only free before the first token. After that, a retry is visible to the user, so I'd treat first-token emission as the commit point — hedge and fail over freely before it, and after it only cancel.”

Trap

“We'll buffer a little at the start so we can retry on an early error.” Superficially reasonable and it silently sells the thing streaming was for. If you hold the first k tokens to keep your retry option open, you have added the time to generate k tokens to your TTFT — at 20 ms per token, buffering ten tokens costs 200 ms of the number the whole feature exists to minimise. If you want an early-error retry window, take it from the pre-first-token region, where it is free.

Ten · Failing overRetries, breakers, timeouts

Chapter tenFailing over

Providers degrade, rate-limit and fail. The reason a router exists is usually to survive that. The reason a router takes a system down is usually the code that was supposed to.

The problem

A partial outage becomes a total one through amplification. A provider slows down; requests time out; the client retries; retries add load to the thing that was already struggling; more requests time out. The system now has a stable failure state it will not leave even after the original cause is gone, because the retry traffic is sustaining it. Every mechanism in this chapter is a way of bounding that.

Bound retries as a budget, not as a count

“Three retries per request” sounds conservative and permits a 4× traffic multiplier at exactly the moment you can least afford one. A retry budget caps retries as a fraction of total requests over a window — say 10% — and refuses them beyond that. It is self-limiting under widespread failure and unrestrictive under isolated failure, which is precisely the behaviour you want and the opposite of what per-request counts give you. Add full jitter to the backoff, or your retries synchronise into waves.

Ten · Failing overRetries, breakers, timeouts

Break circuits per provider and model

A breaker keyed on the provider alone means an outage on one model blocks traffic to every other model that provider serves. Key it on provider × model × region — the failure domains are usually per model deployment, and so should the breaker be. Half-open probes then let a single request test recovery instead of the whole fleet stampeding back the instant the timer expires.

Say this

“Retry budget rather than retry count, jittered backoff, and a breaker per provider-and-model rather than per provider. Those three together are what stop a slow backend from becoming an outage.”

Ten · Failing overOne timeout is not enough

A single overall timeout cannot tell healthy from hung

The rule to carry away. Total-time timeouts on streaming LLM calls are a category error: a legitimate answer can be arbitrarily long, so any total bound either truncates good work or fails to catch a hang. Bound each phase instead, and put the strict bound on the inter-token idle gap, which has a real expected value — TPOT — and therefore a defensible threshold.

Here is a failure that only exists because the two halves of this book meet, and it is reproduced rather than hypothetical.

Chapter elevenTokens and money

An agent conversation's input cost grows quadratically in the number of turns unless something caches it. The router is the only component that sees every request and can therefore either capture that saving or silently destroy it.

The problem

Turn one sends L tokens. Turn two resends those plus the new ones. Turn i sends roughly i × L. Summed over n turns that is L × n(n+1)/2 — quadratic in turn count, in both prefill latency and input billing. A twenty-turn agent session does not cost twenty times a one-turn session; it costs roughly two hundred times.

Eleven · Tokens and moneyEnforcing a budget you cannot predict

Denial of wallet

Rate limiting by requests per second is the wrong unit for a system where one request can cost ten thousand times another. The threat model has a name — denial of wallet — and it does not require an attacker: a runaway agent loop with no step cap is a self-inflicted version of it, and is by far the more common cause.

The standard construction is a token bucket denominated in budget units rather than requests, refilling at a fixed rate, checked per key or per tenant. Azure API Management's LLM token-limit policy is a shipped example, and its response semantics are worth copying: 429 when a per-minute rate is exceeded, 403 when a period quota is exhausted. Those are different conditions and a client should be able to tell them apart — one means retry later, the other means stop.

The structural difficulty, and the answer

You cannot enforce an output-token budget before the call, because nobody knows the output length. So the enforcement has three parts, and naming all three is the staff-level answer:

Bound it in the request. max_tokens is the only hard pre-emptive control you have. A gateway that lets a request through without one has no ceiling — which incidentally is why a gateway inventing max_tokens: 64000 is dangerous in a second way: it silences the missing-ceiling problem while setting a ceiling nobody chose.

Reserve, then reconcile. Deduct an estimate at admission — input tokens plus max_tokens — and refund the difference when the actual usage comes back. This is what keeps a thousand concurrent requests from each individually passing a check they collectively blow through.

Cap the loop, not just the call. Per-request budgets do not bound an agent that can call itself. The enforcement point has to be the session or task, with a step count and a cumulative token ceiling, and it has to live somewhere the agent cannot edit.

A gateway exists partly so that provider keys live in one place instead of scattered through a dozen services. That is a genuine security improvement, and it means the one place now holds every key for every tenant.

The problem

Consolidating credentials moves risk rather than removing it. Before, a compromised service leaked one key. After, a leak at the gateway is the union of every provider and every tenant. Allowlist what crosses the boundary, in both directions. Every one of the header-forwarding defects is a denylist that was complete on the day it was written. 2 min“What's the blast radius of putting every team's provider keys behind one gateway?”

Model answer

Concede the benefit first, or the rest reads as obstruction: consolidation genuinely reduces the number of places a key can leak from, and it is the only way to get uniform rotation and attribution. 45 sec“How would you test for credential leaks in a gateway, in CI, without real keys?”

Model answer

Canaries. Configure the gateway with distinctive fake secrets, drive it with a probe suite, and scan every byte that comes back out — response bodies, error bodies, health and admin endpoints, and the bytes forwarded to a local mock upstream — for the canary strings. That is fully deterministic, needs no provider account, and runs on every commit. Add the negative probes too: plant a credential in a client header and in the body and assert it does not reach the mock upstream, which makes the assertion inverted — a pass means the gateway declined to do the bad thing.

Chapter thirteenProving it

Every defect in the last five chapters is invisible to the tests these products ship, because they all return 200. So the last mechanism is the one that makes the others knowable: how you turn “the model seems worse” into a checkable assertion.

The problem

You cannot test a translation layer from the outside by looking at responses, because most losses are on the encode side — the request that reached the backend was already wrong, and the response is a perfectly valid answer to the wrong question. And you cannot test it by reading documentation, because the documentation describes the intended mapping and every defect lives in the gap between intent and code.

The three-legged standard

kairo holds every finding to three legs, and the second is the one people omit.

Wire evidence. The actual bytes, raw SSE or JSON, committed. Not a screenshot, not a paraphrase, not a log line. If the claim is that a field was absent, the artefact is the body it was absent from.

Thirteen · Proving itConformance as practice

A control that works. The same input succeeding somewhere — the model called directly, another route on the same process, another version of the same product. The control is what pins the blame on the translation layer instead of on the model or the prompt. Without it you have an anecdote about a bad output, which is what most bug reports in this space are, and why most of them go nowhere.

Determinism. N of N reproductions with the trigger narrowed as tightly as you can make it — exact field, exact length, exact chunk shape. “Sometimes” is a lead, not a proof.

Say this — it is the sentence that separates levels on this topic

“A bug report against a gateway is worthless without a control. Same input, same version, succeeding on another route — that's what makes it a translation-layer defect rather than a story about a model behaving badly.”

Thirteen · Proving itThe technique

Point the gateway's backend at something that only records

Why this works. The interesting losses happen on the way out, so the observation point has to be upstream of the gateway, not downstream of it. A mock that records and replies makes that observation trivially, with no provider account, no rate limits and no nondeterminism — which means it runs on every commit. kairo names it as the technique that unlocked most of its findings, and the entire “silent field loss” family was found this way.

Thirteen · Proving itScoring instead of arguing

A checker is an invariant, and it runs both directions

The unit of a conformance suite is not a test of a product; it is an invariant that any correct translator must satisfy, evaluated against recorded bytes and returning a verdict with a reason:

// if a streamed Anthropic response contains a tool_use block,
// the terminal stop_reason MUST be "tool_use".
pub fn anthropic_toolcall_stop_reason(sse: &str) -> Verdict {
    // ... no tool_use block? nothing to check, Conformant.
    match stop_reason.as_deref() {
        Some("tool_use") => Verdict::Conformant,
        other => Verdict::Violation(format!(
            "tool_use block present but stop_reason is {other:?}")),
    }
}

Run that against a buggy gateway's transcript and it reports the violation; run it against a correct one and it reports conformance. Same checker, both directions. That is what turns a bug list into a score, and a score is something you can put in CI and in a comparison table without arguing about it.

It also means invariants outlive products. The checker written for LiteLLM's stop-reason bug caught Bifrost's regression of its own already-fixed issue, unchanged. One checker written for a dropped parallel-tools flag catches the same defect on five gateways in three languages. You are not testing a product; you are testing a claim about a protocol.

Thirteen · Proving itScoring instead of arguing
Keep the negatives

kairo records non-reproductions alongside confirmations: cited bugs that turned out to be patched on current, symptoms that would not fire on a backend that sends tool arguments whole, a probe that came back correct because the gateway's streaming translation genuinely works. Three reasons this matters, and the third is the one worth saying aloud. It keeps the corpus from being a sales deck. It records the boundary conditions of the finding, which is what makes the next reproduction cheaper. And “this cited bug is already fixed” is itself the argument for a permanent suite — because a bug that was fixed is not a bug that is gone, as Bifrost's regression demonstrates.

Trap

“We ran 96 probes and 20 failed, so the gateway is 79% conformant.” Only if all 96 ran. kairo's matrix carries an explicit not run column so that a gateway which could not be started shows up as unmeasured rather than disappearing from the table — because a missing row silently improves the denominator. Report the denominator, the version, and what you could not measure, every time. That habit is more of the signal in a staff interview than the finding is.

2 min“We're building our own router. How do you stop it from silently corrupting requests as it grows?”

Model answer

Make the encode side observable, then make it a gate. Concretely: a mock upstream in the test harness that records exactly what the router forwards; a corpus of golden request transcripts, one per interesting feature — tool calls, tool results with errors, images in tool results, reasoning blocks, cache breakpoints, stop sequences, structured output; and a set of invariants asserted as checkers that return conformant or a violation with a reason. Then the two things that keep it honest as it grows. Keep negatives — a probe that comes back clean is a result and gets recorded, or the corpus drifts into a list of things you already know are broken. And write the invariants against the protocol, not against your implementation, so a checker you wrote for your own bug also catches the same bug in a vendor you later adopt. That is the property that makes the suite compound instead of decay.

Anthropic: write at 1.25× input for a five-minute TTL, or 2.0× for an hour; reads at 0.10×; minimum 1,024 tokens; up to four breakpoints. Part IIIContested, one

ContestedWhat this field has not settled

Five questions where practitioners genuinely disagree. Knowing that a question is contested is worth more than having an opinion on it, because it lets you handle an interviewer who holds either position.

One · Does model routing pay off outside a benchmark?

For: the reported wins are large and come from more than one group — RouteLLM's 45–85% cost reductions at 95% of GPT-4's performance, Switchyard's 74% at roughly six accuracy points on a multi-turn agent benchmark. Traffic really is dominated by easy requests, and the money is real.

Against: every published result is measured on a benchmark, and a 2026 arXiv paper — Unsolvability Ceiling in Multi-LLM Routing: An Empirical Study of Evaluation Artifacts — argues from its title onward that routing evaluations are contaminated by artefacts of how they are constructed. Sceptics add an engineering argument: a router is a component with a decay rate, and the same money is often available from caching and static class rules with no accuracy risk and no maintenance.

Part IIIContested, one

What each side optimises for: proponents optimise cost at fixed quality on aggregate traffic; sceptics optimise worst-case quality and operational simplicity. Both are coherent. The reconciling position, and the one worth stating, is that the argument is really about ordering: caching and static rules first because they are free and auditable, learned routing afterwards on the ambiguous remainder, shipped in shadow.

Two · Should the router be a network hop or a library?

Hop: one dialect for every client in every language, central quota and spend attribution, credentials in one boundary, policy changed without redeploying callers. Library: no extra network hop, no new single point of failure, no credential concentrator, and no cross-process serialisation of a 60 KB body twice per request.

Switchyard ships both surfaces deliberately — a standalone server and an embeddable Rust library — which is a reasonable read of the disagreement: it is not resolvable in general, it is resolved by whether you need central control across many services or speed within one.

Part IIIContested, two

Three · Is silent lossy translation acceptable?

This is the sharpest disagreement in the book, and it is a genuine values split rather than a knowledge gap.

The compatibility position: a gateway's job is to make heterogeneous things work together, so when a field has no target equivalent it should be dropped and the request should proceed. Failing loudly on every unmappable field makes the product useless, because real clients send fields real backends do not support all day long. Some of the losses catalogued in chapter eight are documented by their authors as by-design, permitted with diagnostics.

The correctness position: a caller who set is_error, or a cache breakpoint, or a stop sequence, expressed an intent. Discarding it while returning 200 is not compatibility, it is a lie about what was executed — and the cost lands weeks later on someone who cannot see the gateway.

Where they can meet: the distinction between dropping and reporting the drop. kairo's own invariant is not “never drop”; it is that a dropped feature with no target equivalent must be surfaced as a decision, not silently discarded. That reframing dissolves most of the argument, and it is the answer to give: the dispute is not about whether to drop, it is about whether the caller is told.

Four · How much load imbalance should a cache hit be worth?

Part IIIContested, two

Nobody has a general answer. Prefix affinity and load balance are two terms in one objective and the weight between them is workload-dependent: long shared prefixes and short generations favour affinity, short prompts and long generations favour balance. Treat a fixed weight as a tuning parameter with a monitor on it, and be suspicious of anyone who states a universal number.

Five · Normalise, or expose an escape hatch?

A gateway that normalises everything to a common subset is predictable and cannot express what a specific provider does well — extended thinking budgets, provider-specific cache controls, structured-output dialects. A gateway with a passthrough escape hatch preserves capability and destroys portability, since clients start depending on the thing that only works on one backend. Most products end up shipping both and being unclear about which one you are using, which is its own answer about how hard the question is.

Say this when handed a contested question

“That one's genuinely contested. One camp optimises for compatibility and treats an unmappable field as something to drop and continue; the other treats it as a lie about what was executed. I lean toward reporting rather than dropping, because the cost of silence lands on someone who can't see the gateway — but I'd want to know which failure your users can tolerate before I designed it.”

Appendix ACheat sheet

Open with these five. Which client dialects? Which backends? Streaming? Multi-tenant? TTFT or end-to-end? Thirty seconds, then stop and listen.

Two workloads. Prefill: compute-bound, parallel over the prompt, ends at the first token. Decode: memory-bandwidth-bound, serial over the output. e2e = TTFT + TPOT×(n−1).

Goodput, not throughput. Throughput counted only over requests meeting p99 TTFT < t1 and p99 TPOT < t2. Throughput alone is always improvable by making the p99 worse.

Queues. L = λW. Delay carries 1/(1−ρ) — 90% utilisation is ~10× the floor. Ten steps at p99 = 1 s means ~10% of loops blow the budget.

Never average percentiles. Order statistics do not compose. Store histograms.
