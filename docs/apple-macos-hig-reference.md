# Apple macOS design reference for Bridge

Reviewed **September 6, 2026**. Starting point: [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos).

**Platform scope: macOS only.** Shared HIG guidance is included only where it applies to Mac. Mobile, TV, watch, and spatial-platform requirements are outside this reference's scope.

## Coverage

Read the starting article and **all 13 unique destinations linked from its article body and Resources section**: eight HIG topics, two resource pages, and three WWDC sessions. Read the sessions' published transcripts; this was not a frame-by-frame video review. Also reviewed the general and macOS guidance in **18 related HIG topics**, for **32 sources** total. Every source appears below.

This scope excludes Apple's global navigation, account and legal links, binary design-kit downloads, and an unlimited recursive traversal of every subsequent link. The resource landing pages were read; the linked Figma/Sketch files were not inspected. The notes are a synthesis, not a verbatim archive of Apple's documentation.

Apple's HIG article bodies were retrieved from the public documentation JSON served under `https://developer.apple.com/tutorials/data/design/human-interface-guidelines/<topic>.json`. The starting article was also checked in the rendered website. Resource pages and transcripts were read from Apple's published HTML.

These are research notes, not a completed audit or implementation of Bridge. Bridge-specific applications below are interpretations. Repository requirements in [AGENTS.md](../AGENTS.md) continue to govern implementation.

## Working principles for Bridge

1. **Make sustained work comfortable.** Use the desktop's space to keep the task and useful context visible. Prefer a clear hierarchy and adjustable panes over repeatedly interrupting work with modal steps. Support narrow windows as well as expansive workspaces. [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos)

2. **Make commands discoverable.** The menu bar is a dependable command directory, including actions also offered in toolbars. Preserve familiar menu ordering, keyboard equivalents, and disabled states. A toolbar should expose a useful subset of commands. [The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar), [Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)

3. **Let the operating system manage windows.** Preserve familiar moving, resizing, minimizing, activation, and full-screen behavior. Open additional windows when they help the task. Treat focus and inactive-window appearance as functional information. [Windows](https://developer.apple.com/design/human-interface-guidelines/windows), [Going full screen](https://developer.apple.com/design/human-interface-guidelines/going-full-screen)

4. **Use materials to express a hierarchy.** Liquid Glass is intended for the navigation and control layer. Standard materials serve the content layer. For Bridge, this suggests quiet, legible transcript and work surfaces, with selective separation for navigation and floating controls. [Materials](https://developer.apple.com/design/human-interface-guidelines/materials)

5. **Express relationships through spacing and grouping.** Group related controls, align edges, and make nested corner shapes harmonious. Compact desktop controls still use rounded rectangles; larger, prominent controls can use capsules. [Get to know the new design system](https://developer.apple.com/videos/play/wwdc2025/356/)

6. **Support several ways to act.** Keyboard navigation, pointer interaction, contextual commands, selection, paste, and drag and drop should work coherently. Never make a gesture or hover discovery the only practical route to important work. [Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards), [Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices), [Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data)

7. **Preserve work and context.** Save appropriately, retain the user's place, and finish user-initiated background work when it does not require participation. Completion notifications should earn their interruption. [File management](https://developer.apple.com/design/human-interface-guidelines/file-management), [Multitasking](https://developer.apple.com/design/human-interface-guidelines/multitasking)

8. **Make accessibility part of the base design.** Provide useful accessible names, visible focus, readable text, adequate targets, and alternatives to color-only or audio-only feedback. Support changes in contrast, transparency, motion, and text size. [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)

## The starting article and all its direct links

| Source | Notes from the source |
| --- | --- |
| [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos) | Design for large, high-resolution displays, potentially several at once; precise input; both brief interactions and long sessions; and frequent app switching. Offer flexible windows, keyboard shortcuts, menu commands, and useful customization. Comfortable density and shallow navigation matter. |
| [Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards) | Preserve standard shortcuts and Full Keyboard Access. Reserve custom shortcuts for frequent app-specific actions. Command is the preferred primary modifier; related Shift variants should retain a meaningful relationship. Consider international keyboard layouts. Shortcut symbols are ordered Control, Option, Shift, Command. |
| [Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices) | Keep mouse, trackpad, keyboard, and modifier behavior consistent. Preserve system gestures and user customization. Use appropriate Mac cursor meanings for text, links, dragging, resizing, and invalid drops. Secondary click should reveal contextual commands. |
| [Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls) | Mac games should retain keyboard and mouse/trackpad input, detect controllers, show labels appropriate to the active controller, and allow keyboard remapping. Game-specific single-key bindings are not general desktop-app requirements. This direct link was reviewed but has limited application to Bridge. |
| [Siri](https://developer.apple.com/design/human-interface-guidelines/siri) | Expose useful actions and content through App Intents and appropriate entities or schemas. Prefer familiar terminology, relevant content, concise responses, and contextual errors. Responses should work audibly and visually. Integration is an optional product capability; an app's own assistant interface is not automatically a Siri integration. |
| [The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar) | Use the familiar App, File, Edit, optional Format, View, app-specific, Window, Help ordering. Keep unavailable commands visible but disabled. Separate view customization from window management. Include Window even for a single-window app. Menu bar extras should be optional and cannot be the sole route to a feature. |
| [File management](https://developer.apple.com/design/human-interface-guidelines/file-management) | Prefer familiar open/save interfaces and preserve work automatically where appropriate. Let users choose names, formats, and locations. Quick Look can preview attachments the app cannot edit. Custom browsers should respect users' understanding of the file system. Unsaved-change indicators must accurately reflect saving behavior. |
| [Going full screen](https://developer.apple.com/design/human-interface-guidelines/going-full-screen) | Use the system full-screen experience and let users decide when to enter or exit. Keep essential features accessible, preserve context across app switching, and make layout transitions subtle. Retain access to the Dock in ordinary apps. Do not confuse full screen with zooming or a custom display mode. |
| [Dock menus](https://developer.apple.com/design/human-interface-guidelines/dock-menus) | Include a few useful actions, such as opening recent windows or beginning common work while the app is not frontmost. Provide those commands elsewhere too. Dock access supplements the main interface. |
| [Apple Design Resources](https://developer.apple.com/design/resources/#macos-apps) | Official UI kits, icon templates, fonts, symbols, and production assets support accurate design. At review time the macOS section listed macOS 27 UI kits for Figma and Sketch. This establishes the available reference material; those kits were not downloaded or inspected. |
| [macOS Pathway](https://developer.apple.com/macos/get-started/) | The development overview connects windows, menus, Dock integration, accessibility, localization, privacy, security, testing, and performance. It points to Xcode, SwiftUI, and AppKit resources. These framework recommendations need translation for Bridge's Tauri architecture. |
| [Meet Liquid Glass — WWDC25](https://developer.apple.com/videos/play/wwdc2025/219/) | Glass responds to its surroundings and interaction to separate controls from content. Avoid stacking glass surfaces. Use tint for emphasis. Regular and clear variants have different purposes. Native materials accommodate reduced transparency, increased contrast, and reduced motion. Read the current Materials article for refinements to the older session's guidance. |
| [Get to know the new design system — WWDC25](https://developer.apple.com/videos/play/wwdc2025/356/) | Maintain coherent geometry, clear content/control relationships, and continuity across sizes. Group toolbar actions by function; separate text actions when they could be mistaken for an icon's label. Scroll-edge effects protect legibility where floating controls overlap scrolling content. Compact Mac layouts retain desktop-appropriate density. |
| [Build an AppKit app with the new design — WWDC25](https://developer.apple.com/videos/play/wwdc2025/310/) | Native toolbar and split-view APIs supply much of the new appearance. Custom native glass uses `NSGlassEffectView` and, for related elements, `NSGlassEffectContainerView`. Avoid glass backing on informational labels that would then resemble buttons. Audit hard-coded control heights and content near rounded window corners. These are AppKit behaviors, not automatic React features. |

## Related guidance reviewed

For these 18 sources, review focused on general guidance applicable to Mac and the macOS sections.

| Source | Notes relevant to macOS |
| --- | --- |
| [Windows](https://developer.apple.com/design/human-interface-guidelines/windows) | Prefer system window frames and controls. Distinguish primary and auxiliary windows. Let layout adapt and provide optional new-window actions where useful. Main, key, and inactive windows communicate different states. Critical actions should not depend on a bottom bar that users may move offscreen. |
| [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars) | Use the leading side for top-level navigation. Keep hierarchy to roughly two levels, with disclosure and concise section labels. Allow hiding and useful customization. Consider collapsing as a window narrows. Honor accent preferences and size settings when applicable. Avoid burying essential actions at the bottom. |
| [Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars) | Choose frequent, meaningful actions; keep groups few and stable; preserve navigation and important trailing actions during resizing. Use a useful content title. Distinguish an explicit More menu from system-managed overflow. Provide toolbar commands in the menu bar. Restrict strong prominence to the primary action. |
| [Menus](https://developer.apple.com/design/human-interface-guidelines/menus) | Use concise action labels and ellipses when further input is required. Group related commands; limit submenu depth. Make current states legible through checkmarks or action-oriented changing labels. Use recognizable icons consistently within each group. Unavailable menus and submenus should still reveal their commands. |
| [Panels](https://developer.apple.com/design/human-interface-guidelines/panels) | Supplement the current task with a small set of controls or information. An inspector follows selection; a fixed information window does not. Native panels follow app activation and generally do not need minimization. Dark HUD styling is specialized for suitable media experiences. |
| [Popovers](https://developer.apple.com/design/human-interface-guidelines/popovers) | Keep scope small and connected to the invoking element. Use one at a time, avoid cascades, and preserve work on incidental dismissal. Show explicit cancellation when it intentionally discards changes. Use alerts for warnings. A detachable Mac popover may become a panel while retaining visual continuity. |
| [Settings](https://developer.apple.com/design/human-interface-guidelines/settings) | Start with good defaults and a manageable set of options. Keep frequently changed task options beside their task. Respect system settings. On Mac, provide App > Settings and Command-comma. Settings navigation should remain stable and restore the last pane. |
| [Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data) | Reduce unnecessary entry, provide clear labels and useful defaults, support paste and drop, and validate near the field. Use secure entry for secrets. Choose lists or menus when they simplify input. Reveal the full value of truncated fields when useful. |
| [Layout](https://developer.apple.com/design/human-interface-guidelines/layout) | Use alignment, spacing, and grouping to establish hierarchy. Keep essential content visible; progressively disclose secondary detail. Let layouts adapt to window dimensions, locale, text size, and displays. Backgrounds can extend edge to edge while interactive content respects safe areas. |
| [Multitasking](https://developer.apple.com/design/human-interface-guidelines/multitasking) | Save and restore context around interruptions. Finish background work that does not need participation; pause activities that would cause users to miss important content. Notify selectively about significant completions. Mac app switching and multiple visible windows are normal operating conditions. |
| [Motion](https://developer.apple.com/design/human-interface-guidelines/motion) | Animate to communicate an interaction, relationship, or state. Keep feedback brief and precise, let users continue acting, and avoid costly repeated flourishes. Provide reduced-motion behavior and other ways to perceive important feedback. Pointer-driven motion can be subtler than touch-driven effects. |
| [Focus and selection](https://developer.apple.com/design/human-interface-guidelines/focus-and-selection) | Make the interaction target apparent and avoid moving focus unexpectedly. Use familiar field rings and list selection treatments. Focus, selection, and activation are related but can differ. Interpret the native focus model alongside the webview's own semantics and accessibility behavior. |
| [Materials](https://developer.apple.com/design/human-interface-guidelines/materials) | Choose material by function. Regular glass supports text-bearing controls; clear glass suits media backgrounds. Dimming for clear glass depends on background brightness and existing playback treatments. Standard materials structure content. macOS supports within-window and behind-window blending with different purposes. |
| [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) | Support perception, input, and comprehension through several channels. Test assistive technology rather than relying on visual inspection. Allow text enlargement, comfortable controls, and non-color state cues. Avoid essential information that vanishes too quickly. Respond to accessibility preferences. |
| [Color](https://developer.apple.com/design/human-interface-guidelines/color) | Use semantic colors consistently, test light/dark/increased-contrast appearances, and avoid encoding state only in color. Native system color values vary with context. Respect the user's accent selection. Use tint selectively on glass and ensure content behind controls preserves legibility. |
| [Typography](https://developer.apple.com/design/human-interface-guidelines/typography) | Use readable size and weight, a restrained type hierarchy, and layouts that accommodate enlarged text. Custom fonts need equivalent accessibility care. Avoid tight leading for longer passages. macOS uses SF Pro as its system font and does not support Dynamic Type. |
| [Offering help](https://developer.apple.com/design/human-interface-guidelines/offering-help) | Explain the current task rather than standard interface mechanics. Tips should be brief, useful, dismissible, and shown to people who need them. Mac tooltips should describe the action, generally within 60–75 characters, using concise sentence case. |
| [Writing](https://developer.apple.com/design/human-interface-guidelines/writing) | Use consistent terms, direct action labels, and language suited to context. Empty states should offer a next step. Place actionable error guidance near the problem. Prefer useful explanations over blame, jokes, vague failure messages, or implementation vocabulary. |

## Platform and version details to retain

- **Native points are not CSS `pt`.** Apple's current accessibility guidance lists macOS text at 13 pt by default and 10 pt minimum, and controls at 28 × 28 pt by default and 20 × 20 pt minimum. These are platform reference values, not instructions to shrink every component to the minimum or directly substitute CSS physical units. Translate and verify sizing in the actual webview. [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- **Text enlargement still matters on Mac.** The absence of Dynamic Type does not remove the need for readable, adjustable content. The HIG encourages enlargement to at least 200 percent. Bridge needs an appropriate web/native mechanism and layout verification. [Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- **Current articles can refine older talks.** The Materials article allows clear glass without an added dimming layer over sufficiently dark content or when standard media controls already supply one. The 2025 introductory session expresses the conditions more broadly. Use the current article when implementing. [Materials](https://developer.apple.com/design/human-interface-guidelines/materials)
- **Menu icon guidance has evolved.** The Menus page records a June 8, 2026 update and calls for uniform icon treatment within a group. Check it before reproducing examples from WWDC25. [Menus](https://developer.apple.com/design/human-interface-guidelines/menus)
- **Historical examples require judgment.** Even a live page can contain older system shortcut examples. Use the familiar relevant shortcuts, then check actual behavior on Bridge's supported macOS versions before assigning conflicting commands. [Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)

## Applying this research within Bridge

These are candidate review questions, not findings that Bridge currently fails them.

| Bridge area | What to evaluate |
| --- | --- |
| App shell and title bar | Native window behavior, draggable regions, activation appearance, safe areas, resize limits, full screen, and discoverable commands. |
| Sidebar and Projects | Shallow information hierarchy, clear selection, retained context, resizing/collapse, and enough space for primary work. |
| Conversation and composer | Readable text, coherent focus, normal editing shortcuts, draft preservation, clear send/stop states, and sustained keyboard use. |
| Work views and inspectors | Whether supplementary detail can remain beside the task; whether a separate window, inspector, or transient popover best fits its duration and purpose. |
| Menus and toolbars | Matching command availability, consistent labels, sensible grouping, understandable icons, and reliable behavior when space is constrained. |
| Settings | App-wide options separated from task-local controls; familiar access; stable grouping and restoration. |
| Feedback and background work | Visible progress and actionable errors without unnecessary interruption; context retained after switching apps. |
| Memory | Apply the same legibility, hierarchy, and accessibility standards within the existing Memory screen and its Activity tab. |

Implementation boundaries from the repository:

- Use Tailwind CSS v4 utilities and the existing tokens; shared tokens and exceptional rules belong in `src/index.css`.
- Reuse `.u-glass`, `.u-glass-popover`, `.u-glass-soft`, and the segmented-control primitives according to their existing roles. Their names do not establish that they implement Apple's native Liquid Glass behavior.
- Keep the existing Geist, Bricolage Grotesque, and Geist Mono roles, and use `lucide-react` under current repository conventions. Apple's system fonts and symbols are useful references; adopting the HIG does not itself authorize replacing the project's choices.
- React elements do not acquire `NSToolbar`, `NSGlassEffectView`, or native accessibility behavior merely because they appear inside a Tauri window. Check what the native shell supplies and what the webview must implement. Preserve semantic HTML and usable keyboard access when translating native guidance.
- Maintain one Memory surface in the normal Graphite & Paper chrome. The Panels article's specialized HUD option does not call for a separate dark Memory interface.
- Preserve the app's shared transcript behavior. Visual changes must not introduce agent-specific interaction rules.

For future implementation, verify a representative flow in the actual desktop app: resize the window, switch away and return, use keyboard-only navigation, invoke menu commands, open and dismiss transient UI, enlarge text, and inspect light/dark and accessibility appearances. This research pass did not perform those product checks.
