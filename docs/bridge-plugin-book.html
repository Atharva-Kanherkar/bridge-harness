Part one

What a harness is

A harness is not a model and not an editor. It is the loop between them — and the loop is the thing that ossifies.

One · The loopFoundations

Chapter oneThe loop is the product

The model is bought; the loop is built. Everything Bridge is arguing about lives in the loop.

Notice what is absent: no session list, no diff viewer. Those exist because the loop runs unattended and someone must supervise it afterwards. Bridge's README states its position exactly — it renders normalized messages, plans, tool calls, approvals and file changes “instead of embedding provider TUIs.” Bridge is a supervision surface over somebody else's loop.

Two · ResponsibilitiesFoundations

Chapter twoFour things it must own

Every harness owns the same four responsibilities. Naming them makes the rest of this book a comparison rather than opinion.

The model seam. Which model, at what tier, over which protocol. Bridge calls this an adapter and has three: Codex over app-server, Claude Code through an Agent SDK sidecar, OpenCode against its headless server.

The tool surface. What the agent may do to the machine, and what it must ask about first. Bridge pushes tools down into the provider and keeps the authorization.

Context and memory. What enters the prompt, what is dropped, what survives a restart. Bridge's answer is a session forest: append‑only entries, each with a parent pointer, projected into a branch.

The supervision surface. How a human sees what happened and intervenes. For Bridge this is the whole React application — and the responsibility this book argues is least well served.

Why the four matter

DeepSeek makes all four swappable in configuration. Bridge has made one swappable in code. That gap is Part V.

Three · OssificationFoundations

Chapter threeWhy harnesses ossify

Harnesses do not rot because their authors are careless. They rot because the cheapest way to add the eleventh capability is to add a field to the object that already holds the other ten.

Every application has a composition root: the one place where concrete implementations are chosen and handed to everything else. In a young project it is a small struct with four fields, and reading it tells you the whole system.

The root is also the path of least resistance. A new capability needs a database handle, a subscription, and somewhere to keep a cache — and the root already has all three. So the field goes in. Nothing breaks.

What changes is the cost of removal. Once thirty subsystems reach into one struct, none can be lifted out without touching thirty call sites, and the honest answer to “can we swap the storage layer” becomes no. The architecture did not fail. It accreted.

Four · Three treesBridge today

Chapter fourThe three trees

Bridge's central idea: three hierarchies exist, they do not line up, and pretending they do is how agent tools lie to their users.

Five · The protocolBridge today

Chapter fiveThe protocol is the good part

Bridge already did the hard prerequisite for a plugin architecture, and appears not to know it: a versioned, generated, drift‑tested RPC contract sits in the middle of the system.

The bridge-protocol crate is the single source of truth. Everything under docs/protocol/schemas/ and src/protocol/generated/ is produced from it, and drift is a test failure rather than a review note:

cargo test --manifest-path src-tauri/Cargo.toml -p bridge-protocol

Measured 87 methods across 18 domains, 105 generated JSON schemas, 1,405 lines of generated TypeScript. A test parses Tauri's generate_handler![...] and asserts the registry matches one to one, so adding a command without extending the contract fails the build.

Why this matters for Part V

A plugin system needs a stable boundary a plugin can be written against without reading the host's source. Bridge has one, it is enforced, and a client other than the desktop app already speaks it: bridged serves newline‑delimited JSON‑RPC 2.0 over a Unix socket under an exclusive owner lease. The expensive part of “everything is a plugin” is already built.

Six · HarnessAdapterBridge today

Chapter sixOne real plugin boundary

Bridge has a working plugin system for exactly one capability. Reading it is the fastest way to see what the other eight would look like.

pub trait HarnessAdapter: Send + Sync + Any {
    fn descriptor(&self) -> AdapterDescriptor;
    fn start(&self, request: StartRequest<'_>)
        -> Result<StartedAdapter, BridgeError>;
    fn supports_native_resume(&self) -> bool;
    fn normalize(&self, value: &Value) -> Vec<NormalizedEvent>;
}

pub struct AdapterRegistry {
    adapters: HashMap<String, Box<dyn HarnessAdapter>>,
}

Source bridge-core/src/adapters.rs 256–267, elided: as_any and resume are omitted.

Three properties make this a boundary rather than a gesture. descriptor() lets an adapter declare itself, availability included. supports_native_resume() lets it admit a missing capability instead of faking it. And normalize() means the rest of the system never learns which provider it is talking to.

Six · HarnessAdapterThree registries

Registration is already dynamic

built_in() happens to hard‑code three adapters, but register() takes any box and rejects empty or duplicate ids:

registry.register(Box::new(CodexAdapter))?;
registry.register(Box::new(ClaudeAdapter {
    streams: Mutex::new(HashMap::new()) }))?;
registry.register(Box::new(OpenCodeAdapter::new(
    opencode_settings, on_opencode_discovered)))?;

This is a string‑keyed runtime registry, not a match over an enum. The mechanism a plugin architecture needs is present and working.

Trap

The boundary you can see is not the whole story. Which backend may execute is decided by a second object, BackendResolver, fed by a signature‑verified Catalog, against a third registry called IntegrationRegistry — whose own doc comment reads “Empty today, and that is the point.” Bridge has three overlapping registries for one capability. Chapter 21 argues that is what a single named service replaces.

Seven · The god-structConsequence

Read the first line again

Mutex<rusqlite::Connection> is not a storage interface. It is a specific SQLite connection, held by value, reachable from every subsystem that can see BridgeCore. There is no trait Store.

So swapping persistence — for a remote runner, a test double, or the hosted plan Bridge's own issue #119 describes — means touching every call site that reached through that field. The same holds for the event bus, the worktree root, the skill store path, the credential broker and the browser supervisor. Each is a concrete type in a field, and each was the cheapest correct thing to write at the time.

Measured

The Rust core is 70,481 lines and declares 12 public traits. Seven are real extension points: HarnessAdapter, AgentIntegration, BackendDriver, ArtifactFetcher, ProcessSupervisor, ReadinessProbe, Transport. Storage, sessions, the agent loop, scheduling and the UI are not among them.

Eight · Missing seamsTwo defences

Two rows deserve defending, not fixing

Tools and loops are genuinely the provider's job in Bridge's design. The whole premise is supervising Codex and Claude Code rather than reimplementing them, and issue #116 tracks a first‑party loop as a separate deliberate project. Scoring those “no” is not a criticism.

The other five are not design choices. Storage, sessions, sandboxes, scheduling and the UI are concrete because concrete was cheaper — and each now blocks something already in the tracker: the remote runner split (#108), the hosted plan's metering (#119), and a terminal client needing the conversation projection without the React tree (#148).

Trap

Bridge's roadmap has already priced the missing seams without naming them. Issue #148 asks for “pure conversation projection + parity harness against conversation.ts” — a request to extract a plugin boundary out of the UI after the fact. Doing that once per client is the cost of not having done it once.

Nine · App.tsxThe interface

Chapter nine962 lines, 36 states

One React component holds 36 useState calls, 17 useEffect blocks, and the definitions of four other components. It is not a screen; it is the application.

$ wc -l src/App.tsx

    echo "$h: $(grep -c $h src/App.tsx)"; done

Across all 37 non‑test .tsx files there are 140 useState calls. More than a quarter of the application's client state lives in one function body.

The consequence is coupling, not slowness. App.tsx owns the polling loop, the agent‑event batching timer, the file‑mention index, the slash‑command list, the usage rate samples, the forest snapshot key, the pending‑adoption queue and the composer draft — simultaneously. No part of it can be tested, reused by the planned TUI, or reasoned about alone.

Nine · App.tsxIts own rule

The repository already knows better

AGENTS.md states the right rule: “App.tsx owns app state and composes BridgeSidebar, the ComposerPill, AgentConversation, and dialogs. Prefer small, prop‑driven presentational components in src/components/.”

Four components violate it by being defined inside App.tsx instead: EventPanel, Welcome, WelcomeModelBadge and CommandPalette.

Trap

Two of those four are unreachable. Chapter 12 shows CommandPalette and EventPanel are defined and never rendered. The build is strict enough to reject an unused icon import and does not notice an unused local component — so the two defects that look alike get opposite treatment.

Ten · NavigationThe interface

Chapter tenThe combinatorial shell

Bridge's navigation is not a hierarchy. It is four independent switches read by one render function.

Source src/App.tsx 74–80, reflowed to fit. Four orthogonal axes, declared four lines apart, resolved by one nested ternary chain.

The symptom a user feels is inconsistency. Switching to Mission Control silently discards which tab you were on, and openSession resets three axes at once — setView("workspace"); setParadigm("single"); setActiveTab("agent") — because with four independent switches the only way to reach a known state is to stamp on all of them.

The backend has contracts and tests; the frontend has prose. The drift is what that asymmetry predicts.

The events tab with no tab

activeTab's union includes "events". The TabsList offers three tabs — Agent, Changes, Terminal. No control sets "events" and no branch renders it. EventPanel is fully implemented and referenced nowhere.

Thirteen · StatusThe interface

Chapter thirteenThirteen statuses, shouted

A session has thirteen states. The interface renders all thirteen as capitalised words and distinguishes five by colour. The other eight look identical.

  | "waiting" | "warm" | "checkpointing" | "ready" | "stopped"
  | "resuming" | "restored" | "failed" | "completed" | "cancelled";

Source src/protocol/generated/protocol.ts line 800 — generated from the Rust contract, so the vocabulary is deliberate.

Twelve of the thirteen UI labels are the variant in capitals. Only waiting → "NEEDS YOU" was translated into something a user can act on: the right instinct, applied exactly once. In StatusDot, eight statuses collapse to the same grey dot.

Fourteen · KeyboardThe interface

Chapter fourteenFive keymaps, no keymap

A console for supervising concurrent agents is a keyboard tool. Bridge has five separate keydown listeners, no shared registry, and zero occurrences of tabIndex.

Two attach to window, two to document, one sits in the dead WelcomeScreen. Each decides its own precedence and removes itself on unmount, so nothing can answer “what does Escape do right now” — the answer depends on mount order.

What is absent matters more than what is duplicated. There is no shortcut to switch sessions, none to approve or reject a pending approval, none to move between the three trees, and no working command palette. Every one of those is a keystroke in the tools Bridge competes with.

In fairness

Accessibility is not the weak spot. The codebase carries 209 aria-* attributes, 39 explicit role=s and 144 aria-hidden on decorative icons — deliberate, consistent work. The gap is keyboard operation, not screen‑reader labelling. Those two are usually neglected together; here only one was.

Fifteen · DiagnosisThe interface

Chapter fifteenNot a styling problem

Every finding in Part III has one cause, and it is not taste.

Fifteen · DiagnosisConclusion

Read the findings again

612 bypassed tokens. Seventeen ad‑hoc font sizes. Three dead components. An inert command palette. Four competing navigation switches. Five uncoordinated keydown listeners. Two implementations of the welcome screen, two of agent rendering.

Not one of those is a visual judgement. Each is a structural defect that no reviewer was obliged to catch — which is why a redesign would not fix them and would regenerate them.

This is why the rest of this book is about plugin architecture rather than typography. A design system that lives in prose will always lose to a deadline. A design system that lives behind a boundary — where a component can obtain a colour, a size, a status projection or a keybinding only by asking a service for it — cannot be bypassed by accident, because bypassing it means not calling anything.

Part four

The DeepSeek design

What DeepSeek Harness and its Cordis kernel actually claim, read from the project's own documentation rather than the coverage of it.

Sixteen · The claimDeepSeek Harness

Chapter sixteenEverything is a plugin

The motto is load‑bearing rather than decorative: the agent loop and the user interface are plugins on the same footing as a tool.

npx @deepseek-ai/dsh web        # serves the UI on 127.0.0.1:3080

The project states the scope in one sentence: “Every capability is a plugin that can be swapped or recomposed: models, tools, skills, sessions, sandboxes, storage, loops, scheduling, and the UI” — selectable in configuration, without changing Harness source. Most frameworks advertising plugins mean the last two items and keep the rest fixed. Four entries make this different:

CategoryWhy making it swappable is unusual
LoopsThe agent loop is normally the framework. Mounted, a ReAct loop and a plan‑then‑execute loop are two packages, not two forks.
UIWeb, terminal and headless become configurations of one core rather than three clients chasing it.
StoragePersistence behind a boundary is what makes local and hosted the same build.
SessionsHow a transcript is projected into a prompt becomes a policy you choose, not a behaviour you inherit.

Harness also drives other coding agents as sub‑agents, Claude Code and Codex included — Bridge's product, reached from the opposite direction. Bridge built a console that hosts three agents; DeepSeek built a kernel and made hosting agents one of the things you plug in.

Seventeen · CordisDeepSeek Harness

Chapter seventeenContext as service repository

Cordis is the kernel underneath, and its central idea is that plugins find each other through a shared context keyed by name, never through an import.

A context holds services under stable identifiers — ctx.tools, ctx.llm, ctx.sessions, ctx.agents. A plugin needing the tool registry asks the context for tools. It does not import a ToolRegistry class, so it cannot depend on that implementation's internals.

Cordis calls itself a meta‑framework for spatiotemporal composability, and both halves work. Spatially, components can be added and removed without the rest of the system being edited — that is what naming rather than importing buys. Temporally, they can be added and removed while running, in any order, with no boot sequence anyone maintains by hand.

The comparison to hold on to

Bridge's equivalent of ctx is BridgeCore, and the whole difference is naming versus typing. core.db is a Mutex<rusqlite::Connection> — the caller knows it is SQLite. ctx.storage is whatever answered to storage.

Eighteen · LifecycleDeepSeek Harness

Chapter eighteeninject, apply, dispose

A Cordis plugin is a function with two properties. The smallness is the point: a boundary nobody minds implementing is a boundary that gets implemented.

Eighteen · LifecycleCompared

The shape Bridge already half has

A plugin implements Service either as a function carrying an optional inject list and an apply(ctx) body, or as a Service subclass. inject names required services; apply registers what the plugin provides. The kernel handles mounting, unmounting and dependency order.

Compare HarnessAdapter from Chapter 6. Bridge's descriptor() is the declaration step; register() is the mount. What Bridge has no equivalent of is inject — the ability for a component to state its dependencies and be activated once they exist.

That absence has a visible cost. Bridge's startup order is written by hand in built_in_with_opencode_notify, complete with a callback threaded through three functions because OpenCode's catalog discovery finishes after boot. Under inject, that is not a callback. It is a dormant plugin that wakes when its service appears.

Nineteen · DispatchDeepSeek Harness

Chapter nineteenFour ways to dispatch

Cordis gives services four dispatch modes, and choosing between them is the design decision the framework actually asks you to make.

ModeAwaitedOrderReturnsUse it when
emitnoregistrationnolisteners only observe
waterfallnoregistrationyeslisteners may wrap or veto
parallelyesparallelnofan out and wait
serialyesregistrationyesrun in turn, take a result

waterfall is the mode that matters for Bridge. A listener receives the arguments plus a next. Calling next() passes the possibly‑wrapped result down the chain; returning without calling it short‑circuits. So a cooperative listener mutates a shared object and delegates, while a listener that owns a decision terminates the chain.

Twenty · ProfilesDeepSeek Harness

Chapter twentyProfiles instead of forks

The payoff is mundane and enormous: several products out of one codebase, expressed as different sets of mounted plugins. Harness ships Standard, Code, Minimal and Creator profiles — not presets of settings, different assemblies of the same parts.

Bridge needs exactly this, and its own tracker proves it:

Bridge issueWhat it is really asking for
#139, #149–#154 (TUI)the same core with a terminal UI mounted
#148conversation projection separated from the React tree
#107bridge exec --json — the core with no UI at all
#108the core split across a remote runner and a coordinator
#116, #117a first‑party agent loop beside the three adapted ones
#119metering and quotas — a different storage and policy assembly

Six epics, and every one is a profile. Today each will be built as a client or a mode that chases bridge-core's changes. Under a composition model they are configurations, and most of the fourteen TUI issues become “mount a different UI plugin”.

Twenty · ProfilesTeardown

The rule that makes profiles real

Cordis's least glamorous rule is the one the rest depends on: every registration must be reversible. Prompt sections, tools, adapters and listeners install through ctx.effect() or ctx.on(), and both hand back the disposer. The primer is blunt about it — every registration needs a disposer for clean teardown.

Reversibility is what makes reconfiguration true rather than approximately true. A plugin system where mounting works and unmounting leaks is a system you can configure once, at startup, which is a build flag with extra ceremony.

Bridge's teardown is real but hand‑written per subsystem. The daemon stops the accept loop, drains connections, refuses new requests with 2003 shutting_down, then stops adapters so sessions land recoverable. Careful engineering — repeated once per subsystem. It is also why BridgeCore carries fields like worker_activity_persisted: a cadence‑limiting cache with no registration mechanism to hang off went into the root instead.

Trap

This is the strongest argument in the book and also the reason not to rush. The profiles Bridge wants are known now, so the boundaries can be cut to fit them rather than guessed at. Cutting seams for hypothetical plugins is how abstraction earned its bad name; cutting them for six issues already filed is just doing the work once.

Twenty-one · TranslationThe strategy

Build on the last row

Cordis achieves composability in‑process, because it is one TypeScript runtime. Bridge's plugin boundary can instead be the bridged protocol it already ships: 87 contracted methods, generated client types, drift‑tested, newline‑delimited JSON‑RPC 2.0, a single‑owner lease, bounded per‑connection queues and explicit lag notification.

For Bridge's actual product, an out‑of‑process boundary is strictly stronger than an in‑process one. A plugin that crashes does not take the supervisor down. A plugin cannot reach around a trait to touch core.db, because it shares no address space with it. And a third‑party plugin gets no ambient credentials — which is the whole subject of Bridge's issue #105 on credential policy.

The one-sentence version

Bridge should not mount Cordis. It should recognise that bridged is already its Cordis, stop adding fields to BridgeCore, and start expressing capabilities as things that register against a contract.

Twenty-two · The UIAdoption

Chapter twenty-twoDissolving App.tsx

Part III is not fixed by a redesign. It is fixed by the UI having interior boundaries at all — and unlike the Rust core, the frontend can use this pattern literally, today, in TypeScript.

Twenty-two · The UIFour services

Four services, and Part III dies with them

A surface registry replaces the four navigation switches, so a route is one value — and Mission Control cannot silently discard your tab, because there is no second axis to discard.

A presentation service owns the thirteen‑to‑four status projection from Chapter 13. Written once, the TUI in issue #148 gets it for free instead of reimplementing it.

A keymap service replaces five listeners with one registration that returns its own disposer, so “what does Escape do right now” has an answer that does not depend on mount order.

A token service becomes the only way to obtain a colour or a size. At that point the 612 hardcoded values are not a style violation but a call to a function that does not exist — and the difference between those two sentences is the whole argument of Chapter 15.

Twenty-three · The exceptionAdoption

Chapter twenty-threeWhat must never be a plugin

Bridge should refuse one part of the DeepSeek design, and the refusal is not conservatism. If the policy engine is swappable, Bridge has no product.

Return to Figure 1.1: the approval gate is the only node a human touches, and Bridge's claim is that it is deterministic. The README says so of the learning system in as many words — it “can rank eligible candidates, but it cannot grant permissions, widen a write scope, or bypass an approval.”

That sentence is the difference between Bridge and a nicer terminal. “Everything is a plugin” is right for a research harness under MIT; it is wrong for a supervision tool, where an installable plugin that can replace the authorization chain is a supply‑chain vulnerability with a manifest file.

The precise line to draw

Composition is plural; authorization is singular. Anything may participate in a decision — that is what waterfall is for, and a plugin declining to call next() is a perfectly good veto. But only first‑party compiled‑in policy may widen a permission. A plugin can make Bridge more careful; nothing installable may make it less careful. The constraint is cheap: it restricts one direction of one chain and leaves every other seam untouched.

Twenty-four · Order of workRationale

Why this order

P0 first because it is cheapest and it stops the bleeding. Every later phase adds code, and adding code to a codebase with 612 unenforced violations means adding violations. A ratchet — the count may fall, never rise — needs no cleanup campaign and no debate about which of the seventeen font sizes was correct.

P2 before P3 because the frontend services are the smaller, reversible version of the same idea; getting them wrong costs a week rather than an epic. P4 last because trait Store across 70,481 lines is the only genuinely expensive item, and by then three phases will have taught you what the boundary should look like.

What not to do

Do not start at P4, and do not take Cordis as a dependency. The temptation is to fix the core first, because that is where the real coupling is. But the UI is where the user is, the UI is where every finding in Part III lives, and the UI is the one layer where this pattern applies in the same language Cordis is written in — no rewrite, no new dependency, results this month.
