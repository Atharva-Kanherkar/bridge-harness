# Shiki syntax highlighting (issue #295) contract

## Functional Behavior

- [x] Chat code blocks (`Markdown.tsx`'s `CodeBlock`) and diff views (`DiffView.tsx`'s `PatchView`) render plain, escaped text immediately, then upgrade to colorized syntax highlighting once Shiki's grammar for that language loads — first paint is never blocked on the highlighter.
- [x] Colorized output uses the **same** `--syn-*` CSS custom properties chat code, diffs, and the CodeMirror editor already share (`index.css`'s documented "one palette for every piece of code in the app" invariant). Shiki's own bundled theme colors are never emitted directly — only semantic bucket classes (renamed `.hljs-*` → `.stx-*`, same targets). Confirmed live in a real browser: every `.stx-*` class resolves to its own distinct `--syn-*` value in both light and dark mode (see Manual Verification).
- [x] Every language currently supported via `highlight.js` has a confirmed Shiki grammar; none is dropped. The **public** id vocabulary (`normalizeLang`'s output) is unchanged from before this PR — it's a shared contract with `editor/language.ts`'s `LOADERS` map (see below) — but internally, `objectivec`/`ini`/`javascript`/`typescript` load Shiki's more accurate `objective-c`/`toml`/`jsx`/`tsx` grammars via a `SHIKI_GRAMMAR_FOR` indirection that never changes what a caller sees from `normalizeLang`/`languageFromPath`.
- [x] Renaming the public id was tried first and was wrong: it broke `editor/language.ts`'s `loadLanguage(languageFromPath(path))` for `.m`/`.mm`/`.toml`/`.jsonc`/`.json5` (confirmed via a real external review, then independently reproduced by reading `editor/language.ts`'s actual `LOADERS` keys). Fixed by reverting the public vocabulary and adding the indirection above instead. A regression test (`highlight.test.ts`'s "keeps every SHIKI_GRAMMAR_FOR-touched id resolvable by the editor's own loader map") guards this specifically.
- [x] JSX/TSX: fenced ` ```tsx `/` ```jsx ` blocks (and `.tsx`/`.jsx` files) get Shiki's dedicated `tsx`/`jsx` grammars, not the plain `typescript`/`javascript` ones — confirmed the plain grammars actively *misparse* a JSX tag as a comparison expression (`<Button>` read as less-than/greater-than), and confirmed the `tsx` grammar handles plain, JSX-free TypeScript identically to the non-JSX grammar, so this has no downside for ordinary `.ts` content.
- [x] A language with no grammar (unknown extension) renders plain escaped text — never throws, never shows raw unescaped HTML. An *unlabeled* fence (no language tag at all) also renders plain now, which is a real, deliberate behavior change from `hljs`'s `highlightAuto` (which used to guess-colour these) — see "Found during verification" below; this is not "same as today" and the contract shouldn't have said so.
- [x] A grammar/theme load failure (network hiccup, corrupt dynamic import) falls back to plain escaped text instead of crashing the block.
- [x] `highlightPatch(patch, path)` keeps its exact existing synchronous signature and is called the same way at its existing call site — it now returns structurally-correct, plain-escaped rows instantly; the new async `colorizePatch(patch, path)` produces the same rows with color.
- [x] Diffs/code above a re-tuned size cap (`MAX_HIGHLIGHT_CHARS`, lowered from 400,000 to 50,000 — see Manual Verification for why) render plain escaped text rather than paying Shiki's scope-classification cost at a size where it becomes slow.
- [x] A multi-line construct (block comment, template literal) split across diff-added lines keeps consistent coloring on every line it spans — the property `splitHighlightedLines` used to hand-roll for hljs's blob output, now satisfied natively by Shiki's per-line token arrays.
- [x] A streaming assistant message re-rendering `CodeBlock`/`PatchView` on every delta does not re-run Shiki's tokenization on every intermediate length of a still-growing fence — colorization is debounced (`COLORIZE_DEBOUNCE_MS`, 200ms) so only the settled state pays the cost. Confirmed the re-render path is real by reading `AgentConversation.tsx`'s `ItemView`, which renders `<Markdown text={item.text} .../>` on every change to `item.text` regardless of streaming status once there's any text.
- [x] Changing `CodeBlock`'s `body`/`lang` (or `PatchView`'s `patch`/`path`) never paints the *previous* input's coloured HTML under the *new* input, even for one frame. The reset is computed at render time (comparing a cache against current props), not inside a `useEffect` — an effect only runs after commit/paint, so an effect-driven reset has a real one-frame window where React has already painted the new props next to the old cached HTML. `act()`-based jsdom tests can't observe this distinction (it flushes effects synchronously as part of the same act() call), so this is verified by the render-time derivation being structurally impossible to get wrong, not by a paint-timing test.

### Found during verification, outside the original contract

- **A real test flake, not a production bug**: a fixed `setTimeout(0)` wait in the new integration tests wasn't a reliable way to wait for real dynamic-import + real Shiki tokenization once the *entire* 70-file suite ran concurrently (contending for CPU across many Vite-transform workers) — surfaced only under the full `bun run test`, not the isolated file. Replaced with a poll-until-condition helper. Production code was never affected: `CodeBlock`/`PatchView` have no timeout of their own, they just wait for the real promise, however long that takes.
- **Bundle-size note, not a blocker**: per-language chunk sizes vary far more than expected — most languages land under ~30KB, but a few (`cpp` ~797KB, `graphql`, `php`/`objective-c`/`csharp`/`swift`/`jsx`/`tsx` 90–200KB) are heavy, likely because those TextMate grammars embed other languages (e.g. PHP commonly embeds HTML/JS/CSS). Lazy-loading means this cost is paid only when that specific language is actually rendered, but a ~800KB one-time fetch for a C++ snippet is worth knowing about. No before/after byte comparison against the old `highlight.js` baseline was done (would need a separate clean build of `main`); flagging as a good follow-up rather than blocking on it here.

### A real external review of the opened PR, and what came of it

A code review of PR #302 found 5 issues, all independently re-verified before fixing (see commit `fix(highlight): ...` for the full write-up):

1. **P1, confirmed** — renaming `objectivec`/`ini`/`json`'s public id broke `editor/language.ts`'s `LOADERS` contract for `.m`/`.mm`/`.toml`/`.jsonc`/`.json5`. Fixed by reverting the public vocabulary and adding `SHIKI_GRAMMAR_FOR` as an internal-only indirection. Now has a dedicated regression test.
2. **P1, confirmed** — `jsx`/`tsx` fell back to the plain `javascript`/`typescript` grammars, which actively misparse JSX tags rather than merely leaving them uncoloured. Fixed via the same indirection, routing to Shiki's real `jsx`/`tsx` grammars unconditionally (confirmed safe for plain, JSX-free code too).
3. **P1, confirmed** — no debounce meant a streaming reply could schedule a full tokenization pass on every delta of a growing code fence. Fixed with a 200ms debounce (`COLORIZE_DEBOUNCE_MS`).
4. **P2, confirmed** — this contract claimed the unlabeled-fence fallback was "same as today," which is false: `hljs`'s `highlightAuto` used to guess-colour unlabeled fences, and Shiki has no equivalent without paying its classification cost once per candidate grammar. Fixed the wording above to state this as an accepted trade-off, not parity.
5. **P2, confirmed** — the plain-text reset lived in a `useEffect`, which only runs after paint; a real browser could show one frame of the *previous* input's stale coloured HTML. `act()`-based tests couldn't have caught this (it flushes effects synchronously). Fixed by deriving the displayed HTML at render time from a body/lang-keyed cache instead.

All 5 were real; none were dismissed. Full suite re-verified green (3 consecutive full runs) after the fixes, plus 5 new targeted tests.
